Web Security & Authentication

Establish identity and resource permissions, manage sessions and credentials, then examine browser vulnerabilities and API defenses.

Secure applications protect against browser attacks, verify identity, enforce permissions, and defend API endpoints. Each layer addresses a different risk.

Authentication & authorization

Authentication verifies who the user is. Authorization determines what that user may do. For example, signing in establishes identity; checking whether that user can delete a project enforces permissions. Enforce authorization on the server for every protected operation. Scope caches to the correct user or tenant so performance optimizations do not bypass data isolation.

SecurityAPI integrationHTTP
  • OAuth 2.0: A framework for delegated authorization using access tokens, such as allowing an app to access a user’s calendar without sharing their password. OAuth itself is not a login protocol; OpenID Connect (OIDC) adds an identity layer. Browser and mobile apps commonly use the Authorization Code flow with PKCE (Proof Key for Code Exchange), which binds authorization-code redemption to the client that initiated the flow.
  • JWT · JSON Web Token: A token format containing claims, commonly signed and used in authentication and authorization systems. A signed JWT provides integrity, not confidentiality: its payload is readable, so do not put secrets in it. Verify the signature and permitted algorithm, then validate claims including issuer (iss), audience (aud), expiration (exp), and not-before (nbf, when present). JWT is a format; OAuth is a framework, and OAuth access tokens do not have to be JWTs.
  • RBAC · Role-Based Access Control: Assign permissions to roles such as admin, editor, and viewer, then assign roles to users. Also enforce object-level authorization for resource ownership and tenant isolation. Missing these checks can cause IDOR (Insecure Direct Object Reference), also called BOLA (Broken Object Level Authorization) in API security.

Connect the concepts: login, credentials and permissions

Think in three steps: establish identity → carry credentials on later requests → authorize the requested operation. OAuth, JWT and sessions fit into different steps; they are not competing names for login.

Two common architectures: a web backend completes OIDC and creates an opaque browser session, keeping upstream tokens server-side; alternatively, a browser client obtains an access token with Authorization Code + PKCE and calls its intended API. A JWT can also be issued after your own password login. OAuth access tokens can be opaque rather than JWTs.

Cookie versus JWT is not a direct comparison: a cookie is a browser storage/transport mechanism; JWT is a token format. A cookie can contain an opaque session ID or a JWT. A signed JWT does not automatically provide a safer session lifecycle.

OAuth 2.0 and OIDC: follow a sign-in from start to finish

Example: a job platform offers “Sign in with Google.” Google authenticates the user; the platform establishes its own local user and session. OIDC adds identity to the OAuth flow.

PKCE binds code redemption to the verifier held by the initiating client. state correlates the callback to the login attempt and helps prevent login CSRF. nonce binds the OIDC ID token to that authentication request. They address different checks. Use an established OIDC client library and registered redirect URIs; do not invent the protocol.

Continue with session lifecycle and refresh-token rotation. Permission scopes limit delegated access; they do not replace resource-level authorization.

JWT-based authentication: issuing, using and validating a token

A JWT is not a login protocol. It is a token format. After the user authenticates—through your login endpoint or an identity provider—an issuer can create a signed JWT access token. The API validates it on later requests.

SecurityAPI integration
PATCH /api/jobs/42 HTTP/1.1
Authorization: Bearer <access-token>
Content-Type: application/json

{"title":"Senior React Engineer"}

Readable payload example: these claims are signed, not encrypted. This is a decoded illustrative payload, not a usable token.

{
  "iss": "https://identity.example.com",
  "aud": "jobs-api",
  "sub": "user-123",
  "exp": 2000000000,
  "scope": "jobs:write"
}

iss identifies the trusted issuer; aud identifies the intended recipient; sub identifies the subject; exp limits validity; scopes describe granted access. A typical signed JWT has header.payload.signature. Decoding claims is not verification: use a trusted validation library and configured issuer/key source. With asymmetric signing, the issuer signs with a private key and APIs verify using public keys, commonly published through JWKS; plan for key rotation.

What this does not solve: XSS, safe token storage, immediate revocation or object permissions. See storage tradeoffs, logout/revocation and object-level checks. Do not send bearer tokens in URLs or log them. An opaque session is often simpler when one web backend owns authentication and requests.

Protect the login: passwords, MFA and abuse

A correct token flow still depends on secure authentication and recovery. Know these foundations; use maintained authentication libraries or an identity platform for the mechanisms.

SecurityAPI integration
  • Password hashing: store salted, deliberately expensive password hashes, such as Argon2id—not plaintext, reversible encryption or a fast general-purpose hash. Verify with the password-hashing library; TLS protects credentials in transit.
  • MFA and passkeys: an additional factor reduces password-only compromise. WebAuthn/passkeys use origin-bound public-key credentials and resist phishing; MFA methods have different security properties.
  • Login abuse: rate-limit attempts with account and network signals, detect credential stuffing and use non-enumerating error/recovery responses. Avoid a lockout policy that lets attackers trivially deny access to other users.
  • Password reset / account recovery: use expiring, single-use recovery credentials and a verified delivery path; protect against enumeration. Revoke affected sessions according to policy and require reauthentication for sensitive changes.
  • Trust boundaries: the frontend can hide controls, but the server must validate credentials and enforce permissions. CORS, route guards and a decoded JWT are not authorization controls.

Study next: the existing session/storage/rotation lifecycle, RBAC and object-level access, and XSS, CSRF, injection and clickjacking. Connect each attack to the trust boundary and its prevention mechanism.

Session lifecycle: establish, renew & expire

A session links subsequent requests to an authenticated identity. A server-side session commonly uses an opaque cookie identifier; token-based APIs may use short-lived access tokens and longer-lived refresh credentials. Both designs need expiration, revocation, and server-side authorization.

SecurityAPI integrationHTTP
  1. Establish: Verify credentials or complete OIDC, then rotate the session identifier after login or privilege changes to prevent session fixation. Set appropriate cookie attributes and return only the user data the UI needs.
  2. Use: Validate the session or token on protected requests. Apply idle and absolute timeouts appropriate to the application. A frontend timer is a UX hint; the server enforces expiration.
  3. Renew: Refresh through the intended protocol or session endpoint. Coordinate concurrent renewal attempts and retry the original request at most under a bounded policy. Avoid recursive refresh loops; an unauthenticated 401 differs from a permission-denied 403.
  4. End: Invalidate the relevant server session or refresh credential and clear identity-scoped client data. Require reauthentication for sensitive actions when the risk warrants it.

Cookie configuration: Use Secure, HttpOnly, an appropriate SameSite policy, and narrow scope. A __Host- cookie requires Secure, Path=/, and no Domain attribute, reducing domain-scoping mistakes. Cross-site cookie flows may require SameSite=None; Secure and can still face browser restrictions. Cookie storage does not replace XSS prevention.

Refresh-token rotation & replay detection

SecurityConcurrency

With refresh-token rotation, the authorization server issues a replacement refresh token and invalidates the previous one on successful redemption. Reuse of an invalidated token can indicate theft; the server can revoke the affected token family and require reauthentication according to its policy. Short access-token lifetimes limit exposure but do not make already-issued tokens immediately revocable.

Concurrency trap: Two tabs redeeming the same refresh token can look like replay. Coordinate renewal through a shared owner/BFF or a suitable coordination mechanism; a promise shared within one tab does not coordinate other tabs. Follow the identity provider’s rotation and reuse policy, and avoid storing refresh tokens in ordinary web storage. BroadcastChannel can distribute session-change notifications without distributing credentials.

Logout, revocation & cache cleanup

SecurityResource lifecycle
  • Server boundary: Invalidate the session or revoke refresh credentials through a protected endpoint. Clear cookies with matching name, path, and domain scope. Local token deletion alone does not invalidate a stolen token.
  • Access-token limits: A self-contained JWT can remain valid until expiry unless resource servers consult revocation/introspection or another server-side policy. Local app logout and identity-provider logout are distinct operations.
  • Client boundary: Clear user/tenant query caches, stores, and sensitive persisted drafts; close real-time subscriptions. Cancel reads and prevent already-started responses from repopulating the previous user’s cache. Notify other tabs and revalidate on resume.
  • Failure behavior: If server invalidation fails, report that logout was not fully confirmed; clearing the local UI does not prove remote revocation. Personalized responses also need appropriate HTTP caching policies.

Object-level authorization: enforce access per resource

BOLA / IDOR occurs when an API accepts a resource identifier without checking whether the authenticated principal may perform the requested action on that specific object. A valid login and an “editor” role are insufficient if the object belongs to another tenant.

SecurityAPI integrationHTTP

Example: For PATCH /api/projects/42, derive identity and tenant membership from the validated session; load project 42 within an authorized tenant/ownership scope; verify edit permission; allowlist editable fields; then write. Do not trust a client-supplied tenant ID, hidden button, or unguessable UUID as authorization. Apply equivalent checks to reads, downloads, list queries, batch endpoints, and real-time subscriptions.

Implementation and tradeoff: Centralize policy checks so every handler enforces the same rules, while keeping resource-specific decisions explicit. Recheck permissions when membership changes and deny by default. Cache isolation and UI permission checks improve correctness and UX but never replace this server enforcement; see identity-scoped query lifecycles.

Web vulnerabilities

XSS · Cross-Site Scripting

SecurityBrowser

What happens: An attacker injects malicious JavaScript that runs in the context of your website, potentially reading page data or acting as the user.

Prevent it: treat user input as text, not executable code.

  • Output encoding (escaping): React escapes text interpolated as {comment}. When accepting children or render props, distinguish text nodes from intentionally supplied markup. For plain DOM code, element.textContent = comment is a safe DOM sink: it inserts text without parsing HTML. Encoding must match the output context; HTML escaping alone does not make arbitrary URLs or JavaScript safe.
  • HTML sanitisation: Sanitise rich HTML with a trusted library such as DOMPurify to remove unsafe elements, attributes, and URL schemes while keeping permitted markup. Never send raw user input to innerHTML or dangerouslySetInnerHTML.
  • Content Security Policy (CSP) — defense in depth: Restrict script execution with script-src, using nonces or hashes for approved scripts. CSP supplements output encoding and sanitisation. These protections remain necessary with both CSR and SSR.

CSRF · Cross-Site Request Forgery

SecurityBrowser

What happens: An attacker tricks an authenticated browser into sending an unwanted request, such as changing an email address. The attack relies on credentials the browser sends automatically, typically session cookies.

Prevent it: a login cookie alone should not approve a sensitive action.

  • CSRF token validation: With the synchronizer token pattern, include an unpredictable, session-bound token in state-changing requests. The server validates it; the browser’s same-origin policy prevents an attacker’s site from reading it, assuming no XSS or permissive cross-origin access.
  • SameSite cookie policy: Use SameSite=Lax or Strict where your flow allows it. This restricts when cookies accompany requests from other sites.
  • Origin validation & safe HTTP methods: Validate the Origin header against trusted origins, with a Referer check where appropriate. Client-side default-action cancellation does not protect a server endpoint from CSRF. GET must have read-only semantics; use state-changing methods such as POST with CSRF protection.
Key distinction: XSS runs attacker code inside your site. CSRF exploits the browser’s existing authentication to send requests. HttpOnly cookies prevent JavaScript from reading the cookie, but do not stop injected code from making authenticated requests.

SQL injection

SecurityAPI integration

The trap: User input becomes part of a SQL command.

Prevent it: parameterized queries (parameter binding). Keep SQL structure separate from values by binding input to placeholders. The database treats bound values as data, even if they look like SQL. Dynamic table names, column names, and sort directions require an allowlist; value placeholders do not cover SQL identifiers.

// Parameterized query (placeholder syntax depends on your DB driver)
db.query('SELECT * FROM users WHERE email = ?', [email]);

Clickjacking

SecurityBrowser

The trap: An attacker hides your page inside an iframe and tricks a user into clicking its buttons.

Prevent it: anti-framing with CSP frame-ancestors. This prevents UI redressing through framing. Send this HTTP response header to block all framing:

Content-Security-Policy: frame-ancestors 'none'

Use 'self' if your own site needs to embed it. X-Frame-Options: DENY is a legacy alternative for blocking frames.

Open redirects

SecurityBrowser

The trap: A trusted-looking link to your app forwards the user to an attacker’s site.

Prevent it: redirect destination validation using an allowlist.

  • Server-side route mapping: Accept a destination key such as next=dashboard and map it to a fixed route such as /dashboard.
  • URL parsing & origin validation: Resolve the URL with a standard parser, then validate its scheme and origin against an explicit allowlist. Checking that it starts with / is insufficient: //evil.example points to another site.

API security

  • Rate limiting: Restrict request frequency to reduce abuse, brute-force attempts, and resource exhaustion. Apply limits by user, API key, or IP as appropriate; Common algorithms include token bucket (allows controlled bursts) and sliding window (limits requests over a rolling interval). Return 429 Too Many Requests, optionally with Retry-After, when limits are exceeded.
  • HTTPS / TLS (Transport Layer Security): Provides confidentiality and integrity in transit, plus server authentication through certificate validation. TLS does not replace input validation or access checks.
  • CORS · Cross-Origin Resource Sharing: Browser-enforced rules controlling whether JavaScript from another origin can read a response. CORS builds on the same-origin policy (SOP); an origin is the scheme, host, and port. Configure Access-Control-Allow-Origin for trusted origins. Cookie-based credentialed requests also require Access-Control-Allow-Credentials: true and cannot use a wildcard allowed origin. For requests requiring a preflight, the browser sends OPTIONS to check permission before the actual request. CORS does not stop every cross-origin request or restrict non-browser clients, so it cannot replace authentication, authorization, or CSRF protection.

For GraphQL, a single request may select substantial work. Apply operation cost limits and field/resource authorization alongside the HTTP and identity protections here.

Interview-ready answer

I separate identity, permissions, and attack prevention. Authentication establishes who the user is; server-side authorization checks what they can do. I prevent XSS with context-appropriate output encoding and HTML sanitisation, CSRF with token validation and SameSite cookie policies, and SQL injection with parameterized queries. For APIs, I use TLS, validate tokens, enforce access checks and rate limits, and configure CORS for the intended browser origins. OAuth delegates access, while JWT is one possible token format.
