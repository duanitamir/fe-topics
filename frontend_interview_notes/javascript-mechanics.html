Lexical scope, closures & lifetime

Lexical scope resolves names from where code is defined. A closure retains access to its surrounding lexical environment after the outer function returns. It captures bindings, not an automatic frozen copy of every value.

JavaScriptResource lifecycle

Closure: a function keeps access to where it was created

A binding is the association between a variable name and its value. A lexical environment holds bindings and links to surrounding environments. A closure is a function together with access to its surrounding lexical environment. You do not explicitly create a special closure object; JavaScript functions retain this access when they are created.

In the counter below, the returned arrow function uses count, which belongs to makeCounter. Returning ends that invocation of makeCounter, but the returned function can still read and update that invocation’s count. That continuing access is the closure.

function makeCounter() {
  let count = 0;
  return () => ++count;
}
const next = makeCounter();
next(); // 1
next(); // 2
  1. makeCounter() creates a new binding: count = 0.
  2. It creates and returns a function that accesses that binding.
  3. next now refers to the returned function. The outer call has finished; its execution frame is no longer on the call stack.
  4. The first next() changes the retained binding to 1; the second changes the same binding to 2. The counter does not restart because makeCounter is not being called again.

Separate calls, separate state: const other = makeCounter(); other(); returns 1, even after next() has returned 2. Each invocation creates a different count binding.

Capturing a binding versus computing a snapshot

A closure does not automatically copy the value a variable had when the function was created. It reads the binding when it executes. A separately computed value can still be a snapshot:

function createReader() {
  let count = 0;
  const message = `Initial count: ${count}`;

  return {
    increment: () => { count += 1; },
    read: () => ({ count, message }),
  };
}

const reader = createReader();
reader.increment();
reader.read(); // { count: 1, message: 'Initial count: 0' }

increment and read share the same invocation’s environment. read sees the updated count. But message was computed once as a string; it is not a formula that re-runs when count changes. To get a fresh message, compute it inside read. This distinction helps explain stale closures and derived snapshots.

Lifetime: how long the function and retained data remain reachable

Scope answers “Where can this name be accessed in the source code?” Lifetime answers “How long does this value or environment remain available during execution?” A local binding can outlive the function call that created it when a reachable closure still needs it.

JavaScript uses reachability-based garbage collection. While application code, a registered event listener or another live reference can reach the closure, the bindings and objects it needs must remain available. Once no live reference can reach them, they become eligible for garbage collection. Collection is not immediate or scheduled by your code. Engines can optimize unused bindings; do not assume every local variable is always retained.

Practical lifetime: an event listener can keep data alive

function attachPreview(button, job) {
  const onClick = () => {
    console.log(job.description);
  };

  button.addEventListener('click', onClick);
  return () => button.removeEventListener('click', onClick);
}

let dispose = attachPreview(document.querySelector('#preview'), job);
// Later, when this interaction is no longer needed:
dispose();       // Remove the listener's reference to onClick.
dispose = null;  // Release our reference to the cleanup closure too.

A reachable button’s listener retains onClick, whose closure accesses job. The returned cleanup function also references the handler. Removing the listener and releasing the cleanup reference removes these retention paths; the job object can be collected only if nothing else still references it. Closures are useful and normal: a memory leak happens when an unintended live reference retains data longer than needed. Cycles alone do not prevent collection.

In a React effect, return the cleanup function so React removes the listener at the effect’s lifecycle boundary. See listener lifecycle and render snapshots and effect dependencies.

Interview explanation: “A closure lets a function access bindings from the lexical environment where it was created. Those bindings can outlive the outer call while the closure remains reachable. Scope determines visibility; reachability determines whether retained data can be garbage-collected.”

Use: Encapsulated state, callbacks, factories, and dependency injection. Each factory invocation has a separate environment; closures created within the same invocation can share bindings. Closures are ordinary functions, not separate threads.

Pitfalls: var is function-scoped; let/const are block-scoped and cannot be accessed before initialization because of the temporal dead zone. const prevents reassignment of the binding, not mutation of an object. Long-lived callbacks can retain large environments.

React connection: Each render creates a new snapshot and closures from that render observe its values. Use correct dependencies, functional updates, or refs according to the intended lifecycle; see render snapshots and dependencies. Do not suppress dependencies merely to keep a closure stable.

this, arrow functions & method invocation

For ordinary functions, this depends on how the function is called. A method call binds its receiver; extracting the function loses that receiver. Arrow functions inherit this lexically and cannot be rebound with call/apply/bind.

JavaScript
const counter = {
  value: 2,
  read() { return this.value; }
};
counter.read(); // 2
const read = counter.read.bind(counter);
read(); // 2, even when passed as a callback.

Use: Understand method callbacks in SDKs and classes. call/apply invoke with an explicit receiver; bind creates another function. In strict mode, an ordinary unbound call has undefined this.

Choose deliberately: Arrow callbacks suit lexical behavior; use an ordinary method when the receiver should vary. A closure with explicit parameters often avoids receiver ambiguity entirely. Repeated bind() creates new references; listener removal requires the original callback identity.

Objects, prototypes & classes

Prototype delegation searches an object’s own properties first, then its prototype chain. Class methods typically live on the prototype; a class is JavaScript syntax with additional semantics, not a separate inheritance runtime.

JavaScriptArchitecture
class Counter {
  constructor() { this.value = 0; }
  increment() { this.value += 1; }
}
const counter = new Counter();
Object.hasOwn(counter, 'value');     // true
Object.hasOwn(counter, 'increment'); // false

Use: Reading library behavior, understanding shared methods, and integrating class-based APIs. Class field arrow functions are created per instance; prototype methods are shared. Native #private fields provide runtime private access, unlike TypeScript’s ordinary private modifier.

Alternatives and pitfalls: Prefer composition and functions when inheritance does not represent a stable substitutable relationship. Avoid changing built-in prototypes. Use Object.hasOwn when inherited keys must not count, and validate untrusted object keys to avoid prototype-pollution paths. A Map can be clearer for a dynamic key/value registry.

Equality, mutation & copying

Primitives compare by value; objects compare by identity. Assigning or passing an object copies its reference value, so two variables can refer to the same mutable object. JavaScript passes arguments by value, including reference values.

JavaScriptState management
const previous = { user: { name: 'Ada' }, count: 1 };
const shallow = { ...previous };
shallow !== previous;             // true
shallow.user === previous.user;   // true
const next = { ...previous, user: { ...previous.user, name: 'Grace' } };
// Only the changed path has new identities; previous remains unchanged.

Use: Immutable state updates and predictable cache selectors. Spread/Object.assign are shallow copies. structuredClone supports many structured values and cycles, but not functions or DOM nodes and does not preserve arbitrary custom class behavior. JSON round-tripping loses or rejects values such as undefined, dates-as-dates, BigInt, and cycles.

Equality details: === considers NaN unequal to itself and +0/-0 equal; Object.is does the opposite for those cases. React uses Object.is in several identity comparisons. Map/Set use SameValueZero for keys/values.

When not to deep-copy: Deep-cloning every update wastes work and destroys unchanged reference identities. Use structural sharing or a maintained immutable-update helper; see referential stability and memoization.

Property descriptors: ownership, visibility & mutation

A property descriptor defines an own property’s behavior. A data descriptor contains value and writable; an accessor descriptor contains get and/or set. Both can specify enumerable and configurable. A property cannot be both a data property and an accessor.

JavaScript
const account = {};
Object.defineProperty(account, 'id', {
  value: 'u-42',
  writable: false,
  enumerable: true,
  configurable: false
});
Object.keys(account); // ['id']
Object.getOwnPropertyDescriptor(account, 'id');
// In strict mode, assigning account.id throws TypeError.

Mechanics: For a new property created with Object.defineProperty, omitted boolean attributes default to false; ordinary object-literal data properties normally have all three true. Non-configurable restricts deletion and redefinition, with limited permitted transitions such as writable true to false.

Use: Library contracts, getters for computed views, and understanding why a property cannot be changed. Object spread and Object.assign read enumerable own property values, including symbols, and may execute getters; they do not clone descriptors or prototypes. Use getOwnPropertyDescriptors with Object.create when descriptor preservation is intentional.

Alternatives & limits: Prefer plain objects for application data. Object.freeze is shallow and does not prevent mutation inside nested objects or disable an accessor’s setter; TypeScript readonly is a static restriction. Non-enumerable is not private or secure. Connect this to identity and copying and readonly contracts.

Coercion: explicit conversion & operator semantics

Type coercion converts values between types. Boolean contexts use truthiness; arithmetic and comparison operators apply their own conversion rules. Objects can customize primitive conversion through Symbol.toPrimitive, or valueOf/toString fallbacks.

JavaScript
Boolean('false');     // true: a non-empty string
Number('');           // 0: often wrong for an empty form field
Number('12px');       // NaN
'5' + 1;              // '51': string concatenation
'5' - 1;              // 4: numeric conversion
0 ?? 10;              // 0: only null/undefined trigger fallback
0 || 10;              // 10: any falsy value triggers fallback
null == undefined;    // true
null === undefined;   // false

Use: Normalize values at an explicit boundary, such as URL parameters or form inputs. Check empty input before Number, then validate Number.isFinite and domain constraints. parseInt parses a prefix and can accept trailing garbage; it is not general numeric validation.

Pitfalls: Empty arrays and objects are truthy; NaN is unequal to itself; strict equality still compares object identity. Mixing BigInt and Number in arithmetic generally throws. Prefer strict equality and intentional conversions; a deliberate value == null check can cover null and undefined when the team agrees on that convention.

React connection: count && <Badge /> can render 0; use count > 0 when the condition must be boolean. See equality and boundary validation.

Iteration protocols: iterable, iterator & generator

An iterable exposes [Symbol.iterator](), returning an iterator whose next method produces { value, done }. for…of, array spread, and destructuring consume this protocol. A generator function produces a generator that is both an iterator and an iterable.

JavaScriptResource lifecycle
function* range(end) {
  for (let value = 0; value < end; value++) yield value;
}
const numbers = range(3);
numbers.next(); // { value: 0, done: false }
[...numbers];   // [1, 2]: this generator instance is consumed
[...range(3)];  // [0, 1, 2]: a fresh instance

Use: Lazy transformations, traversal, and sequences that should not be fully allocated up front. A generator suspends at yield; it does not create a background thread. Avoid spreading a large or unbounded iterable into memory.

Distinctions: An array is reusable as an iterable; a generator instance generally advances once through its sequence. for…in enumerates enumerable string keys, including inherited ones; for…of consumes values. Plain objects are not iterable by default—choose Object.entries for key/value iteration.

Lifecycle & alternatives: Early exit from for…of calls an iterator’s return method when present; generator finally blocks can clean up resources. Prefer array map/filter for small materialized collections. Async iterables use Symbol.asyncIterator and await each next result; see async iteration and backpressure.

Module execution order: linking, live bindings & cycles

ES modules are linked before their bodies execute: imports connect to exported bindings, rather than copying snapshots. Evaluation follows dependencies; module text order is not a global scheduling guarantee. A module is normally evaluated once per resolved module identity within its environment.

JavaScriptTooling
// counter.mjs
export let count = 0;
export function increment() { count++; }

// main.mjs
import { count, increment } from './counter.mjs';
console.log(count); // 0
increment();
console.log(count); // 1: an imported live binding
// count = 2;       // invalid: import bindings are read-only to importers

Cycles: Circular imports can link successfully, but reading a let/const/class binding before initialization throws a ReferenceError. Function declarations can be available earlier; relying on evaluation-order accidents still creates fragile coupling. Break cycles by extracting shared contracts or injecting dependencies.

Async modules: Top-level await delays dependent module evaluation; it does not block the whole JavaScript thread. Independent branches may proceed. Dynamic import returns a promise for a module namespace and is useful for optional code; it does not guarantee a separate network chunk in every build.

Use & tradeoffs: Keep module top-level work small and predictable. Use an explicit initialization function when ordering, failure, or cleanup needs control. CommonJS executes require synchronously and cycles can expose partially initialized exports. For format/resolution, tree shaking, and bundling, use the module-boundary section; for scheduling, see the existing event-loop explanation.

Garbage collection & memory leaks

JavaScript garbage collection reclaims objects that are no longer reachable from live roots. An unwanted object that remains reachable is a memory leak; cycles alone are not necessarily leaks.

JavaScriptPerformanceResource lifecycle

Example: A window listener keeps a closure alive, which retains a detached panel and its data. An unbounded Map cache or timer can cause the same retention even when the UI disappears.

Investigate: Reproduce repeated mount/unmount or navigation, compare heap snapshots, inspect retained objects and their retaining paths, and check whether memory stabilizes after collection. Allocation volume and retained memory are different measurements.

Prevent: Define cache size/eviction and resource disposal. WeakMap/WeakSet avoid strongly retaining keys but are not general cache eviction policies: keys are non-enumerable and collection timing is nondeterministic. FinalizationRegistry does not provide reliable timely cleanup.

Interview review: reason from the runtime

Explain where a variable resolves, which invocation owns its binding, how a function gets its receiver, which object identities change, and what keeps data reachable. Use those mechanisms to explain stale closures, failed memoization, mutation bugs, and retained listeners rather than memorizing isolated output puzzles.
