Static types vs. runtime validation

TypeScript checks code statically and erases most type syntax during compilation. It does not validate incoming JSON, enforce authorization, or change JavaScript runtime behavior. A type assertion tells the compiler to trust you; it is not a conversion or validation step.

TypeScriptSecurityAPI integration
type User = { id: string; name: string };
function isUser(value: unknown): value is User {
  return typeof value === 'object' && value !== null
    && 'id' in value && typeof value.id === 'string'
    && 'name' in value && typeof value.name === 'string';
}
const raw: unknown = JSON.parse('{"id":"42","name":"Ada"}');
if (!isUser(raw)) throw new Error('Invalid user response');
raw.name.toUpperCase(); // Narrowed to User.

Use: Treat network/storage values as unknown and validate at trust boundaries. For complex schemas, use a maintained schema validator and infer compatible types where possible. A hand-written type predicate can lie too; verify its checks and contract.

Choose: unknown requires narrowing before use; any disables checking and can propagate unsafety. Reserve any for constrained interop boundaries rather than application-wide models. Generated API types improve consistency but still do not validate a response.

Structural typing, interfaces & object contracts

Structural typing checks whether a value has the required shape, rather than requiring a declared nominal relationship. Extra-property checks on fresh object literals catch likely mistakes, but TypeScript object types are not generally exact object schemas.

TypeScriptArchitecture

Example: A value with id, name, and avatar can satisfy a function accepting only id/name. Use interface for extendable object contracts and type for unions, tuples, and other compositions; both can describe most ordinary object shapes.

Important distinctions: readonly restricts writes through that type, not runtime mutation or deep aliasing. Optional properties and explicit undefined are not always interchangeable, especially with exactOptionalPropertyTypes. Enable strict null checking and avoid treating missing data as present with repeated non-null assertions.

When not to model everything: Prefer small domain contracts over types that mirror every implementation detail. Branded types can prevent accidental mixing of structurally identical IDs, but require disciplined constructors/validation; they are not a runtime security mechanism.

Discriminated unions, narrowing & never

A discriminated union represents valid alternatives with a shared literal field. Narrowing refines the type through control flow. never represents an impossible value and can enforce exhaustive handling as the union evolves.

TypeScriptState management
type Result =
  | { status: 'success'; value: string }
  | { status: 'error'; message: string };
function assertNever(value: never): never {
  throw new Error('Unhandled result');
}
function describe(result: Result): string {
  switch (result.status) {
    case 'success': return result.value;
    case 'error': return result.message;
    default: return assertNever(result);
  }
}

Use: Async outcomes, reducer actions, parser results, and component props with mutually exclusive modes. This avoids optional fields that permit impossible combinations. See the state-machine union.

Alternatives: A boolean is enough for one independent toggle. Avoid a large union for unrelated data; separate responsibilities. Narrow unknown inputs with checks before relying on the discriminant.

Generics, constraints & reusable APIs

Generics preserve relationships between types. A useful generic says how an input type relates to an output or another input; it is more than a placeholder for any.

TypeScriptArchitecture
function byId<T extends { id: string }>(items: readonly T[], id: string): T | undefined {
  return items.find(item => item.id === id);
}
const user = byId([{ id: '42', name: 'Ada' }], '42');
// user is { id: string; name: string } | undefined; the name field is preserved.

Use: Generic collections, typed component items, and adapters that preserve a domain model. Constrain only what the implementation needs; allow inference instead of requiring many explicit type arguments.

Tradeoffs: Deep conditional types and broad generic component APIs can make errors inscrutable. If two inputs need no type relationship, a concrete interface or unknown is often clearer. Avoid a “generic” response helper that simply casts unvalidated JSON to T.

Comparison: Use unions for known alternatives, overloads for distinct call signatures where inference benefits, and generics for a relationship that varies across calls. These choices complement reusable component contracts.

satisfies, const assertions & utility types

satisfies checks assignability without replacing the expression’s inferred type with the target type. as const preserves literal types and makes literal object/array members readonly at the type level; neither freezes an object at runtime.

TypeScript
const routes = {
  home: '/',
  profile: '/profile'
} as const satisfies Record<string, `/${string}`>;
type RouteName = keyof typeof routes; // 'home' | 'profile'

type User = { id: string; name: string; email: string };
type UserSummary = Pick<User, 'id' | 'name'>;
type EditableUser = Omit<User, 'id'>;

Use utilities: Pick/Omit define projections; Record describes keyed values; Partial makes fields optional; ReturnType/Awaited extract related types. Partial is shallow and is not automatically a valid PATCH schema—some field combinations may be forbidden.

Choose deliberately: Use an annotation when callers should see an abstract contract, satisfies to check a configuration while retaining its useful inferred shape, and an assertion only when external evidence justifies it. Prefer an explicit domain type over a long chain of utility transformations that hides business meaning.

Interview review: types express guarantees you can defend

Show how types eliminate invalid states, preserve input/output relationships, and expose null/error paths. Then identify where runtime validation is still necessary. A well-typed API should be easier to use correctly, not simply impressive to read. Connect contracts to server validation and generated GraphQL types.
