Node.js Runtime & Server Execution

Choose the right execution resource, bound concurrency, and make request and process lifecycles explicit. Build on the existing event-loop foundation.

Server execution: separate JavaScript, I/O & CPU work

Node.js runs application JavaScript on an event-loop thread per isolate, while delegating work to operating-system facilities and runtime workers. Concurrency allows many requests to be in flight; it does not make CPU-heavy JavaScript execute in parallel on the same thread.

JavaScriptConcurrencyPerformance

Follow the existing foundation: Tasks, microtasks, starvation, and scheduling are explained in Event loop & scheduling. Node adds host-specific phases and process.nextTick; it has no DOM rendering phase. Do not assume browser timer ordering or memorize one timer/immediate output as a universal guarantee.

Diagnose: A slow endpoint can wait on I/O, wait for pooled capacity, or block the event loop. Measure event-loop delay/utilization alongside CPU, dependency latency, and queue wait time. High latency alone does not identify which resource is saturated.

Choose: Await asynchronous I/O for database/network work. Use bounded worker capacity for expensive computation. Async syntax around a large synchronous JSON parse or a CPU loop still blocks the thread. Connect execution to the request pipeline.

libuv thread pool: shared capacity & saturation

The libuv thread pool handles selected operations that cannot use the same non-blocking mechanism as network sockets. Common consumers include many asynchronous filesystem operations, crypto operations such as pbkdf2/scrypt, zlib, and dns.lookup. Network socket I/O generally uses OS readiness/completion mechanisms instead.

ConcurrencyPerformance

Example: A burst of password-hash jobs can occupy the pool and delay unrelated filesystem or DNS work. The process-wide pool is shared across event loops, including worker threads; moving pool-using APIs into a worker does not automatically create an independent libuv pool.

Diagnose & control: Measure operation latency under concurrent load, bound expensive work, and apply admission control. The default pool size is typically four; UV_THREADPOOL_SIZE is configured before initialization. Raising it can help only when CPU/memory and the workload support greater concurrency.

Alternatives: Use worker threads for CPU-heavy JavaScript, dedicated services/processes for stronger isolation, and dependency-specific concurrency limits. dns.resolve uses a different DNS path and has different behavior; it is not a drop-in optimization for dns.lookup. See bounded concurrency and bulkheads.

Worker threads: parallel CPU work with explicit ownership

A worker thread runs JavaScript in a separate isolate with its own event loop. Use it for expensive CPU work such as parsing, transformations, or computation that would otherwise delay every request on the main thread. It is usually unnecessary for ordinary asynchronous network I/O.

JavaScriptConcurrencyResource lifecycle
// main.mjs — a minimal one-job demonstration, not a production pool
import { Worker } from 'node:worker_threads';
const worker = new Worker(new URL('./compute.mjs', import.meta.url), {
  workerData: { limit: 1_000_000 }
});
worker.once('message', result => console.log(result));
worker.once('error', error => console.error(error));
worker.once('exit', code => {
  if (code !== 0) console.error('Worker failed:', code);
});

// compute.mjs
import { parentPort, workerData } from 'node:worker_threads';
let sum = 0;
for (let i = 0; i < workerData.limit; i++) sum += i;
parentPort.postMessage(sum);

Mechanics: Messages usually use structured cloning; transferable ArrayBuffers move ownership and detach the sender’s buffer. SharedArrayBuffer shares memory and requires deliberate synchronization, commonly using Atomics. Worker threads do not receive the main thread’s ordinary object references.

Production contract: Reuse a bounded worker pool, bound its queue, reject overload, enforce job deadlines, and handle error/exit/shutdown. Worker creation and serialization cost can exceed the computation saved. Cancellation requires an explicit protocol or termination; rejecting a caller’s promise alone does not stop computation.

Comparison: Workers share a process and some native resources; child processes provide stronger isolation at higher overhead. Browser Web Workers solve a related responsiveness problem using different APIs; see Web Workers.

Streams & backpressure: bound memory as data flows

A stream processes data incrementally. Readable streams produce chunks; writable streams consume them; transform streams do both. Backpressure makes a fast producer respect a slower consumer instead of buffering an entire file or response in memory.

Resource lifecyclePerformance
import { createReadStream, createWriteStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';
import { createGzip } from 'node:zlib';

await pipeline(
  createReadStream('input.log'),
  createGzip(),
  createWriteStream('input.log.gz')
); // Coordinates backpressure and destroys the pipeline on failure.

Mechanics: A writable write returning false means the chunk was accepted but the producer should wait for drain before continuing. highWaterMark is a buffering threshold, not a strict global memory cap; object-mode thresholds count objects rather than bytes.

Use: Large uploads/downloads, exports, compression, and incremental transformations. pipeline is preferable to hand-wiring pipe and independent error listeners for most complete flows. In supported Node versions, pass an AbortSignal to cancel a pipeline; propagate client disconnects when work should stop.

Tradeoffs: Buffered reads are simpler for small bounded payloads. Incremental parsers must handle boundaries across chunks; streaming does not remove validation limits. Once HTTP headers are sent, a later stream error cannot become a clean JSON error response. See async iteration for the protocol-level model.

Graceful shutdown: stop admission, drain & close

Graceful shutdown lets accepted work finish within a deadline while stopping new work. It prevents an ordinary restart from unnecessarily dropping requests, abandoning transactions, or losing buffered telemetry.

ResilienceResource lifecycle
  1. Mark unready: stop being selected for new traffic; account for routing propagation delays.
  2. Stop admission: stop accepting new connections/work and reject new jobs appropriately.
  3. Drain: track in-flight requests and jobs; allow completion within a bounded period.
  4. Close dependencies: release database pools, message clients, workers, and telemetry after their users finish.
  5. Enforce a deadline: abort remaining work and close lingering connections; report incomplete work.

Implementation: Make SIGTERM/SIGINT handling idempotent. server.close stops accepting connections and waits for eligible connections to close; idle-connection behavior depends on the supported Node version. Track WebSockets/SSE separately because long-lived connections need a shutdown/reconnect contract. Installing signal handlers means the application must finish shutdown itself.

Pitfalls & alternatives: Calling process.exit immediately can truncate responses and logs. The exit event cannot run awaited cleanup. Crashes and forced termination still happen, so use idempotency and explicit retry semantics rather than treating graceful shutdown as a delivery guarantee. See real-time connection lifecycles.

AsyncLocalStorage: request context across async boundaries

AsyncLocalStorage propagates context through associated asynchronous execution so logs and traces can carry a request ID without passing it through every utility. It stores execution context, not globally shared “current request” state.

JavaScriptResource lifecycle
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';
import { createServer } from 'node:http';

const context = new AsyncLocalStorage();
function log(message) {
  console.log(JSON.stringify({ requestId: context.getStore()?.requestId, message }));
}
createServer((request, response) => {
  context.run({ requestId: randomUUID() }, () => {
    setTimeout(() => {
      log('request completed');
      response.end('ok');
    }, 10);
  });
}).listen(3000);

Use: Correlation IDs, trace context, and structured diagnostic metadata. run scopes a store to the callback and async work created inside it. Prefer a fresh, small store per request; do not reuse a mutable global context object.

Boundaries: It does not automatically cross worker/process/network boundaries: transmit allowed metadata explicitly and re-establish context on the receiving side. Some custom callback integrations need AsyncResource or explicit binding. Long-lived background work can retain context; avoid putting entire request bodies or secrets in the store.

Alternatives & limits: Explicit parameters are clearer for business dependencies. Do not hide authorization or transaction ownership inside an unreviewed ambient store; enforce authorization at the service boundary. AsyncLocalStorage carries metadata; it does not create a database transaction or propagate cancellation.

Interview review: identify the constrained resource

For a slow Node endpoint, distinguish event-loop blocking, libuv pool saturation, worker queueing, database-pool contention, and remote I/O. Choose a bounded intervention and measure queue time, memory, latency, and failure behavior. Explain who cancels work, who closes resources, and what happens during shutdown.
