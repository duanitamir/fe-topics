Promises, async/await & error propagation

A Promise represents an eventual fulfillment or rejection. Its executor runs synchronously; registered reactions run as microtasks after the current stack completes. async functions always return a promise, and await suspends that function’s continuation, not the JavaScript thread.

JavaScriptConcurrency
async function readJson(url, signal) {
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}
try {
  const profile = await readJson('/api/me');
  console.log(profile);
} catch (error) {
  console.error('Profile unavailable', error);
}

Mechanism: Returning a promise from a then callback adopts its eventual result; throwing rejects the next promise. A catch handler that returns normally converts rejection into fulfillment. Return or await work whose failure the caller must observe; “fire and forget” needs an explicit rejection handler.

Pitfalls: Fetch usually fulfills for HTTP 4xx/5xx, so inspect status. try/catch catches an awaited rejection, not an unrelated promise you start without awaiting. Avoid async promise executors: their returned promise is ignored by the Promise constructor. See task and microtask scheduling.

Choose a Promise combinator by failure semantics

Combinators coordinate promises; they do not create threads, impose concurrency limits, or cancel underlying operations. Constructing an array with async calls usually starts all those operations before the combinator observes them.

JavaScriptConcurrencyResilience
APIResultGood fit / pitfall
Promise.allAll values in input order; rejects when an input rejects.Independent required reads. Other requests continue after rejection.
Promise.allSettledAll outcomes after every input settles.Optional widgets or batch reporting; inspect each outcome.
Promise.raceFirst settlement, success or failure.Competing outcomes; a timeout race does not cancel the request.
Promise.anyFirst fulfillment; AggregateError if all reject.Equivalent redundant sources where any success suffices. Losers continue.

Example: Fetch profile and permissions with Promise.all if the page needs both. Use allSettled for independent dashboard widgets that can fail separately. Do not issue duplicate payments with Promise.any to “make them faster.” Empty inputs also differ: all/allSettled fulfill, any rejects, race stays pending.

Alternative: Use sequential awaits when operation B depends on A, or when a deliberate ordering/rate constraint requires it. For many independent operations, use bounded concurrency rather than an unbounded Promise.all.

Sequential, parallel & bounded concurrency

Concurrency means operations are in progress during overlapping periods. Parallelism means execution happens simultaneously. Network concurrency does not imply parallel JavaScript execution; CPU-heavy work may need a worker.

JavaScriptConcurrencyPerformance
// Independent requests overlap; returned values retain input order.
const [profile, settings] = await Promise.all([
  readJson('/api/profile'), readJson('/api/settings')
]);

// Simple bounded batches, assuming readJson above and an array of URLs.
const results = [];
for (let index = 0; index < urls.length; index += 4) {
  results.push(...await Promise.all(urls.slice(index, index + 4).map(url => readJson(url))));
}

Use: Bound concurrency for bulk imports, uploads, or upstream API calls to avoid exhausting memory or connection capacity. Batches are simple but wait for the slowest member before starting the next batch; a worker pool or maintained limiter keeps capacity utilized.

Choose failure behavior: The example stops starting further batches after failure, but already-started requests continue. Decide whether to collect failures or cancel siblings where supported. forEach(async ...) does not await callbacks; use for/of, map with a combinator, or a limiter.

Comparison: Concurrency limits bound simultaneous work; rate limits bound frequency. Bulkheads isolate capacity between workloads.

Cancellation, deadlines & stale results

Cancellation is an operation’s agreement to stop unnecessary work, not a property of every promise. Use AbortController/AbortSignal for supporting APIs and a request/version guard before committing a result that may now be obsolete.

ConcurrencyResilienceResource lifecycle

Example: Query A starts, then B starts; B finishes first. Cancel A if possible and ensure only the current request updates the display. In a mutation, cancellation cannot prove the server did not commit the write.

Use deadlines: Bound total user-visible time, including retries and queueing. Promise.race can stop waiting but leaves the losing work running; a timeout signal can request cancellation. Clear manually created timers in cleanup.

When not to retry: Validation errors, authorization failures, and unsafe duplicate effects need resolution, not blind repetition. Use bounded backoff/jitter and idempotency policies where appropriate. See failure containment.

Async iteration & backpressure

An async iterable supplies values through promises; for await...of consumes them one at a time. It fits paginated sources and streams that produce values over time. Pull-based consumption can provide backpressure when the producer respects demand; an unbounded push buffer does not become safe merely because it exposes an async iterator.

JavaScriptConcurrencyResource lifecycle
async function* pages(loadPage) {
  let cursor;
  do {
    const page = await loadPage(cursor);
    yield page.items;
    cursor = page.nextCursor;
  } while (cursor != null);
}
for await (const items of pages(loadPage)) {
  await saveBatch(items); // Illustrative application functions.
}

Use: Incremental processing without loading everything into memory. Handle stream errors, cancellation, and resource release; breaking a for-await loop invokes the iterator’s return method when available. A stream reader may still need explicit cancellation/release through its own API.

Alternatives: A normal array and loop are simpler for already-loaded data. Use streams for continuous or large transfers; use a bounded task pool when processing items concurrently is safe. Respect pagination contracts rather than assuming every API uses the same cursor rules.

Interview review: define ownership and outcome

For each asynchronous workflow, explain its dependencies, concurrency bound, failure policy, cancellation owner, stale-result guard, and cleanup. Distinguish a task that failed from a response that never reached the client. Connect those decisions to command handlers and outcome events.
