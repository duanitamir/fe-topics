From URL to response: the request lifecycle

A network navigation can involve cache lookup, DNS resolution, a connection, TLS negotiation, an HTTP request/response, and browser parsing/rendering. Existing connections, service workers, caches, redirects, and speculative work can change which steps occur.

HTTPPerformance

Example: A slow product page may have fast server execution but a long DNS/TLS setup, redirect chain, or JavaScript request waterfall. Inspect the Network panel’s timing and initiator chain instead of labeling all waiting time “backend latency.”

Protocol choices: HTTP/1.1 commonly uses multiple connections; HTTP/2 multiplexes streams on a TCP connection but can still suffer connection-level TCP head-of-line blocking; HTTP/3 uses QUIC with independent streams and TLS integration. These change transport behavior, not resource authorization or application semantics.

Use: Diagnose connection reuse, cache behavior, payload transfer, and dependent requests before optimizing. DNS/CDN routing and geographic distance affect latency; moving a service does not fix an avoidable client waterfall. See performance measurement.

Methods, status codes & idempotency

Safe methods have read-only intended semantics; idempotent methods have the same intended server effect when repeated as when applied once. This does not require identical responses and does not mean every implementation obeys the contract.

HTTPAPI integration
MethodIntended useImportant distinction
GET / HEADRead representation / response metadata.Safe and idempotent; do not use them for state-changing commands.
POSTSubmit work or create a subordinate resource.Not inherently idempotent; a server-supported idempotency key can deduplicate one operation.
PUTCreate/replace the state of a target resource.Idempotent semantics; send the representation required by the contract.
PATCHApply partial modifications.Not inherently idempotent; depends on patch semantics.
DELETERemove the target resource association.Idempotent intended effect; a second call may return a different status.

Status contract: 200 for successful content, 201 for creation, 202 for accepted but unfinished work, 204 for no response body. 400 covers invalid requests; 401 unauthenticated, 403 forbidden, 404 unavailable resource, 409 application conflict, 412 failed precondition, 422 semantically invalid content where adopted, 429 rate-limited, and 5xx server/gateway failure. Follow a documented API contract rather than assuming all clients treat codes identically.

Use: Correct semantics support caching, retry decisions, and client recovery. Never retry a mutation just because a connection failed without considering its idempotency contract. Use structured error bodies for actionable details.

HTTP caching: freshness, validation & cache keys

An HTTP cache stores a response under a cache key and policy. A fresh response can be reused without contacting the origin; a stale response may need revalidation. Browser private caches and shared CDN/proxy caches have different privacy boundaries.

HTTPPerformanceSecurity
Cache-Control: public, max-age=60, s-maxage=300
ETag: "product-v7"
Vary: Accept-Encoding

Interpretation: This deliberately public response can be fresh for 60 seconds in a private cache and 300 in shared caches. Vary makes relevant request-header values part of cache selection. Use public policies only for data safe to share across users; URL-only CDN keys can leak personalized content if policy and authorization are wrong.

Directives: no-store asks caches not to store; no-cache permits storage but requires validation before reuse; private disallows shared-cache storage. immutable suits fingerprinted assets with long freshness. stale-while-revalidate permits bounded stale reuse while revalidating where supported.

Conditional reads: Send If-None-Match with the ETag; a 304 response reuses the cached body with updated metadata. Last-Modified/If-Modified-Since provide another validator. Conditional writes use If-Match and optimistic concurrency control, which solve a different problem.

Choose the layer: HTTP caches reuse responses; a query cache coordinates application data and mutations. One does not automatically invalidate the other. Version static asset URLs, set explicit personalized-response policies, and define invalidation for mutable public resources. See the optimization overview.

Payloads, compression & request waterfalls

Total request time includes waiting, transfer, decompression, parsing, and downstream rendering. Smaller wire payloads can still require expensive JavaScript parsing or application work.

HTTPPerformance

Use: Inspect transfer size versus decoded size; use negotiated compression for suitable text, appropriately sized images, pagination, and conditional requests. A CDN can cache suitable public assets near users, but does not make an uncacheable personalized request disappear.

Waterfall example: Fetch user → then settings → then permissions when settings/permissions only need the user ID creates dependencies. If an authenticated API can provide independent requests or an appropriate aggregate response, start them together. Do not parallelize work that truly depends on earlier results.

Tradeoffs: Aggregation reduces round trips but can couple latency and failures; splitting lets optional UI load independently. Preload/prefetch can help known critical resources but waste bandwidth when overused. Connection reuse and HTTP multiplexing do not eliminate application dependencies. See bounded concurrency and BFF composition.

Browser origin, credentials & storage boundaries

The browser enforces rules that a server-side HTTP client does not share. An origin is scheme, host, and port; a cookie’s scope and SameSite rules use additional concepts and are not identical to same-origin checks.

HTTPSecurityBrowser

Example: A fetch can fail browser CORS checks even when a server-side request to the same API succeeds. Cross-origin fetch credentials require the appropriate client option and server policy, while browser cookie restrictions can still block their use.

Choose deliberately: Keep the canonical explanations in CORS and TLS, CSRF, and credential storage. CORS governs browser access to responses; it is not authentication or an authorization boundary. Never “fix” credentialed CORS with wildcard origins.

Interview review: follow the response contract

Describe the request path, method semantics, cacheability, validators, credential boundary, and failure response. Diagnose a slow request with timings before choosing a CDN, batching, GraphQL, or a BFF. Those mechanisms address different sources of cost.
