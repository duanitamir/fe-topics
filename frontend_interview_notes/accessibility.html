Semantic HTML & the accessibility tree

Browsers expose an accessibility tree derived from DOM semantics, state, and rendering. Assistive technologies use it to understand roles, names, values, and relationships. It is related to the DOM but is not a one-to-one copy.

AccessibilityBrowser

Example: A native button exposes role and state plus built-in keyboard behavior. A div with role=button changes exposed semantics but still needs focusability and keyboard activation. ARIA describes semantics; it does not implement missing behavior.

Use: Start with native headings, landmarks, links, buttons, labels, and form controls. Inspect the accessibility tree when markup appears correct but a control is unnamed or misrepresented. Use ARIA to fill a real semantic gap, not to override valid native behavior.

Pitfalls: aria-hidden hides a subtree from assistive technology but does not itself prevent keyboard focus. Do not hide a focused control or ancestor. Decorative icons can be hidden; interactive content needs an operable and understandable contract. See component accessibility guarantees.

Accessible names, descriptions & states

An accessible name identifies a control; an accessible description supplies additional guidance. Browsers compute names from sources such as associated labels, aria-labelledby, aria-label, and element content according to the element’s naming rules.

AccessibilityForms
<label for="email">Email address</label>
<input id="email" name="email" type="email" aria-describedby="email-hint">
<p id="email-hint">Used for receipts.</p>
<button type="button" aria-label="Close dialog">×</button>

Use: Prefer visible labels that match the accessible name; use aria-labelledby to reference visible text. aria-label can override a name that would otherwise come from content, so adding it casually can create a mismatch. Placeholder text is not a replacement for a persistent label.

State: Expose expanded, selected, checked, disabled, and invalid states through native controls or the correct ARIA attributes. aria-disabled communicates state but does not block clicks or submissions; implement the behavior. Use useId for stable label/description relationships, not as a domain identifier.

Alternative: If native semantics already express the contract, avoid redundant ARIA. For validation, connect descriptive error text to the field and follow the form feedback model.

Keyboard navigation & focus ownership

Focus order should follow a meaningful reading and task sequence. Tab generally moves between controls; composite widgets can use arrow keys internally according to their interaction model. DOM order, visual layout, and focus behavior must work together.

AccessibilityBrowser

Example: Opening a modal moves focus appropriately, keeps interaction in the modal while it is active, and returns focus to the invoking control after close when that control still exists. Native dialog.showModal supplies important browser behavior; choose an initial focus target based on the task.

Use: Prefer natural document order and tabindex=0 for elements that truly require focus. tabindex=-1 allows programmatic focus without adding a normal tab stop. Avoid positive tabindex values that create a second, brittle ordering system.

Composite widgets: Roving tabindex moves DOM focus among items; aria-activedescendant keeps focus on a container/input while identifying the active item. They are different implementations and require correct roles, IDs, and keyboard behavior. Virtualization must keep the active descendant available.

Pitfalls: A focusable element is not necessarily understandable or operable. Prevent focus traps, preserve visible focus indicators, and handle unmounted targets during navigation. See compound widgets and default-action cancellation.

Dynamic updates, errors & live regions

A visual DOM update is not always announced to a screen-reader user. Live regions communicate important updates without moving focus. role=status provides polite status semantics; role=alert is assertive and should be reserved for appropriate urgent feedback.

AccessibilityForms

Example: Keep a status region mounted and update it with “3 results found” after a search completes. Announcing every keystroke or every streamed token overwhelms the user. A submission failure may need an error summary and intentional focus rather than only a live announcement.

Use: Announce meaningful outcomes, maintain focus for ordinary background refreshes, and avoid replacing the focused control unnecessarily. Mark a changing region busy where appropriate and clear the state when updates finish.

Alternatives and limits: Focus movement is appropriate when the task context changes, such as opening a dialog or navigating to an error summary. Live-region behavior varies by browser/assistive-technology combination; verify the actual task with a screen reader rather than assuming every announcement is guaranteed.

WCAG, zoom & practical verification

WCAG organizes accessibility requirements around perceivable, operable, understandable, and robust experiences. Conformance is broader than passing an automated scan; each criterion has applicability and exceptions.

Accessibility

Practical baseline: Check text contrast (generally 4.5:1 for ordinary text, 3:1 for large text), meaningful non-text contrast, visible focus, meaningful link names, alternative text, reflow, zoom, keyboard access, and errors that do not rely on color alone. Target WCAG 2.2 criteria as relevant, including target size and focus not being obscured.

Verify a task: Navigate only with the keyboard; inspect names/roles/states in the accessibility tree; test zoom and a narrow viewport; enable reduced motion; use a screen reader to submit and recover from an invalid form. Automated tools help find missing labels and some contrast issues but cannot judge a logical workflow or good alternative text.

Tradeoffs: Custom controls and highly dynamic layouts increase the behavior you must implement. Prefer established accessible primitives when they fit. Accessibility is part of the component contract, not a final visual polish pass.

Interview review: demonstrate a usable task

Explain semantics, naming, keyboard interaction, focus ownership, status/error feedback, and verification together. Show how an autocomplete or dialog works for keyboard and screen-reader users, including asynchronous results and recovery. Correct role names alone are not a complete implementation.
