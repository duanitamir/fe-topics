Build Tooling & Modules

Understand what the toolchain transforms, what ships to the browser, and how releases remain compatible.

ES modules, CommonJS & module resolution

ES modules (ESM) use import/export with a statically analyzable structure and live bindings. CommonJS (CJS) uses require/module.exports with different loading and interop semantics. Resolution determines which file/package entry a specifier refers to; it depends on runtime, package exports, extensions, and tool configuration.

ToolingJavaScript
// counter.js — ESM
export let count = 0;
export function increment() { count += 1; }

// consumer.js — imported count is a live binding, not a copied snapshot.
import { count, increment } from './counter.js';
increment();
console.log(count); // 1

Use: Understand which environment executes a module and how its entry points are selected. Browser native ESM, Node, TypeScript, and bundlers can resolve differently. TypeScript path aliases do not automatically configure the runtime resolver.

Pitfalls: Cyclic dependencies can expose uninitialized bindings or order-sensitive setup. CJS/ESM default/named import interop varies by environment. Fix the dependency graph and package exports rather than relying on accidental transpiler behavior. Code splitting with dynamic import returns a promise; loading can fail.

Bundling, transpilation & polyfills

A bundler analyzes dependencies and emits deployable assets/chunks. Transpilation rewrites source syntax for a target. Type checking verifies types. A polyfill supplies a missing runtime API. These jobs are separate even when one toolchain combines them.

ToolingJavaScript

Example: A tool may strip TypeScript and transform optional chaining while never running a full type check. Transforming syntax does not provide fetch, Promise.any, or another missing runtime API. Set explicit browser/runtime targets and run a separate type-check step if needed.

Use: Define supported environments and feature detection before adding polyfills. Prefer native APIs when supported; use targeted compatibility tooling when the support contract requires it. Avoid large indiscriminate polyfill bundles and do not assume a successful build means type-safe or runtime-compatible code.

Tradeoffs: Bundling can reduce request and packaging overhead; native ESM can simplify suitable deployments. Development behavior can differ from optimized production output, so verify a production build, not only the dev server.

Tree shaking, side effects & dependency duplication

Tree shaking removes statically provable unused exports/code in an optimized build. It depends on analyzable modules and correct side-effect information; importing a library does not guarantee only the used function is shipped.

ToolingPerformance

Example: A module that registers a locale, patches a global, or imports CSS performs observable work at import time. Incorrectly declaring all files side-effect-free can remove necessary behavior. Package sideEffects metadata and bundler behavior need deliberate configuration.

Use: Inspect a bundle analyzer for duplicate dependencies, large transitive imports, and unexpected chunks. Duplicate React instances can break hook assumptions; align peer dependencies and resolution rather than only deduplicating at random.

Alternatives and limits: Tree shaking is different from minification and from lazy loading. Use selective imports where needed, route/feature splitting for deferred code, and remove unused dependencies. Avoid manual micro-optimizations until the emitted bundle identifies a real cost.

Asset versioning, source maps & configuration

A production artifact should have explicit runtime configuration and cache behavior. Content-hashed asset names allow long-lived immutable caching while the HTML entry point selects the current build.

ToolingResilienceSecurity

Deployment example: Keep older chunks available during rollout so an already-open tab can load its referenced version. Deleting all old assets immediately can cause chunk-load failures. Provide a deliberate recovery flow that does not discard unsaved work.

Configuration: Build-time environment values are embedded into client assets; treat them as public. Runtime public configuration can vary without rebuilding if the application is designed for it. Server secrets must remain server-side; an environment-variable name or prefix is not a security boundary by itself.

Source maps: Map minified stack traces back to authored code. Associate maps with the exact release; decide whether to publish them or upload privately to reporting tooling, since they may reveal source details. Maps improve diagnosis, not security isolation.

Tradeoffs: Aggressive asset caching needs versioned URLs and rollout compatibility. A service worker adds another cache/update lifecycle; it is not automatically a deployment fix. Connect decisions to HTTP caching and incremental rollout.

Interview review: inspect the emitted application

Explain module boundaries, package resolution, compile targets, polyfills, chunking, cache policy, and release identification. Distinguish “the compiler accepted it,” “the bundle built,” and “the supported runtime can execute it.” Each is a different guarantee.
