Frontend Performance Optimization

Start with a measured symptom. Understand the browser pipeline, isolate React-specific work, then choose a targeted technique and verify its impact.

Start with a user-visible problem, measure its cause, then verify the improvement. A smaller bundle or fewer React renders matters when it improves loading, responsiveness, stability, or resource use. Optimize the critical path rather than an isolated number.

Measuring performance

Choose the right measurement tool

Performance
  • React DevTools Profiler: Record an interaction to find expensive component renders and commits. Use its flamegraph, ranked view, and render-reason information where available. React render work is not the same as browser layout or paint; use a browser trace for those costs.
  • Chrome DevTools Performance panel: Record a reproducible user journey. Inspect the main-thread flame chart, interaction timings, JavaScript call stacks, style recalculation, layout, paint, and dropped frames. Bottom-up groups accumulated cost by function; Call tree shows how execution reached it.
  • Chrome DevTools Network & Coverage: Find request waterfalls, large transfers, cache behavior, and unused JavaScript or CSS in the recorded journey. Unused code on one screen may still be required elsewhere.
  • Lighthouse: A repeatable synthetic (lab) audit for loading and diagnostics under configured conditions. Its score is a signal, not a complete account of real-user experience. Total Blocking Time (TBT) is a lab responsiveness metric; it is not INP.
  • Real User Monitoring (RUM): Measure production users across devices, networks, and routes. Compare field data with lab traces to understand who is affected and reproduce their bottleneck. Chrome UX Report (CrUX) offers aggregated field data for eligible pages and origins.

Measure JavaScript execution and rendering bottlenecks

Performance
  • Self time vs. total time: Self time belongs to the function itself; total time includes functions it calls. Inspect both to avoid blaming a cheap wrapper for expensive descendants.
  • Long tasks: Main-thread tasks longer than 50 ms can delay input and rendering. Split work into smaller tasks and yield to the browser; move suitable CPU-intensive computations to a Web Worker, which cannot access the DOM directly.
  • User Timing API: Use performance.mark() and performance.measure() to label application work in a trace. Elapsed time across an await includes waiting; it is not necessarily JavaScript CPU time.
  • Frame budget: A 60 Hz display refreshes about every 16.7 ms; at 120 Hz, about every 8.3 ms. JavaScript shares that time with rendering and browser overhead, so it cannot consume the full interval.
performance.mark('filter-start');
const results = expensiveFilter(products, query);
performance.mark('filter-end');
performance.measure('product-filter', 'filter-start', 'filter-end');

Browser rendering pipeline

This is a conceptual model: browsers perform work incrementally, and an update may skip stages when earlier results remain valid.

BrowserRenderingPerformance
  • DOM (Document Object Model): The parsed document tree. JavaScript can add, remove, or update its nodes.
  • CSSOM (CSS Object Model) & style calculation: The browser parses CSS rules and resolves the cascade, inheritance, and selectors into computed styles for elements. CSS can block initial rendering; synchronous scripts can block HTML parsing.
  • Render tree: Combines renderable content with its styles. It differs from the DOM; for example, display: none elements produce no layout boxes.
  • Layout (reflow): Calculates box sizes and positions. Changing geometry, such as width or font size, can invalidate layout for the element and related content.
  • Paint: Produces drawing instructions for backgrounds, text, borders, and other visual content. Repaint means regenerating affected visual output; changing a color typically needs paint without layout.
  • Rasterization: Converts drawing instructions into pixels, commonly in tiles.
  • Compositing: Combines rasterized layers into the final frame. Animating transform or opacity on a suitable composited layer can avoid layout and paint. Layer promotion is browser-dependent; excessive layers consume memory.
Reflow vs. repaint: Reflow changes geometry; repaint changes appearance. A layout change usually leads to paint for affected content, but a paint-only change need not recalculate layout. Neither is the same as a React re-render.

Layout thrashing: alternating DOM writes and geometry reads

BrowserRenderingPerformance

Forced synchronous layout occurs when JavaScript reads geometry after a change has invalidated layout, forcing the browser to calculate it immediately. Repeating this write/read cycle is layout thrashing.

// Avoid: each width update can invalidate the next geometry read.
for (const row of rows) {
  row.style.width = container.offsetWidth + 'px';
}

// Prefer: batch the read before the writes.
const width = container.offsetWidth;
for (const row of rows) {
  row.style.width = width + 'px';
}

Recognize geometry reads: offsetWidth, offsetHeight, and getBoundingClientRect() may require up-to-date layout. A read is not automatically expensive; pending invalidation determines whether it forces work.

  • Batch DOM reads before writes when the algorithm permits. Prefer CSS layout rules when they can express the relationship directly.
  • Use requestAnimationFrame() to schedule visual updates before a repaint. It does not prevent forced layout if the callback still alternates writes and reads.
  • Reduce affected work: Large DOM trees and broad style invalidation increase cost. Consider virtualization, CSS containment, or content-visibility for suitable offscreen sections; verify layout, accessibility, and find-in-page behavior.

DOM operations are not equally expensive: The cost depends on which styles and layout boxes become invalid. Many writes can be batched by the browser; one badly timed geometry read can force that pending work onto the critical path.

Diagnosing unnecessary React renders

A component can render because its state changes, an ancestor renders, or a consumed context changes. A render does not imply a DOM mutation or repaint. First identify which renders are expensive and whether they affect the interaction.

ReactPerformance
  1. Record the interaction in React Profiler and find the expensive commits and components.
  2. Inspect the trigger: Look for state placed too high in the tree, broad context updates, unstable object/function props, or effects that repeatedly update state.
  3. Reduce the scope of updates: Colocate state with its consumers, split unrelated context values, and avoid storing derived values in state when they can be calculated during rendering.
  4. Apply memoization selectively: Use the techniques below when unchanged inputs can skip meaningful work; profile again to confirm the benefit.

Measurement caveat: Development-mode StrictMode can invoke rendering and effect setup/cleanup extra times to expose bugs. Validate user-facing performance in a representative production build; React profiling itself may require a profiling-enabled build and adds overhead.

Optimization techniques: purpose and tradeoffs

Control frequency and repeated computation

Performance
  • Debouncing: Run after a quiet interval, resetting the timer on each input. Example: fetch search suggestions 250 ms after typing stops. It reduces calls but adds latency; cancel pending timers on cleanup.
  • Throttling: Limit execution frequency during continuous activity. Example: update scroll analytics at most once every 200 ms. Choose leading-edge and/or trailing-edge behavior deliberately so the final update is handled.
  • Memoization: Reuse a result when its inputs are unchanged. useMemo caches a calculation, useCallback caches a function identity, and React.memo can skip a component render when props compare equal. Default comparisons use Object.is for dependencies or individual props. State/context updates still render memoized components. See hook cache guarantees and React Compiler. Memoization costs memory and comparison work; unstable dependencies or cheap calculations may erase its value.

Reduce initial loading and rendering work

Performance
  • Code splitting: Divide JavaScript into independently loadable chunks, often by route or feature, using dynamic import(). This reduces initial download, parsing, and execution work when chunks are deferred. Excessive splitting can create request waterfalls.
  • Lazy loading: Defer a resource until it is needed. Use React.lazy with Suspense for supported component loading, or loading="lazy" for offscreen images. Reserve image dimensions to avoid CLS; do not lazy-load the likely LCP image. For visibility-triggered custom loading, see Intersection Observer. Code splitting creates chunks; lazy loading decides when to request them. See Streaming SSR and Suspense for progressive server delivery.
  • Virtualization (windowing): Mount only visible list items plus a small overscan region. This reduces DOM size, React work, and layout cost. Account for variable row heights, keyboard focus, screen-reader navigation, and browser search. Resize Observer can measure variable row heights.
  • Pagination: Limit the data fetched per page. Cursor-based pagination is often useful for large or changing datasets; offset-based pagination is simpler for page-number navigation. Pagination reduces data volume; virtualization reduces mounted UI. They can be combined.

Reduce network work and prevent stale results

PerformanceAPI integrationConcurrency
  • Caching: Reuse responses or computed data. HTTP caching uses Cache-Control; validators such as ETag support conditional requests and revalidation. Application query caches reuse server state across components; see query keys, freshness, and mutation invalidation. Define freshness, invalidation, and user-specific cache keys; personalized responses must not leak through shared caches.
  • Request cancellation: Stop obsolete asynchronous work to reduce wasted processing and prevent stale results. See AbortController & AbortSignal for the mechanism, React cleanup example, and correctness limits.
  • Request deduplication: Share one in-flight request among consumers of the same query key. Caching reuses completed results; deduplication shares pending work. Include all result-affecting parameters and the relevant user/tenant scope in the key.

Example: a slow product search. Debounce typing to reduce requests, cancel or ignore obsolete searches to prevent stale results, deduplicate identical in-flight queries, and cache reusable results. If the result list itself is expensive, paginate the data and virtualize the rows. Use the trace to decide which of these is actually needed.

For the protocol details behind cache and bundle optimizations, see HTTP freshness and validators and tree shaking and module side effects.

Interview-ready investigation

  1. Define the symptom and target: Is loading slow, typing delayed, scrolling janky, or content shifting? Choose the relevant metric and affected user segment.
  2. Capture a baseline: Reproduce the same journey with representative data, device constraints, and explicitly cold or warm caches. Use field data to check how widespread it is.
  3. Identify the dominant bottleneck: Network, JavaScript, React rendering, layout, paint, or a combination. Follow the critical path and call stacks rather than guessing.
  4. Make a targeted change and remeasure: Compare repeated runs under equivalent conditions, then check production percentiles. Watch for regressions in memory, accessibility, data freshness, and other metrics.
  5. Prevent recurrence: Establish performance budgets for important journeys and asset sizes, and monitor regressions in CI and production.
I begin with the user-visible symptom and a representative baseline. I combine field metrics with Chrome performance traces, using React Profiler when component rendering is implicated. I separate JavaScript execution, React render work, and browser layout and paint, then address the largest cost on the critical path. I validate the result under the same conditions and monitor production percentiles, rather than assuming fewer renders or a higher audit score means a better experience.
