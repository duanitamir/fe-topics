Component Composition

Start with composition and state ownership, then define customization, accessibility guarantees, and form validation and submission contracts.

Composition builds larger interfaces by combining small components with explicit responsibilities. Prefer a clear contract for behavior, state ownership, and customization over a component with dozens of interacting boolean props.

Composition patterns & children

  • Containment with props.children: A wrapper accepts nested React nodes without knowing their concrete component types. A Card can provide structure while callers supply content.
  • Named slots: Props such as header and footer accept React nodes for specific insertion points. Use them when placement has meaning beyond a single children region.
  • Render props: A function prop, such as renderItem(item), lets the caller render content using state or data supplied by the component. A function-valued children prop is also a render-prop pattern when the component explicitly invokes it.
function Card({ title, children, footer }) {
  return (
    <section>
      <h2>{title}</h2>
      <div>{children}</div>
      <footer>{footer}</footer>
    </section>
  );
}

<Card title="Products" footer={<Pagination />}>
  <ProductList />
</Card>

Contract: Ordinary children are React nodes, not callbacks. Do not assume every child is an element you can clone; it may be text, a fragment, or null. Prefer explicit props or context over inspecting and rewriting arbitrary children.

Design patternReact

Controlled vs. uncontrolled components

  • Controlled: The parent owns the input’s value contract (separate from server/client data ownership) and supplies the source of truth through value and a change callback. Use it for coordinated inputs, validation, or externally driven updates. The callback requests a change; the parent must supply the updated value.
  • Uncontrolled: The component or native DOM input owns current state. defaultValue supplies an initial value; changing it later is not a controlled update. When editing fetched data, use an explicit server snapshot and draft policy. Read native input values through form submission or refs when needed; see handling submit events with FormData.
  • Hybrid API: A reusable component may support either mode, but each state variable must have one owner. For native text inputs, keep controlled values as strings, often value={value ?? ''}, and avoid switching between controlled and uncontrolled modes during the component’s lifetime.
// Controlled: React state is the source of truth.
<input value={query} onChange={event => setQuery(event.target.value)} />

// Uncontrolled: the DOM owns the current value.
<input name="query" defaultValue="React" />

Compound components & slots

Compound components expose cooperating parts under one API. For example, Autocomplete.Root, Autocomplete.Input, and Autocomplete.Results share a state and behavior contract, often through context, while callers control their arrangement.

Design patternReact
// Illustrative API: these named parts are supplied by a component library.
<Autocomplete.Root value={selected} onValueChange={setSelected}>
  <label htmlFor="product-search">Product</label>
  <Autocomplete.Input id="product-search" />
  <Autocomplete.Results>
    {products.map(product => (
      <Autocomplete.Item key={product.id} value={product.id}>
        {product.name}
      </Autocomplete.Item>
    ))}
  </Autocomplete.Results>
</Autocomplete.Root>
  • Compound parts vs. slots: Autocomplete.Input is a named component in a compound API; its behavior comes from its implementation and shared contract. A slot is an insertion or replacement point. They can work together, but dot notation alone does not create slot behavior or shared state.
  • Shared behavior: The root coordinates selection, open state, active option, and IDs. Parts consume only what they need. Keep ownership explicit if input query and selected value are separate state variables.
  • Accessibility contract: A real autocomplete must implement combobox/listbox semantics, accessible names, keyboard navigation, focus management, and relationships such as aria-controls and aria-activedescendant. Flexible composition must preserve those guarantees; see the accessible component contract.

Headless components, hooks & customization

Headless APIs separate behavior from visual presentation. A headless component may render unstyled semantic elements; a custom hook can expose state, actions, and prop getters while the caller renders the DOM. See custom hook API design for lifecycle, return-value, and testing contracts. A hook does not automatically share state between callers; shared state needs a provider or store.

Design patternReact
  • Props: Configure supported behavior and appearance, such as disabled, size, or a formatter. Prefer explicit options for common variations.
  • Slots & render props: Replace a region or its rendering when callers need structural flexibility. Forward required refs and accessibility attributes, and compose internal and user event handlers deliberately.
  • Adapters: Translate an external contract into the component’s contract. For example, a form-library adapter maps field value, change, blur, error, and ref behavior to the input API. Keep vendor-specific details out of the reusable core. See Adapter vs. Strategy and Facade for integration boundaries.

Tradeoff: More customization creates more combinations to support. Define which party owns markup, focus, state, and accessibility; an unrestricted escape hatch can break invariants that ordinary props preserve.

Accessible component contracts

An accessible component API guarantees semantics, keyboard behavior, focus ownership, and state announcements across its supported customizations. See accessibility foundations for the tree, names, and keyboard model. Accessibility belongs to the behavior contract, including in headless APIs.

ReactAccessibility
  • Prefer native semantics: A native button provides keyboard activation and disabled behavior. Adding role="button" to a div does not implement these. Give non-submit buttons inside forms type="button".
  • Define the accessible name: Associate labels with inputs; expose labels for icon-only controls. Forward stable IDs, aria-describedby, and state attributes to the actual interactive element. Use useId for relationships, not list keys.
  • Own focus deliberately: A modal dialog needs an accessible title, appropriate initial focus, constrained focus navigation, inert background behavior, and focus restoration on close. Native dialog.showModal() supplies important platform behavior; custom dialogs must implement it.
  • Specify keyboard interaction: Compound widgets need a documented model, such as arrow navigation and an active descendant for a combobox. aria-activedescendant references a real option ID while DOM focus stays on the input; keep that option mounted when virtualizing.
  • Preserve the contract through slots: Forward refs and merge required IDs, ARIA attributes, and handlers. A replacement must preserve the expected element semantics. Define whether a user handler’s preventDefault() vetoes internal behavior; see default-action cancellation.

Validate: Test keyboard-only use, focus restoration, accessible names/states, zoom, and a screen reader. Automated accessibility checks catch only part of the contract. Reuse established accessible primitives for complex widgets when their API fits.

Progressive enhancement: start with a working platform contract

Purpose: Build a useful baseline with browser capabilities, then enhance it where JavaScript is available. The baseline must actually work: semantic markup alone does not make a client-only workflow functional without JavaScript.

Design patternBrowserResilience

Example: A server-handled search form navigates to a results page; client code can later enhance it with debouncing and in-place results. A real anchor preserves copy-link, open-in-new-tab, keyboard, and navigation behavior.

<form action="/search" method="get">
  <label htmlFor="catalog-query">Search products</label>
  <input id="catalog-query" name="q" type="search" />
  <button type="submit">Search</button>
</form>

Use when: Content, navigation, and form submission should remain useful during slow JavaScript loading, partial failure, or constrained devices. Native server endpoints must validate/authorize input; state-changing forms still need CSRF protection.

Benefits and tradeoffs: Preserves platform affordances and a resilient baseline, but enhanced and baseline paths must share rules and be verified. Do not intercept navigation or submission until the enhancement can fulfill its contract.

When not to force a full fallback: Rich canvas editors and complex live collaboration may inherently require JavaScript. Keep accessible surrounding navigation, explain loading/failure, and recover drafts rather than maintaining an unusable duplicate implementation.

Compare: SSR improves initial HTML delivery but does not automatically make interactions work without JavaScript; see hydration. Graceful degradation starts from a richer experience and defines fallback; progressive enhancement starts with the baseline. Framework form Actions have framework-specific enhancement guarantees; choose them deliberately alongside the form submission contract.

Complex forms: fields, validation & asynchronous submission

Compose a form from a form owner, field adapters, and domain sections. The owner coordinates submission and cross-field rules; each field exposes name, value/change or default value, blur/touched state, error, and a focusable ref. Use native fieldset/legend for related controls.

ReactFormsAccessibility
  1. Choose ownership: Simple forms can use native inputs and FormData. Use controlled fields for coordinated interactions; a form library helps with dirty/touched tracking, field arrays, and subscriptions. Preserve unsaved drafts when remote data changes.
  2. Validate at the right boundary: Native constraints handle basic required/type/range checks. Schema validation can handle cross-field/domain structure. Client validation improves feedback; the server must independently validate input and authorize the operation. Validation is separate from output encoding and HTML sanitisation.
  3. Keep validation responsive: Show errors after blur or an attempted submit as appropriate. Debounce asynchronous checks such as username availability, cancel obsolete checks, and guard stale responses. Availability checks are advisory; the server must still enforce uniqueness when saving.
  4. Model submission: Distinguish idle, validating, submitting, success, validation failure, conflict, and network failure. Prevent unintended repeat submissions; retain input on failure and map server field errors back to their fields. See useActionState and useFormStatus for React Action-based forms.
// A reusable field contract; the form owner supplies validation state.
function EmailField({ id, value, onChange, error }) {
  const errorId = id + '-error';
  return (
    <div>
      <label htmlFor={id}>Email</label>
      <input id={id} name="email" type="email" required
        value={value} onChange={onChange}
        aria-invalid={error ? true : undefined}
        aria-describedby={error ? errorId : undefined} />
      {error && <p id={errorId}>{error}</p>}
    </div>
  );
}

Accessible feedback: On failed submission, render an error summary with links to invalid fields and move focus to the summary or first invalid field. Associate inline errors through aria-describedby; announce submission status through a restrained live region. Do not announce every keystroke or rely on color alone.

Complexity and tradeoffs: Use stable domain IDs for dynamic field arrays so reordering preserves field identity. Define validation and draft retention across multi-step forms. A disabled submit button only prevents local repeats; retries and ambiguous network outcomes still need a server-supported idempotency and conflict policy. Aborting the request does not undo a save.

Interview review

Interview takeaway: Start with state ownership and accessibility, then choose props, children, compound parts, or a headless hook according to the flexibility callers actually need. See Context + useReducer for coordinating compound parts.
