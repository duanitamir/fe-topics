React Rendering: Updates, Strategies & Hydration

Start with how React computes and commits updates, preserves identity, and schedules work. Then follow initial HTML delivery, hydration, Server Components, and streaming.

Core idea: SSR determines how initial HTML is produced; RSC determines which component code stays on the server; hydration connects browser-side React to server-rendered HTML.

Two different decisions:

RSC and SSR are not alternatives. A framework such as Next.js can use both on the same page.

React updates: render, reconciliation & commit

Trigger → render → commit: An initial root render or a state update schedules work. During render, React calls components to calculate the next UI and performs reconciliation: matching new elements against the previous tree to determine what can be preserved and which changes are needed. Rendering a component does not necessarily change the DOM.

ReactRenderingConcurrency
  • Render phase: Must remain pure. Do not mutate external data, send requests, or subscribe while rendering. React may restart or discard this work, so a render is not proof that the UI appeared.
  • Commit phase: React applies the selected tree’s DOM changes and attaches refs. Layout effects run before the browser repaints; passive effects synchronize external systems after commit, with timing dependent on the interaction. See effect timing and cleanup.
  • Diagnosis: Distinguish component execution, DOM mutations, and browser layout/paint. They are separate costs; use the React Profiler and browser performance trace together.

Component identity & keys: preserve or reset state deliberately

ReactState management

State belongs to a component’s position in React’s tree, identified by element type and, where supplied, its key within the parent. Matching identity preserves state; removing a component or changing its type/key resets its subtree, including effects and uncontrolled input values.

// Stable domain IDs preserve each row's state when sorting or inserting.
products.map(product => <ProductRow key={product.id} product={product} />);

// A different account should receive a fresh local editing draft.
<ProfileEditor key={account.id} initialProfile={account} />;
  • Use stable sibling-unique IDs: Keys need not be globally unique and are not passed as ordinary props. Pass a separate id prop when the child needs it.
  • Avoid index keys for changing lists: Insertion, deletion, or sorting can attach state to the wrong record. Random keys remount everything on every render. Keys do not prevent rerenders and cannot preserve state across arbitrary parent changes.
  • Intentional reset: Key an editor by record identity when switching records should reset it. Do not key by each server version unless losing unsaved edits is intended; see server snapshots and local drafts.

Automatic batching & state update queues

ReactConcurrency

With modern createRoot roots, React automatically batches updates from handlers and asynchronous callbacks such as promises and timers, reducing separate renders. Each render still observes a fixed state snapshot; a setter queues an update rather than changing the current variable.

// Starting at 0, these request the same next value: the result is 1.
setCount(count + 1);
setCount(count + 1);

// Functional updaters compose: starting at 0, the result is 2.
setCount(c => c + 1);
setCount(c => c + 1);

Batching does not combine distinct intentional user events into one transaction, and it is not a server transaction guarantee. Updaters must be pure. Use flushSync from react-dom sparingly for integrations that require the DOM to update before the next statement; it can hurt performance. For previous-state calculations, prefer functional state updates.

Concurrent rendering: prioritize responsiveness

ReactConcurrency

Concurrent rendering lets React interrupt, restart, or discard eligible render work before committing it. This is cooperative scheduling on the JavaScript thread, not parallel component execution. The commit’s DOM mutation work is synchronous; users do not see a partially applied React tree from an interrupted render.

  • Use case: Keep a search input update urgent while marking an expensive results update as a transition. Use useTransition for an update you control, or useDeferredValue to let a consumed value lag behind.
  • Limits: A transition does not debounce requests, make computation faster, or interrupt a single long synchronous calculation inside your function. Split that calculation or use a Web Worker.
  • Correctness: Pure renders and useSyncExternalStore help React work with consistent snapshots. Suspense can coordinate pending UI; transition scheduling does not order overlapping network mutations.

CSR vs traditional SSR

Client-Side Rendering (CSR)

ReactRendering

The initial HTML might contain only <div id="root"></div>. React creates the content in the browser:

import { createRoot } from 'react-dom/client';

createRoot(document.getElementById('root')!).render(<Counter />);

There is no hydration because there is no pre-existing React-rendered DOM to reuse.

Server-Side Rendering (SSR)

ReactRendering

The server might send <button>Count: 0</button> before the browser has loaded the JavaScript needed to make the button work.

Important: In traditional React SSR, client-capable component code is generally also shipped to the browser. The server render improves initial HTML delivery but does not eliminate browser-side React.

Quick comparison

Hydration

Hydration is React connecting client-side component logic to HTML that already exists in the browser.

ReactRendering
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      Count: {count}
    </button>
  );
}

Server output:

<div id="root"><button>Count: 0</button></div>

Browser hydration:

import { hydrateRoot } from 'react-dom/client';

hydrateRoot(document.getElementById('root')!, <Counter />);

Hydration mismatch

ReactRendering

Server and browser should produce the same initial output. This can fail:

function RandomValue() {
  return <div>{Math.random()}</div>;
}

The server might render 0.42 while the client initially renders 0.81. Avoid nondeterministic values in initial rendering, or defer browser-only values until after hydration. See effect setup and cleanup for an example of browser-side work.

Remember: In the browser, React’s render phase computes the next UI tree; reconciliation compares trees, and the commit phase applies DOM changes. SSR produces HTML; hydration reuses that HTML while connecting client-side React logic.

React Server Components (RSC) vs Client Components

Async vs. synchronous components: A synchronous function component returns a React node (often JSX, but also text, null, or other supported values). An async component returns a Promise and can use await during rendering. Server Components support both forms; Client Components cannot be async functions. An async handler still follows event-loop scheduling; async does not move CPU work off the main thread.

Server Component

ReactAPI integration
// Server Component, for example in Next.js App Router
async function ProductInfo() {
  const product = await db.getProduct();
  return <h1>{product.name}</h1>;
}
  • Runs only on the server.
  • Can fetch data and access databases and server-side secrets directly. Keep secrets out of rendered output and props sent to Client Components. Server-state ownership is independent of component execution location. Server execution also does not replace authentication and authorization.
  • Can be async and await data during rendering, as in the example above.
  • Its component implementation JavaScript is not shipped to the browser.
  • Is never hydrated.
  • Cannot use useState, useEffect, or browser event handlers.

Nuance: RSC rendering produces a serialized RSC/Flight payload, not simply an HTML string. SSR can use the resulting tree to produce initial HTML.

Client Component

ReactBrowser
'use client';

import { useState } from 'react';

function LikeButton() {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked(true)}>
      {liked ? 'Liked' : 'Like'}
    </button>
  );
}
  • Its JavaScript is shipped to the browser.
  • Can use useState, useEffect, and event handlers. Access browser APIs in effects or handlers, since initial rendering may run on the server.
  • The component itself must be synchronous, but event handlers can be async. Effects can start async work inside an inner function; the useEffect callback itself must not be async, because it must return either a cleanup function or nothing, not a Promise.
  • Can also be rendered to HTML on the server on the initial request.
  • If server-rendered, it is subsequently hydrated.
'use client' does not mean “render only in the browser.” It marks a module dependency boundary: the module and its transitive imports enter the client module graph. A Client Component can still participate in initial SSR. See children and composition patterns for UI composition; the module boundary is a separate concern.

Streaming SSR and Suspense

Traditional SSR may wait for a slow section before sending the full page. Streaming SSR lets the server send ready sections earlier.

ReactRendering
import { Suspense } from 'react';

function ProductPage() {
  return (
    <>
      <Header />
      <ProductDetails />
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews />
      </Suspense>
    </>
  );
}

Illustrative timeline:

The chunks travel through the same HTTP response. Suspense boundaries help React isolate content that is not ready. Selective hydration lets React hydrate Suspense boundaries independently and prioritise boundaries the user interacts with. Hydration can overlap with streaming rather than waiting for the whole page. The data source must support Suspense; fetching inside useEffect does not trigger a Suspense fallback.

Distinction: Streaming controls when HTML arrives; hydration controls when browser-side React becomes active.

For state, effects, refs, and async APIs within these execution boundaries, see React Hooks.

How RSC, SSR, and hydration fit together

// Server Component
async function ProductPage() {
  const product = await db.getProduct();

  return (
    <>
      <h1>{product.name}</h1>
      <LikeButton />
    </>
  );
}

Combine the two: ProductPage handles server-side data fetching, while LikeButton, the Client Component from the component-boundary example, handles interactive state.

Error boundaries: isolate rendering failures

Purpose: Replace a failed React subtree with a fallback while preserving useful surrounding UI. Choose boundaries by independent recovery and user tasks, not automatically around every component.

Design patternReactResilience

Example: Put recommendations behind a boundary so a rendering exception does not remove product details and the purchase controls. Keep a broader route boundary for failures that make the route unusable.

import { Component } from 'react';
class ErrorBoundary extends Component {
  state = { failed: false };
  static getDerivedStateFromError() { return { failed: true }; }
  componentDidCatch(error, info) {
    // Send error and component stack to the application's reporting service.
  }
  render() {
    return this.state.failed ? this.props.fallback : this.props.children;
  }
}
// Usage: <ErrorBoundary fallback={<p>Recommendations unavailable.</p>}>
//          <Recommendations />
//        </ErrorBoundary>

Scope: Boundaries catch descendant rendering, constructor, and lifecycle errors. They do not catch their own errors, ordinary event-handler exceptions, arbitrary rejected promises/timer callbacks, or the server render itself. Handle request errors through the data layer and event failures with explicit error handling. Suspense-enabled render reads can surface errors to a boundary through their integration.

Use when: A route or widget can fail independently and has a meaningful fallback. A framework’s route error handling or a maintained boundary library often supplies reset/reporting integration. React has no built-in function-component error-boundary hook.

Benefits and tradeoffs: Limits UI failure scope and improves diagnostics. Too many boundaries can conceal broken workflows behind generic messages; never imply a purchase succeeded because its UI failed. Define reset behavior when the resource changes or the user retries; a remount via a changed key resets subtree state but cannot repair invalid data.

Compare: Suspense handles supported pending rendering; error boundaries handle rendering failure. Neither is a retry policy or circuit breaker. Request timeouts and server failure containment address different layers.

Choosing an approach

  • CSR: Useful for highly interactive applications where server-rendered initial HTML is not important.
  • SSR: Useful when the first response should already contain meaningful HTML, including for content visibility and SEO.
  • Streaming SSR: Useful when parts of a page depend on slow data and can be separated with Suspense.
  • Server Components: Good default for server data fetching, non-interactive UI, and keeping implementation JS out of the browser.
  • Client Components: Needed for local interactive state, effects, browser APIs, and event handlers.

In Next.js App Router, a practical default is to use Server Components for server-only work and add Client Components at interactive boundaries, while letting SSR produce the initial page HTML.

Interview-ready answer

CSR creates the UI in the browser. SSR generates initial HTML on the server and then hydrates client-side React so the page becomes interactive. Streaming SSR sends that HTML progressively, often using Suspense boundaries, so slow sections do not block ready content. React Server Components run exclusively on the server and send a serialized result rather than their component implementation JavaScript; they are never hydrated. Client Components can still contribute to server-rendered HTML, but their JavaScript is sent to the browser and hydrated. Modern Next.js combines RSC, SSR, streaming, and hydration rather than treating them as mutually exclusive choices.

Five things to remember

  1. CSR: React creates the DOM in the browser.
  2. SSR: The server generates initial HTML.
  3. Streaming: Ready HTML can arrive before slower sections finish.
  4. RSC: Server-only component code stays on the server; no hydration for those components.
  5. Hydration: Browser-side React activates previously server-rendered interactive UI.

One-line summary: SSR is about HTML generation, RSC is about component execution boundaries, streaming is about delivery timing, and hydration is about client interactivity.
