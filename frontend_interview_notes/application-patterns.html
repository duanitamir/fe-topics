Application Design Patterns

Choose a pattern by the pressure it resolves

Design patterns describe recurring solutions and their tradeoffs. Architectural patterns organize larger boundaries; principles guide decisions. Use the smallest mechanism that makes ownership, behavior, and failure handling explicit. A function or module is often enough; naming a pattern does not require classes or a framework.

PressureStart withRelated alternative
Interchangeable algorithmsStrategyA direct conditional for a small fixed choice.
Mismatched external contractAdapterUse the original API directly when its coupling is acceptable.
Hard-coded dependenciesDependency injectionDirect imports for stable, pure helpers.
A complicated subsystemFacadeDirect calls when the workflow is already simple.
Business rules coupled to infrastructurePorts and adaptersModules with explicit boundaries for small applications.
Client-specific API compositionBFFA shared API or framework server route when sufficient.
Risky replacementStrangler Fig / branch by abstractionA direct replacement for small, easily verified changes.
Dependency failures spreadingCircuit breaker / bulkheadTimeouts and bounded concurrency as a baseline.

For messages and state transitions, use the existing commands, events, and actions, unidirectional data flow, and state-machine sections. This page focuses on application code and integration boundaries.

Strategy: make a behavior interchangeable

Purpose: Encapsulate alternative algorithms behind one contract. The caller chooses a strategy without knowing its implementation. In JavaScript, an injected function is often simpler than a class hierarchy.

Design patternArchitecture

Use when: A product list supports several ranking policies, or an export feature supports different formatters. Each policy varies independently of the calling workflow.

type Product = { price: number; rating: number };
type Ranking = (a: Product, b: Product) => number;
const byPrice: Ranking = (a, b) => a.price - b.price;
const byRating: Ranking = (a, b) => b.rating - a.rating;
function rank(products: Product[], strategy: Ranking) {
  return [...products].sort(strategy); // Preserve caller-owned data.
}
const ranked = rank([{ price: 20, rating: 4 }, { price: 10, rating: 3 }], byPrice);

Benefits and tradeoffs: Policies are independently testable and replaceable, but extra indirection makes a tiny workflow harder to follow. Strategies must honor the same semantics, including mutation, errors, and ordering guarantees.

When not to use: For one stable algorithm or two trivial local branches, use a function or conditional. A data lookup table suits constants; Strategy suits executable behavior.

Compare: Strategy selects how to perform work; the State pattern changes behavior according to lifecycle state. An Adapter translates an incompatible contract rather than selecting an algorithm. A React render prop may inject a rendering strategy; see composition patterns.

Adapter: translate an external contract

Purpose: Convert an existing interface or data model into the one your application expects. Keep vendor naming, serialization, and error formats at the boundary instead of spreading them through components.

Design patternArchitectureAPI integration

Example: A provider returns { payment_id, amount_cents, currency_code }; a payment adapter maps it into your Payment model. Do not silently guess currency precision: money units are part of the contract.

type ProviderPayment = { payment_id: string; amount_cents: number; currency_code: 'USD' };
type Payment = { id: string; amountMinor: number; currency: 'USD' };
function adaptPayment(raw: ProviderPayment): Payment {
  return { id: raw.payment_id, amountMinor: raw.amount_cents, currency: raw.currency_code };
}

Use when: Integrating a vendor, migrating APIs, or connecting a form library to an input contract. Validate untrusted JSON at runtime before adapting it; TypeScript annotations do not validate a network response.

Benefits and tradeoffs: Isolates external changes and makes application models consistent. Mapping code and error translation need maintenance; a lowest-common-denominator interface can hide essential provider capabilities.

When not to use: Do not wrap every utility in a pass-through adapter. Use a stable API directly if there is no meaningful mismatch or boundary to protect.

Compare: Adapter translates a contract; Facade simplifies a subsystem; Strategy swaps behavior. An anti-corruption layer is a broader domain boundary that prevents another system’s concepts from distorting your model, often using adapters. See component and form adapters.

Dependency injection: supply dependencies explicitly

Purpose: Let an application function receive its collaborators instead of locating or constructing them internally. This separates policy from dependency creation and enables deterministic testing.

Design patternArchitecture
type Clock = () => number;
type Session = { expiresAt: number };
function isExpired(session: Session, now: Clock): boolean {
  return now() >= session.expiresAt;
}
isExpired({ expiresAt: 2000 }, () => 1000); // Deterministic: false.
isExpired({ expiresAt: 2000 }, Date.now);   // Production clock.

Use when: Time, network clients, storage, or feature policies need to vary by environment or test. Construct them at a composition root—the application’s setup boundary—and inject through parameters, constructors, or a scoped provider.

Benefits and tradeoffs: Dependencies become visible and replaceable. Too many parameters can reveal an oversized responsibility; a DI container can hide the dependency graph and introduce lifetime mistakes.

When not to use: Stable pure helpers usually work as direct imports. Prefer explicit parameters before introducing a container. A service locator asks a registry for dependencies inside business code; it hides requirements that injection makes explicit.

Compare: React Context can distribute an injected service, but Context is a delivery mechanism, not dependency injection itself. Keep service identity stable when appropriate and scope personalized services per request/session; a global singleton can leak SSR user data. Ports define contracts; injection supplies implementations.

Facade: expose a cohesive workflow

Purpose: Give callers a small interface over a complex subsystem. A facade hides coordination details while exposing outcomes the caller needs.

Design patternArchitectureAPI integration

Example: checkout.submit(draft) coordinates validation, an order API, and confirmation mapping. The React form knows about pending, success, and actionable failure rather than every SDK involved.

Use when: Several callers repeat the same sequence or must obey the same integration rules. Return explicit domain outcomes and preserve enough error information for recovery.

Benefits and tradeoffs: Reduces coupling and centralizes orchestration. An expanding facade can become a god object; keep it scoped to a cohesive capability. Calling several APIs through one method does not make the workflow atomic—handle partial failure explicitly.

When not to use: One clear operation rarely needs another wrapper. If the concern is only translating one provider’s contract, use an Adapter. If business orchestration is substantial, use an application service with injected collaborators.

Compare: A facade can be a local module. A BFF is a server boundary and may expose facade-like endpoints. A proxy preserves an interface while controlling access or remote invocation; a facade intentionally simplifies the interface.

Ports and adapters: protect business rules

Purpose: In hexagonal architecture, the application core defines the capabilities it needs through ports. Infrastructure implements those ports through adapters. Source-code dependencies point toward the core’s contracts; the core does not import React, a database driver, or a payment SDK.

Design patternArchitectureAPI integration

Example: A place-order use case accepts a PaymentGateway port and an OrderRepository port. An HTTP handler is a driving adapter that invokes the use case; a payment SDK adapter is a driven adapter used by it. A composition root wires them together through dependency injection.

// Core contract: owned by the application, not a vendor SDK.
interface OrderRepository {
  findById(id: string): Promise<{ id: string; totalMinor: number } | null>;
}
function makeLoadOrder(orders: OrderRepository) {
  return (id: string) => orders.findById(id);
}
// An HTTP or database adapter implements the port; the use case stays unchanged.

Use when: Business rules are meaningful, several entry points share them, or infrastructure changes independently. In a frontend, keep pricing rules or workflow decisions in framework-independent modules, while hooks adapt those rules to React lifecycles.

Benefits and tradeoffs: Supports focused tests and replaceable infrastructure. Interfaces and mappings add indirection; a port for every CRUD getter can merely duplicate a library API.

When not to use: A small UI with minimal business logic may need only feature modules and a clear API client. Extract boundaries when a real dependency or policy needs isolation.

Compare: A layered architecture can also enforce inward dependencies; folder names alone do not guarantee this. An Adapter is one building block, while hexagonal architecture governs relationships across the application. Keep authoritative rules on the server even if shared client logic improves UX; see server authorization.

Backend for Frontend: shape a server boundary for a client

Purpose: A BFF provides APIs tailored to one frontend experience. It can aggregate upstream responses, adapt payloads, and keep upstream credentials on the server.

Design patternArchitectureAPI integration

Example: A product page calls GET /web/product-page/42; its BFF fetches product and availability data, authorizes the user, and returns a view-oriented response. Reviews may remain independently loaded so a slow optional dependency does not block the page.

Use when: Web and mobile have materially different data needs, browser-to-service orchestration is complex, or a server-managed session fits the credential threat model. Framework route handlers can implement this boundary without a separate service.

Benefits and tradeoffs: Reduces client coupling and can reduce request waterfalls, but adds server operations, latency, cache policies, and another failure boundary. Enforce resource authorization; avoid an unbounded pass-through proxy or aggregation endpoint.

When not to use: If a shared API already fits, use it directly. Use an API gateway for shared routing, authentication infrastructure, or quotas; use a BFF for client-specific composition. GraphQL offers a query contract and execution model and can be used within a BFF—it is not automatically an alternative deployment boundary.

Compare: Server Components govern component execution and can call server-side services; a BFF governs the browser-facing API/session boundary. A single framework application can contain both. Protect upstream work with timeouts and failure containment.

Incremental replacement: Strangler Fig & branch by abstraction

Purpose: Replace a legacy implementation in controlled steps while keeping the product usable. These approaches reduce the amount of behavior changed at once.

Design patternArchitectureResilience
ApproachMechanismExample
Strangler FigRoute selected capabilities to the new implementation while the legacy implementation serves the rest.Move product routes to a new frontend, then checkout, then remove the old frontend.
Branch by abstractionIntroduce a stable interface, implement old and new variants behind it, and migrate callers before removing the old variant.A storage port switches from localStorage to IndexedDB without rewriting each feature simultaneously.

Use when: A design-system, framework, API, or persistence migration is too broad for a safe direct replacement. Define the seam, behavior contracts, verification metrics, rollout cohorts, and rollback path before moving traffic.

Example plan: Adapt the legacy implementation behind the interface; add the new implementation; switch a small cohort with a feature flag; compare errors and user outcomes; expand; remove the flag and old code. For data/schema changes, use backward-compatible expand-and-contract steps. Rolling code back may not undo already-written data.

Benefits and tradeoffs: Smaller releases and explicit rollback come with temporary duplication and compatibility work. Assign an owner and removal criteria so the transition does not become permanent.

When not to use: Prefer a direct replacement for a small, well-tested change. A feature flag is a routing tool, not a migration architecture. Avoid casually dual-writing both systems: divergent writes need an explicit consistency and recovery policy.

Compare: Strangler Fig moves capability boundaries; branch by abstraction moves implementations behind a contract. Adapters translate old/new interfaces; production performance measurements help verify a migration’s actual outcome.

Failure containment: circuit breakers & bulkheads

Purpose: Protect application capacity when dependencies slow down or fail. These patterns are most relevant in your backend/BFF; a browser can degrade its UI but cannot enforce service-wide protection.

Circuit breaker: stop repeatedly calling a failing dependency

Design patternResilienceAPI integration

A breaker monitors configured failure/timeout rates. In closed state it allows calls; in open state it rejects quickly for a cooldown; in half-open state it permits limited probes to decide whether to recover. Scope breakers to the dependency/operation that fails rather than disabling unrelated work.

Example: After repeated recommendation-service timeouts, return a clearly degraded product page without recommendations. A breaker needs minimum sample sizes, suitable thresholds, bounded probes, and observability. It does not repair the dependency.

Bulkhead: isolate capacity so failures cannot consume everything

Design patternResilienceAPI integration

A bulkhead gives operations separate bounded resources, such as concurrency limits, connection pools, or queues. If image processing saturates its allocation, checkout still has capacity. Bound waiting queues and reject or degrade when capacity is exhausted.

Use when: A shared process calls unreliable services or handles workloads with different criticality. Breakers reduce futile work; bulkheads limit how far resource exhaustion spreads. They complement each other.

Benefits and tradeoffs: Better failure isolation costs configuration and capacity planning. Isolated pools can leave capacity unused; a breaker can block a recovering dependency if poorly tuned. Per-instance breakers do not automatically coordinate across a fleet.

When not to use: Start with request deadlines, bounded concurrency, cancellation where supported, and actionable errors. Add breakers where repeated failures are a demonstrated risk; avoid placing every browser fetch behind a homegrown global breaker.

MechanismPrimary question
Timeout/deadlineHow long may this operation occupy resources?
Retry with exponential backoff and jitterIs a bounded additional attempt likely to succeed safely?
Circuit breakerShould we attempt this dependency now?
BulkheadHow much isolated capacity may this workload consume?
Rate limitingHow frequently may requests enter?
React error boundaryWhich UI subtree should show a fallback after a rendering failure?

Retry safely: Retry only suitable transient failures within an overall deadline and attempt budget. Use backoff/jitter to avoid synchronized retry storms; respect server guidance. Mutations need idempotency semantics, and aborting a browser fetch does not guarantee upstream work stopped. Rate limiting protects admission; error boundaries isolate UI failures rather than dependency capacity.

Interview review: explain the seam and the cost

Start with a concrete pressure: changing policy, an external contract, hidden dependencies, repeated orchestration, migration risk, or failure propagation. Identify who owns the contract, show the smallest implementation, and describe how it fails and is tested. Explain the simpler alternative and why the current complexity earns its cost.

Practice: Design a replaceable payment client (Adapter + injection), keep checkout rules independent (ports), hide coordination behind a focused facade, and explain why that does not make payment and order persistence atomic. For frontend state, connect these decisions to command handlers and pure reducers.
