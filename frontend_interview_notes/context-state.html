Server state vs. client state: choose by ownership

Client state is state whose authoritative owner is the running UI: an open dialog, selected tab, or unsaved form draft. Server state is data owned by a remote system: a product, profile, or purchase record. The browser holds a cached representation of server state that can become stale or change independently of this tab.

ReactState management

Two separate dimensions: Server/client state describes data ownership. Server/Client Components describe component execution boundaries. A Client Component can read and mutate server state; sending fetched data as props does not turn it into client-owned state.

QuestionClient stateServer state
Who owns the truth?The UI, its parent, or a client store.A remote system; the client has a snapshot.
Typical changesUser interactions and local workflow transitions.Reads, mutations, other users, background jobs, and remote events.
Primary concernsOwnership, transitions, persistence needs, and subscription scope.Freshness, fetching, errors, retries, invalidation, and reconciliation.
Typical toolsuseState, useReducer, Context, or a client store.Framework loaders/Server Components, TanStack Query, SWR, or a supported data layer.

When to use which tool

  • Local UI state: Start with useState; use useReducer for related transitions. Keep the owner close to its consumers.
  • Shared client state: Lift state to a common parent or distribute it through Context. An external store can fit broad, frequent, selectively subscribed updates; sharing alone does not make state server state.
  • Navigation state: Put shareable filters, sorting, and pagination in the URL when refresh, back/forward navigation, or copied links should preserve them. The query result is server state; the selected filter is a client/navigation input.
  • Read-mostly page data: A framework loader or Server Component may fetch before rendering and provide route-level revalidation. Do not automatically add a second client cache when the framework already owns the needed data lifecycle.
  • Interactive remote data: Use a query cache when multiple consumers need remote data, background refresh, mutation coordination, or cache reuse across navigation. A small isolated request can use an effect, but then you own cancellation and race handling plus the remaining loading/error lifecycle.

Benefits, limitations & alternatives

  • Local state/reducer — benefits: Explicit UI ownership, simple transitions, no remote-cache machinery. Tradeoff: Sharing and persistence require design; these hooks do not provide refetching or invalidation.
  • Context/client store — benefits: Shares client-owned workflows and operations across a subtree. Tradeoff: Provider updates and subscription granularity need attention. Context can distribute fetched data, but does not itself supply a server-state synchronization policy.
  • Query cache — benefits: Shares keyed remote data and provides configurable freshness, retries, in-flight deduplication, and mutation lifecycle hooks. Tradeoff: Adds a dependency and policies for keys, invalidation, memory, and identity changes. It cannot infer all business relationships or make cached data always current.
  • Framework-managed data — benefits: Integrates loading, rendering, navigation, and potentially SSR. Tradeoff: Cache and revalidation semantics depend on the framework; mixed framework/client caches require explicit coordination.

Hooks, state, Context & stores: compare the right dimensions

Hooks and state are not alternatives. State is data that changes; hooks are React APIs that access state and other capabilities. useState/useReducer manage local state, useContext reads a distributed value, and a custom hook packages logic. Choose by ownership, lifetime, transitions, and subscription needs—not by the number of components alone.

Context + reducer vs. Redux Toolkit vs. XState

These tools emphasize different responsibilities. Context distributes a value through a React subtree. Redux Toolkit is the standard Redux approach to a shared store and event/reducer updates. XState models statecharts and actors with explicit workflow lifecycles. They can coexist when their ownership boundaries are clear.

Important distinction: XState context is not React Context

XState’s context is extended data associated with an actor’s state, such as a request or retry counter. React Context is a provider/consumer distribution mechanism. You can provide a stable actor reference through React Context and use selector subscriptions to that actor; this does not make the two concepts interchangeable.

Capabilities overlap: Redux can represent an FSM with disciplined reducers; XState can store shared data; Context can distribute either a store or actor. Choose the tool whose default model best exposes the dominant risk. Do not claim “Redux cannot do workflows” or “Context is always slow.” Measure render and operational complexity in the actual feature.

SSR/lifetime: Create request-scoped stores/actors for personalized server rendering and reset/dispose them at the correct session/feature boundary. Persistence, schema migration, cross-tab synchronization, and backend durability are separate contracts. See Context propagation, external-store subscriptions, and the same problems solved in different ways.

URL state: navigation is a state owner

Use the URL for state that should survive refresh, support copied links, and participate in back/forward navigation: search terms, filters, sort order, pagination, and the selected resource. Keep transient UI such as hover state local. The URL stores the selection; a query cache stores the resulting server data.

State managementBrowser
  • Read and validate: Parse URLSearchParams, allowlist sort values, normalize defaults, and validate page numbers. Use the normalized values in query keys so cache identity matches the request.
  • Update through the router: Prefer its search-parameter API for subscriptions, navigation, and SSR integration. Use push for meaningful history entries and replace for refinements that should not flood history. Reset the page when a filter changes.
  • One authoritative source: Derive committed filters from the URL. A local input draft is useful while typing, but define when it is committed and how navigation resets it. Two independently synchronized copies invite loops and stale values.
  • Tradeoffs: URLs improve shareability but expose values in history, logs, and potentially referrers. Do not put credentials or sensitive drafts there. Encoding is not encryption.

Implementation: Read new URLSearchParams(location.search) at a router boundary, normalize inputs, then pass them to the data layer. Bare history.pushState() does not emit popstate; a custom integration must publish its own updates and handle back/forward events. See persistence choices for state that should persist without becoming a link.

For History API behavior, pending transitions, focus/scroll restoration, and dirty-form guards, continue with Routing & Navigation. URL ownership and navigation lifecycle solve different parts of the problem.

Unidirectional data flow & derived state

Purpose: Make changes traceable: interaction → handler/action → state transition → render. The rendered view derives from state; it does not maintain an independently synchronized copy of the same truth.

Design patternState managementReact

Minimal example · derive instead of copying:

function ProductList({ products }) {
  const [query, setQuery] = useState('');
  const visible = products.filter(p => p.name.includes(query));
  return <><input value={query} onChange={e => setQuery(e.target.value)} />
    {visible.map(p => <div key={p.id}>{p.name}</div>)}</>;
}

With useState imported from React: input changes query → render derives visible items. There is no second visible-items state to synchronize.

Example: Store items and query, then calculate visibleItems = items.filter(matchesQuery) during render. Do not store visibleItems and update it through an effect after every item or query change. That creates temporary inconsistency and extra work.

Use when: Designing form ownership, list filters, reducers, or shared stores. Choose one authoritative owner for each fact, and expose explicit change requests. See controlled component contracts and message design.

Benefits and tradeoffs: Predictable transitions and fewer synchronization bugs. Expensive derived calculations may need memoization or indexed computation; memoization is an optimization, not a new owner. A form draft intentionally diverges from a server snapshot and is a separate state concept.

When not to overengineer: A simple local interaction needs no store or action system. Native uncontrolled forms are valid. Two-way-binding frameworks can still have explicit ownership; the problem is ambiguous or duplicated ownership, not the presence of a binding API. Avoid using effects to synchronize values that can be derived directly.

Message design: actions, commands, events & payloads

These are message-design concepts, not one formal design pattern. They appear in reducers, state machines, domain-driven design (DDD), and event-driven systems. The useful distinction is between intent and fact; the same JavaScript object shape can represent either.

What each part means

State managementArchitecture
TermResponsibilityExample
CommandRequests an operation. A handler validates it, checks permissions, and attempts the work. It can be rejected.CreateOrder: please create an order.
EventDescribes an occurrence. A domain event records a business fact; other consumers may react to it.OrderCreated: an order was successfully created.
ActionA message accepted by a state-management API. In Redux, a plain action is an object with a string type. Its meaning can be command-like or event-like.{ type: 'orders/orderCreated', payload: order } represents a fact as a Redux action.
PayloadThe data needed to process or understand a message, separate from its type and metadata. It is not an operation by itself.A creation command carries product ID and quantity; the resulting event carries the saved order and its assigned ID.

Type and metadata: The type identifies what the message means. Optional metadata can carry a request ID, correlation ID, timestamp, or schema version. payload is a common convention, not a JavaScript requirement: useReducer accepts any action shape you design, and the state-machine example uses top-level fields. An action creator simply constructs an action; dispatch submits it to the store or reducer integration.

How they work together

Example: keep side effects outside the reducer

State managementArchitecture

The example assumes one in-flight submission and starts with { status: 'idle', order: null, error: null }. The handler owns the asynchronous work; the reducer only derives state from the resulting actions.

// Message design example: a command handler performs the side effect.
async function handleCreateOrder(command, dispatch) {
  if (command.type !== 'CreateOrder') throw new Error('Unsupported command');
  dispatch({ type: 'orders/submissionStarted' });
  try {
    const response = await fetch('/api/orders', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(command.payload)
    });
    if (!response.ok) throw new Error('Order could not be confirmed');
    const order = await response.json(); // API returns the saved order.
    dispatch({ type: 'orders/orderCreated', payload: order });
  } catch (error) {
    dispatch({
      type: 'orders/submissionFailed',
      payload: { message: error.message }
    });
  }
}

// A pure reducer consumes actions; it never performs the HTTP request.
function orderReducer(state, action) {
  switch (action.type) {
    case 'orders/submissionStarted':
      return { ...state, status: 'submitting', error: null };
    case 'orders/orderCreated':
      return { ...state, status: 'success', order: action.payload };
    case 'orders/submissionFailed':
      return { ...state, status: 'error', error: action.payload.message };
    default:
      return state;
  }
}

// From a submit handler; dispatch comes from useReducer or a Redux store.
handleCreateOrder({
  type: 'CreateOrder',
  payload: { productId: 'book-42', quantity: 1 }
}, dispatch);
  • Command payload: The requested product and quantity express what the user wants. The server still validates them and derives trusted values such as price and ownership.
  • Event-like action payload: The confirmed order represents what the server accepted. orders/orderCreated is both a Redux-style action and an event-like message; these categories are not mutually exclusive.
  • Failure semantics: A failed response means the client could not confirm success. A connection loss does not prove that the server did not create the order. Preserve the draft and use the idempotency and reconciliation policy before retrying.
  • Production integration: For shared server data, use the existing query-cache mutation lifecycle rather than maintaining a second copy in a reducer. The reducer here makes message roles visible; it is not a replacement data layer.

When this distinction helps—and when to keep it simple

Use it when asynchronous workflows have clear requested, pending, confirmed, and failed outcomes; when several consumers react to one fact; or when a state machine needs explicit transition inputs. Intent/fact naming makes debugging and responsibilities clearer. Tradeoff: Separate message types, handlers, and metadata add code and contracts to maintain. A local toggle may need only setOpen; a command does not require a command bus, and an event does not require a broker.

  • Naming: Commands usually use imperative names (CreateOrder); events use past tense (OrderCreated). Naming helps communicate intent but does not enforce correctness.
  • Delivery is a separate contract: Local dispatch is not durable publication or guaranteed delivery. Network events can be duplicated or missed; see real-time synchronization and recovery.
  • Related architectures: CQRS separates commands (writes) from queries (reads); it does not inherently require separate databases or event sourcing. Event sourcing persists events as the source of truth. Dispatching event-like actions in React or Redux does not automatically implement either architecture.
  • React terminology: React Actions, such as form Actions and useActionState, are functions participating in an update workflow. They are distinct from the message objects discussed here.

Interview explanation: A command expresses intent, an event records an occurrence, an action is the state-management API’s message, and a payload carries the associated data. I perform side effects in a handler or data layer and keep the reducer pure. I choose explicit messages when they clarify a workflow, without introducing unnecessary messaging infrastructure.

Model local workflows and valid transitions

State machines: model valid transitions

Design patternState management

A finite state machine (FSM) defines states, events, and permitted transitions. Its events describe transition inputs; see commands, events, and action messages for the naming distinction. This avoids contradictory boolean combinations such as isLoading and isSuccess both being true. A reducer can implement an FSM, but a reducer is not automatically a state machine.

type SearchState =
  | { status: 'idle' }
  | { status: 'loading'; requestId: number }
  | { status: 'success'; results: string[] }
  | { status: 'error'; message: string };

type SearchEvent =
  | { type: 'started'; requestId: number }
  | { type: 'resolved'; requestId: number; results: string[] }
  | { type: 'rejected'; requestId: number; message: string }
  | { type: 'reset' };

function searchReducer(state: SearchState, event: SearchEvent): SearchState {
  if (event.type === 'reset') return { status: 'idle' };
  if (event.type === 'started') {
    return { status: 'loading', requestId: event.requestId };
  }
  // Completion events only apply to the active request.
  if (state.status !== 'loading' || state.requestId !== event.requestId) {
    return state;
  }
  if (event.type === 'resolved') {
    return { status: 'success', results: event.results };
  }
  return { status: 'error', message: event.message };
}

Discriminated unions make each state’s data explicit. The request-ID check is a transition guard that ignores stale completions. Start requests in an event handler or effect, then dispatch completion events; never fetch inside the reducer. Combine this with request cancellation to reduce wasted work.

Tradeoff: An explicit transition model helps async workflows and multi-step UI. For hierarchical states, parallel states, or complex effects, a dedicated state-machine library can be clearer than an expanding reducer. For a simple toggle, local useState is usually enough.

State pattern vs. finite state machine vs. Strategy

Design patternState management

Purpose: The classic State pattern delegates state-dependent behavior to state-specific objects or functions. An FSM explicitly defines valid states and transitions; the State pattern is an implementation technique and does not by itself guarantee a complete transition model.

Example: An upload’s idle state accepts start; uploading accepts pause/cancel; completed accepts neither. For a few states, a discriminated union and reducer make these rules visible. State objects can help if each state owns substantial behavior, but do not trigger subscriptions or requests inside a React reducer.

Use when: Different lifecycle states permit different operations. Benefits: Replaces scattered state checks with localized behavior. Tradeoffs: More objects and indirection; transitions become difficult to audit if spread across implementations.

When not to use: Use a boolean for one independent toggle, a reducer for a modest explicit workflow, or a statechart library for hierarchical/parallel states and complex transitions. Strategy selects an algorithm independently of lifecycle; State selects behavior because the lifecycle changed.

Library choice: The reducer above is a modest FSM. For a side-by-side version using Redux Toolkit and XState, see the same asynchronous search problem. Model complexity, not the presence of async code alone, should drive the choice.

Same problem, different tools: choose by the pressure

Keep the product behavior fixed while comparing solutions. A library earns its cost when it makes ownership, transitions, failure handling, or subscriptions easier to reason about.

One asynchronous search: reducer, Redux Toolkit, or XState?

Fixed contract: Start a search, show loading, accept only the active result, support failure, and avoid stale completion. The existing local reducer example implements these guards explicitly. Context can share that reducer owner without changing the rules. If the problem is primarily remote result caching, start with a query cache instead of either implementation below.

// Redux Toolkit: useful when this workflow belongs in an existing shared store.
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

export const search = createAsyncThunk<string[], string>(
  'search/run', async (query, { signal }) => {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal });
    if (!response.ok) throw new Error('Search failed');
    return response.json(); // Validate the response at the real API boundary.
  }
);
const initialState: {
  status: 'idle' | 'loading' | 'success' | 'error';
  requestId?: string; results: string[];
} = { status: 'idle', results: [] };
export const searchSlice = createSlice({
  name: 'search', initialState, reducers: {},
  extraReducers: builder => builder
    .addCase(search.pending, (state, action) => {
      state.status = 'loading'; state.requestId = action.meta.requestId;
    })
    .addCase(search.fulfilled, (state, action) => {
      if (state.requestId !== action.meta.requestId) return;
      state.status = 'success'; state.results = action.payload;
      state.requestId = undefined;
    })
    .addCase(search.rejected, (state, action) => {
      if (state.requestId !== action.meta.requestId) return;
      state.status = action.meta.aborted ? 'idle' : 'error';
      state.requestId = undefined;
    })
});
// Add searchSlice.reducer to configureStore; dispatch(search(query)).
// New dispatches do not automatically abort old thunks: abort their returned
// promise when desired. requestId guards protect correctness independently.

Redux tradeoff: Selectors and DevTools integrate this into a shared application model. createAsyncThunk supplies lifecycle actions, but the latest-request policy, transitions, and cancellation ownership remain explicit. Immer-backed reducers permit the apparent mutations above while producing immutable store updates. Do not store AbortController or a promise inside ordinary Redux state.

// XState v5: useful when the interaction lifecycle is the main model.
import { setup, assign, fromPromise } from 'xstate';

export const searchMachine = setup({
  types: {
    context: {} as { query: string; results: string[] },
    events: {} as { type: 'SEARCH'; query: string } | { type: 'CANCEL' }
  },
  actors: {
    load: fromPromise(async ({ input, signal }: { input: string; signal: AbortSignal }) => {
      const response = await fetch(`/api/search?q=${encodeURIComponent(input)}`, { signal });
      if (!response.ok) throw new Error('Search failed');
      return response.json() as Promise<string[]>; // Real boundary needs validation.
    })
  }
}).createMachine({
  id: 'search', initial: 'idle',
  context: { query: '', results: [] },
  on: {
    SEARCH: {
      target: '.loading', reenter: true,
      actions: assign({ query: ({ event }) => event.query })
    },
    CANCEL: { target: '.idle' }
  },
  states: {
    idle: {},
    loading: {
      invoke: {
        src: 'load', input: ({ context }) => context.query,
        onDone: {
          target: 'success',
          actions: assign({ results: ({ event }) => event.output })
        },
        onError: { target: 'error' }
      }
    },
    success: {}, error: {}
  }
});
// With @xstate/react: create the owner using useActorRef(searchMachine),
// select snapshots with useSelector, and actorRef.send({ type: 'SEARCH', query }).

XState tradeoff: Leaving/re-entering loading stops the old invoked promise actor, so its result is no longer applied; passing its AbortSignal also cancels the fetch where supported. It does not guarantee that server work stops. Explicit states and invoked actors make the lifecycle visible, at the cost of additional concepts for this small case. Timed, hierarchical, or parallel behavior is where that model often earns more value.

React integration: Own the reducer/store/actor at the intended feature boundary. Creating one actor in every leaf hook produces independent workflows, just as separate useReducer calls do. Subscribe through the library’s React integration rather than reading mutable snapshots without subscriptions.

Interview recommendation: “I would use the query cache for remote results, local state for the input, and a reducer only if the interaction has meaningful transitions. I would choose Redux if shared client-domain state and conventions dominate, or XState if workflow/lifecycle complexity dominates. Context can distribute whichever owner the feature needs.”

Share state through Context

Context distributes values; it does not define state transitions. useReducer centralizes transitions, while a provider makes state and operations available to a subtree. Keep local state local; introduce shared state only when multiple consumers need the same source of truth. Start with controlled vs. uncontrolled state ownership when designing a reusable component.

Context + useReducer: separate state, actions & dispatch

ReactState management

For hook selection and lazy initialization, see useState versus useReducer. A reducer is a pure function (state, action) => nextState. Return immutable updates and perform side effects outside it. Keep domain actions meaningful, such as itemAdded, rather than exposing arbitrary state mutation. The message-design example separates a command handler’s side effects from event-like actions consumed by a pure reducer.

import {
  createContext, useContext, useReducer, useMemo, useCallback
} from 'react';

const StateContext = createContext(undefined);
const DispatchContext = createContext(undefined);
const ActionsContext = createContext(undefined);

function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'reset': return { count: 0 };
    default: throw new Error('Unknown action: ' + action.type);
  }
}

function CounterProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  const increment = useCallback(() => dispatch({ type: 'increment' }), [dispatch]);
  const reset = useCallback(() => dispatch({ type: 'reset' }), [dispatch]);
  const actions = useMemo(() => ({ increment, reset }), [increment, reset]);

  return (
    <DispatchContext.Provider value={dispatch}>
      <ActionsContext.Provider value={actions}>
        <StateContext.Provider value={state}>
          {children}
        </StateContext.Provider>
      </ActionsContext.Provider>
    </DispatchContext.Provider>
  );
}

function useCounterState() {
  const state = useContext(StateContext);
  if (state === undefined) throw new Error('CounterProvider is required');
  return state;
}

function useCounterActions() {
  const actions = useContext(ActionsContext);
  if (actions === undefined) throw new Error('CounterProvider is required');
  return actions;
}

function useCounterDispatch() {
  const dispatch = useContext(DispatchContext);
  if (dispatch === undefined) throw new Error('CounterProvider is required');
  return dispatch;
}
  • State context: Read current data; these consumers update when the state value changes.
  • Actions context: Expose stable domain operations that hide action-object structure. A button that only calls increment() need not subscribe to count changes.
  • Dispatch context: Expose raw dispatch when consumers genuinely need it. React guarantees a stable dispatch identity. Often state plus actions or state plus dispatch is sufficient; three contexts are an option, not a requirement.
  • Custom consumer hooks: Centralize provider checks and expose a domain API. A hook that reads state and then returns only actions still subscribes its caller to state; keep subscriptions separate.

Context propagation & referential stability

ReactPerformanceState management

React compares the provider’s previous and next value using Object.is. When it changes, consumers reading that context receive an update, even through React.memo. Reading only state.count from a large context does not create a property-level subscription.

  • Referential stability: An object literal or inline function creates a new reference on each render. A provider using value={{ state, dispatch }} therefore changes identity whenever that object is recreated.
  • Stable values: useMemo stabilizes a wrapper object when its dependencies are unchanged; useCallback stabilizes a function. Include all reactive dependencies to avoid stale closures. A callback that depends on changing state must change unless it is restructured safely.
  • Why separation helps: Stable action/dispatch contexts do not broadcast state changes to action-only consumers. Splitting unrelated state domains also reduces the subscription scope.
  • What separation cannot guarantee: Consumers can still render because their own state or props changed, or their ancestor rendered. Context separation removes a particular update source; it does not block ordinary parent-driven rendering. Use the React render analysis workflow to verify the result.

Context selectors & subscription granularity

ReactPerformanceState management

A selector derives the slice a consumer needs. Native useContext does not subscribe selectively: a custom hook returning useContext(Context).count still subscribes to the entire context value.

use-context-selector is a third-party library that supports selected-value subscriptions. Create the context using the library’s createContext, then consume it with its selector hook:

import { createContext, useContextSelector } from 'use-context-selector';

// Alternative to the native StateContext in the earlier example.
const SelectableStateContext = createContext({ count: 0, query: '' });

function CountLabel() {
  const count = useContextSelector(SelectableStateContext, state => state.count);
  return <span>{count}</span>;
}

A query-only update need not trigger a selector subscription update when the selected count remains equal. Selectors should be pure and return referentially stable results for unchanged inputs; returning a fresh object defeats this optimization. Parent-driven renders remain possible. For frequent updates or complex subscriptions, consider an external store with selector support and React’s useSyncExternalStore integration. See Observer and external-store contracts for snapshots, ownership, and tradeoffs.

Observer, publish–subscribe & external stores

Purpose: Notify consumers when a producer changes without hard-coding all consumers into its update logic. Observer usually means subscribing directly to a subject. Publish–subscribe introduces a topic/channel or broker between publishers and subscribers; terminology varies, so describe the actual topology.

Design patternState managementReact

Minimal example · subscribe and unsubscribe:

// Observer: subscribe directly to a store (API is illustrative).
const unsubscribe = store.subscribe(() => render(store.getSnapshot()));
store.setState(nextState); // Notifies subscribers.
unsubscribe();

// Pub/sub: a topic routes events to independent subscribers.
const stop = bus.subscribe('order.created', showNotification);
bus.publish('order.created', { orderId: 'o1' });
stop();

The store/bus implementations define delivery and error behavior. In React, connect an external store through useSyncExternalStore rather than manually invoking a renderer.

Examples: A store maintains listeners through subscribe(listener) and returns an unsubscribe function. A local event bus publishes cart/itemAdded to independent analytics and notification consumers. Network pub/sub adds serialization, authorization, and delivery/recovery concerns; a local bus does not supply those guarantees.

Use when: Several independent consumers react to a change, or an external data source needs React subscriptions. For shared state, keep a source-of-truth store and expose snapshots; use notifications to announce changes, not as the only record of current state.

React integration: useSyncExternalStore connects a subscription and a stable snapshot reader to React. Return an immutable cached snapshot while data is unchanged, subscribe with an unsubscribe contract, and provide an appropriate server snapshot for SSR. Use selector-capable integrations for slice subscriptions; returning a new object on every snapshot read can cause repeated rendering. React’s protocol helps prevent tearing—components displaying inconsistent versions of the same external store.

Benefits and tradeoffs: Decouples producers from consumers, but hidden subscriptions obscure execution order and resource ownership. A listener failure or synchronous reentrant publication needs a defined policy; an event bus is not a transaction. Unsubscribe on disposal and bound buffered work.

When not to use: Prefer props/callbacks for a parent–child interaction, Context for scoped value distribution, and a query cache for server state. Avoid using a global event bus to coordinate a workflow whose steps and errors should be explicit in one handler. Unlike events, commands represent work that needs a responsible handler.

Compare: Native Context subscribes consumers to provider value changes; selectors or external stores can provide finer granularity. Browser observers are specialized platform subscriptions, not general state stores; see Intersection Observer. See resource ownership for cleanup and WebSockets/SSE for remote delivery.

Synchronize remote data and local drafts

Server-state lifecycle: read → mutate → reconcile

State managementAPI integration
  1. Identify the resource: A query key includes the resource and every input that affects its result, including relevant tenant/user scope and filters. Keys identify cached representations; they are not authorization checks.
  2. Define freshness: In TanStack Query v5, staleTime describes how long cached data is considered fresh. Stale does not mean deleted: it may be displayed while eligible triggers refetch. gcTime controls retention after the query becomes inactive; it is a separate concern.
  3. Perform a mutation: Send the command to the server and expose pending/error UI. For confirmation-first behavior, keep the old value until success; for speculative behavior, follow the optimistic UI contract.
  4. Reconcile the cache: Write a complete authoritative response into its detail entry, or invalidate affected query keys. Invalidation marks matching queries stale and normally refetches active matches; it does not discover related lists automatically or fetch every inactive entry immediately.
  5. Handle identity and concurrency: Clear/scope sensitive caches when sessions change. Guard obsolete responses; overlapping writes may need version checks or a conflict policy on the server. A stale-time setting is not a distributed consistency guarantee.

Implementation: local UI state + a remote query cache

State managementAPI integration

This client-rendered example uses TanStack Query v5. It keeps the panel’s expanded state local and the product in one shared query cache. It assumes the API handles authentication, authorization, input validation, and applicable CSRF defenses; the cache does not replace those checks.

// Client-side React application; TanStack Query v5.
import { useState } from 'react';
import {
  QueryClient, QueryClientProvider, useQuery, useMutation, useQueryClient
} from '@tanstack/react-query';

const queryClient = new QueryClient(); // One stable cache for this client app.

async function readJson(response) {
  if (!response.ok) throw new Error('HTTP ' + response.status);
  return response.json();
}

function ProductPanel({ tenantId, productId }) {
  const [expanded, setExpanded] = useState(false); // Client state.
  const cache = useQueryClient();
  const key = ['product', tenantId, productId];
  const url = '/api/tenants/' + encodeURIComponent(tenantId)
    + '/products/' + encodeURIComponent(productId);

  const product = useQuery({
    queryKey: key,
    queryFn: ({ signal }) => fetch(url, { signal }).then(readJson),
    staleTime: 30_000
  });

  const favorite = useMutation({
    mutationFn: nextValue => fetch(url + '/favorite', {
      method: 'PUT',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ favorite: nextValue })
    }).then(readJson), // API returns the complete, confirmed product.
    onMutate: () => cache.cancelQueries({ queryKey: key, exact: true }),
    onSuccess: saved => {
      cache.setQueryData(key, saved);
      return cache.invalidateQueries({ queryKey: ['products', tenantId] });
    }
  });

  if (product.isPending) return <p role="status">Loading product…</p>;
  if (product.isError && !product.data) return <p role="alert">Cannot load product.</p>;

  return (
    <section>
      <h2>{product.data.name}</h2>
      <button aria-expanded={expanded} onClick={() => setExpanded(open => !open)}>
        {expanded ? 'Hide details' : 'Show details'}
      </button>
      {expanded && <p>{product.data.description}</p>}
      <button disabled={favorite.isPending}
        onClick={() => favorite.mutate(!product.data.favorite)}>
        {favorite.isPending ? 'Saving…' : product.data.favorite ? 'Unfavorite' : 'Favorite'}
      </button>
      {favorite.isError && <p role="alert">Change failed. Please retry.</p>}
    </section>
  );
}

function App() {
  // In a real app these come from validated session and route data.
  return (
    <QueryClientProvider client={queryClient}>
      <ProductPanel tenantId="acme" productId="42" />
    </QueryClientProvider>
  );
}
  • Client ownership: expanded belongs only to this panel; it does not need to travel through the server or global Context.
  • Server ownership: product.data stays in the query cache. The query key isolates this tenant/resource representation; staleTime is an explicit freshness choice, not a universal recommendation.
  • Cancellation: The query function consumes the provided AbortSignal. Before the mutation starts, cancelQueries stops an older detail fetch from overwriting the confirmed result later.
  • Mutation reconciliation: Success updates the detail entry and invalidates separately keyed product lists. Returning the invalidation Promise keeps the mutation pending through that step. Other related keys still need an explicit policy.
  • Cache lifetime: A module-level client is suitable for this single client app. For SSR, create/isolate caches per request and follow the framework’s dehydration/hydration integration; never share personalized request data through a process-global cache.
  • Failure handling: Initial read failures and mutation failures have separate UI. A full product should also surface background-refresh failures without unnecessarily discarding already-visible data.

Forms: server snapshot + client-owned draft

State managementForms

A fetched profile is server state; editing its name creates a client-owned draft. Initializing a draft from fetched data can be intentional. Blindly copying every refetch into the form with an effect can overwrite unsaved edits.

  • Initialize deliberately: Mount the editor after the resource loads. Key it by resource identity if changing records should reset the draft. Changing the key on every server version would also discard edits, so only do that under an explicit reset policy.
  • Handle remote changes: Track dirty fields. Keep edits, offer reload/reset, or merge untouched fields when a background update arrives; do not silently replace dirty values.
  • Save and reconcile: Submit the draft, handle validation/conflict errors, update or invalidate the server cache, and reset the draft to the accepted response if that is the intended UX. For conflicting edits, use the server version/ETag precondition and conflict policy.

GraphQL changes the request/schema contract, not server-state ownership. See normalized caches and mutation reconciliation for the GraphQL client choices.

Optimistic updates & concurrent mutation conflicts

An optimistic update displays the expected result before the server confirms it. It improves perceived responsiveness for reversible, predictable operations such as a favorite toggle. For payments, scarce inventory, or ambiguous outcomes, prefer a pending state and authoritative confirmation. useOptimistic models temporary UI; a query-cache mutation lifecycle coordinates shared remote data.

State managementConcurrencyAPI integration
  1. Prepare: Cancel obsolete reads where supported; record the affected entity, mutation ID, and base version. Save a snapshot only if rollback cannot erase newer work.
  2. Apply: Display the pending change, ideally as an overlay of pending operations on a confirmed snapshot. Keep the list and detail representations consistent or invalidate them deliberately.
  3. Confirm or reject: Replace pending values with the authoritative response on success. On failure, remove only that operation’s optimistic change and show a recovery action. Reconcile affected queries after pending operations settle.

Why simple rollback breaks with overlapping writes

ConcurrencyState management

Example: Mutation A optimistically sets a name to “Ada”; B then sets it to “Grace.” If A fails and restores its entire old snapshot, it erases B’s newer change. Similarly, an older success response may arrive last and overwrite newer UI. Response arrival order is not business ordering.

  • Serialize or disable per entity: Simplest when users do not need overlapping writes. The existing favorite example disables its button while saving. Other tabs or users can still write concurrently.
  • Track pending operations: Assign mutation IDs and derive the display from confirmed data plus remaining operations. A “latest request” guard protects local display ordering, but does not undo writes already accepted by the server.
  • Optimistic concurrency control: Send a base version or an If-Match precondition with the resource’s ETag. The server checks and writes atomically; failed preconditions produce 412 Precondition Failed, while application conflicts may use 409 Conflict. Refetch and offer merge/retry rather than silently overwriting.
  • Retry safely: For supported operations, reuse an idempotency key for retries of the same logical command. This avoids duplicate effects; it does not resolve two different commands editing the same resource.

Form connection: Keep the user’s dirty draft separate from the confirmed snapshot and show a conflict explicitly; follow the draft reconciliation policy and submission contract.

Choosing optimistic concurrency control

Design patternConcurrencyAPI integration

Problem: Two editors read version 7 and submit different changes. Without a precondition, the later write may silently overwrite the first. With optimistic concurrency control (OCC), each write includes the version it read; the server atomically updates only if that version is still current.

Example: Read a profile with ETag "v7", then send If-Match: "v7" with PATCH. After another write advances it to v8, the stale request receives 412. Preserve the local draft, load the latest version, and offer a merge or explicit retry. Use a strong validator for If-Match; server-side compare-and-update must be atomic.

Use when: Conflicts are infrequent and users can resolve them. Benefits: No lock held during human editing; conflicts are explicit. Tradeoffs: Requires versions and recovery UX. Frequent conflicts may make repeated retries unproductive.

Alternatives: A short database transaction with pessimistic locking can coordinate tightly contested server operations; avoid holding a lock across a human editing session. Atomic domain operations such as increment can avoid unnecessary read-modify-write conflicts. Last-write-wins is acceptable only when intentional data loss is harmless; collaborative merging may need specialized algorithms. UI serialization controls one client, not other users.

Distinction: OCC prevents stale writes; an optimistic UI predicts an outcome; an idempotency key deduplicates retries of one logical operation. They solve different problems and can be used together. See migration compatibility when versions span old and new clients.

Real-time updates: WebSockets vs. Server-Sent Events

Real-time messages deliver changes to server-owned data; they do not create a second source of truth. Feed them into the same query cache or normalized store used by ordinary reads and mutations.

  • Own the lifecycle: Subscribe in an effect or shared data service and close connections on teardown, resource changes, or logout. Avoid a separate connection per row. See effect synchronization.
  • Merge safely: Validate message shape, resource identity, and version. Ignore duplicate or older versions. Apply complete authoritative data or invalidate and refetch when a delta cannot be applied safely; coordinate events with pending optimistic operations.
  • Recover gaps: Reconnect does not guarantee missed events are delivered. Use event IDs/sequence numbers and server replay, or refetch a snapshot before resuming. Bound queued messages and coalesce updates when consumers fall behind.
  • Secure the channel: Authenticate connections and authorize every subscription/resource. Validate WebSocket origins; apply appropriate CORS/credential rules to SSE. Handle session expiry and close subscriptions on logout.

Interview review

Interview-ready distinction

I classify state by its authoritative owner before choosing a library. UI state stays local or in a shared client store when needed; remote data is a cached server snapshot with explicit freshness and mutation-reconciliation policies. A form can contain both. Context distributes values, but does not replace a query cache, and Server versus Client Components is a separate execution decision.

Related concepts: HTTP and application caching · Form Actions · External-store subscriptions · Authorization and cache isolation · TanStack Query defaults.

Interview-ready design rationale

I make state ownership and valid transitions explicit before choosing a sharing mechanism. For a shared workflow, I can use a pure reducer with Context, separate data subscriptions from stable operations, and expose custom hooks. I know that native context broadcasts value changes to all its consumers, so I use domain separation or selectors when profiling shows a need for finer subscriptions. For asynchronous workflows, I model explicit states and guard stale transitions rather than managing loosely related booleans.
