Request handlers, middleware & application services

A request pipeline typically parses and bounds the request, establishes identity, validates input, authorizes the operation, invokes application logic, and serializes the result. Middleware handles cross-cutting concerns; domain rules belong in explicit services/use cases rather than an opaque chain of hooks.

API integrationArchitectureSecurity

Example: PATCH /projects/42 runs through a body-size limit, session validation, schema validation, project-specific permission checks, an update transaction, and a response serializer. Generate a request/correlation ID and propagate it to downstream calls and logs.

Use: Keep transport handlers thin and return well-defined outcomes. Order middleware deliberately: an error handler must cover the relevant downstream work, and logging must not expose tokens or sensitive payloads. Bound time, body size, and queued work.

Alternatives: A small endpoint can be a clear function rather than many layers. Introduce a facade or ports and adapters when dependencies and rules justify them. GraphQL resolvers are another transport/application entry point, not permission to bypass these boundaries.

Validate input & enforce authorization at the server

Input validation checks shape, types, ranges, allowed combinations, and business constraints at a trust boundary. Authorization checks whether this principal may perform this operation on this resource. Client types and validation improve UX but cannot establish either server guarantee.

API integrationSecurity

Example: A create-order endpoint accepts product IDs and quantities, derives trusted prices on the server, validates availability, and checks the account’s permissions. It must not trust a price or tenant owner supplied by the browser.

Implementation: Parse into a validated input model, allowlist writable fields to prevent mass assignment, enforce object/tenant scope in data access, and use parameterized queries and output defenses. JSON/schema validation is distinct from HTML sanitisation and SQL parameter binding.

Tradeoffs: Shared schemas can reduce drift, but server business rules may exceed what the client can know. Avoid duplicating authorization in every UI component as if that protected the endpoint; use server-enforced object-level checks.

Error contracts, retries & ambiguous outcomes

An API error contract gives clients a stable machine-readable code plus safe details. HTTP status describes the protocol-level outcome; application codes identify recoverable cases without requiring clients to parse human wording.

API integrationResilienceHTTP
{
  "type": "https://example.com/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "errors": [{ "field": "quantity", "code": "OUT_OF_RANGE" }],
  "requestId": "req-42"
}

Example: Use a documented Problem Details representation or another consistent contract. Expose safe field errors; keep stack traces, credentials, and internal database details out of the response. Log diagnostic context with the same request ID.

Choose recovery: Validation failures need corrected input; forbidden actions need permission changes; transient overload may permit a bounded retry. A 202 acceptance needs a status/polling contract. A lost response after a write is ambiguous: use an idempotency/result lookup policy rather than assuming rollback.

Alternatives: A simple API can use a small explicit error union. Do not return 200 with an undocumented failure-shaped body for ordinary REST errors. GraphQL has a separate data-plus-errors execution model. See HTTP status semantics.

Pagination: offset, keyset & cursor contracts

Pagination bounds work and data transfer. Offset pagination skips a count of rows; keyset pagination continues after an ordered key. A cursor is a continuation contract and may encode keyset position, snapshot information, or another server token.

API integrationPerformance
-- Keyset example for a descending feed; parameter syntax is PostgreSQL.
SELECT id, created_at, title
FROM posts
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;

Use: Keyset pagination fits large feeds with deterministic sorting; a matching index such as (tenant_id, created_at, id) can help. Include a unique tiebreaker and bound page size. Offset is simpler for small datasets or page-number navigation but can become expensive and shift under insertions/deletions.

Contract: Validate cursor format and relevant filter/order scope; an opaque cursor is not authorization. Return next-cursor/has-more information. Pagination alone does not promise a consistent snapshot across changing data; define whether duplicates/gaps are acceptable or snapshot semantics are required.

Comparison: GraphQL connection-style edges/pageInfo describe one pagination schema, not a mandatory database algorithm. Frontend virtualization bounds rendered nodes; pagination bounds data retrieval. Use both when needed.

Indexes, transactions & connection pools

An index accelerates suitable lookup/order operations at the cost of write overhead and storage. A transaction groups database changes under atomicity and isolation rules. A connection pool reuses a bounded number of database connections; it does not create unlimited database capacity.

API integrationConcurrencyPerformance

Example: Creating an order and its line items belongs in a transaction so partial writes do not become a valid order. Keep transactions short; a payment provider call is not automatically included in the database transaction. Design explicit recovery for external side effects.

Measure: Use query plans and representative data to check index use and actual scans. Composite-column order, selectivity, filtering, and sort requirements matter. Avoid adding indexes to every column without evidence.

Concurrency: Isolation levels allow different anomalies. Use atomic conditional updates, constraints, or locks for correctness instead of an unchecked read-then-write. Handle deadlocks/serialization failures with a suitable retry policy. See optimistic concurrency control.

Pool limits: Account for all service instances, bound queue wait and request time, and release connections in finally/managed scopes. Serverless scaling can exhaust a database even when each instance has a small pool. Increasing pool size can increase contention rather than throughput.

N+1 queries, batching & request-scoped caching

N+1 describes fetching a collection once and then making an additional request/query per item or relation. It occurs in REST handlers, ORM code, and GraphQL resolvers; GraphQL does not cause or automatically solve it.

API integrationPerformance

Example: Load 30 orders, then load each customer separately: up to 31 queries. Use an appropriate join/eager load, or collect customer IDs and batch the lookup. Preserve authorization scope and input/output ordering.

Use: Trace database/upstream call counts for representative operations. A request-scoped batch loader can deduplicate repeated entity IDs during one operation; do not share personalized loader caches across users. GraphQL resolver batching shows the integration point.

Tradeoffs: Large joins can multiply rows and transfer unnecessary data; batches need limits and per-key failure semantics. Request-local deduplication is not a shared cache invalidation strategy. Choose based on query shape and measured execution, not endpoint style.

Interview review: make the endpoint’s guarantees explicit

Describe validation, authorization, status/error semantics, pagination, query cost, transaction scope, and bounded resources. Explain what happens when a write succeeds but its response is lost. Prefer clear application contracts over transport-specific magic.
