Start here: learn design through a complete case

System design connects requirements to a defensible architecture. The goal is to explain how data moves, where correctness is enforced, what limits capacity, and how the system behaves when components fail. Naming technologies is useful only after their responsibilities are clear.

Architecture

First case: Design a chat web app. Work through requirements, estimates, APIs, storage, live delivery, recovery, scaling, and the frontend contract. The proposed system is one reasonable answer under stated assumptions, not a universal chat architecture.

How to study: Sketch your own solution before opening each section. Predict a failure, then compare the recovery path. Revisit the same design after changing one requirement. These are original worked examples using the common requirements → design → deep-dive → tradeoff structure.

Frontend component case: Design an agnostic autocomplete package to practice UI contracts, accessibility, state/async ownership, import boundaries, and a directory layout. Compare its in-process component boundaries with the chat app’s distributed boundaries.

The four-step system design framework

Use these four explicit stages to organize the design discussion. Endpoint/entity discovery starts during clarification; detailed contracts and the blueprint are proposed next, then optimizations follow the critical deep dives. Validation is continuous: restate assumptions and ask for alignment before investing in detail.

Architecture

Working order: clarify requirements and scale, sketch the high-level design, examine the highest-risk components, then review bottlenecks and recovery. Revisit assumptions as constraints change.

Requirements: behavior, quality & explicit limits

Functional requirements describe what users can do. Non-functional requirements describe measurable qualities and constraints. Out of scope states what this design deliberately postpones. All three shape architecture.

Requirements cheat sheet · requirements and scope

Goal: agree on who the system serves, the essential journeys, measurable quality targets and explicit boundaries before drawing architecture. Prioritize questions that change the design.

Architecture
OrderAskWrite down
1 · Goal and actorsWho uses this? What outcome matters most? Which client surfaces: web, mobile, third-party API?One-sentence goal, primary actors and critical journey.
2 · Functional requirementsWhat are the 3–5 essential user actions? What must happen after each action? Which edge cases change the behavior?Actor + action + observable result. Example: selecting a filter updates jobs, categories and facet counts.
3 · ScopeWhich actions are required today, optional if time permits, or explicitly excluded? Which external systems do we integrate with?Must-have / stretch / out-of-scope lists. Scope applies to quality and scale too, not only features.

Functional requirements · what should I ask?

Ask about behavior first, then write the requirement from the answer. Use these as prompts, not a script to read in full.

Ask the stakeholderWhat the answer revealsExample requirement after agreement
“Who are the users, and what is the main task each needs to complete?”Actors, permissions and primary journeys.A job seeker can discover and open relevant job postings.
“Walk me through the main journey. What can the user create, view, change or remove?”Core operations and their observable results.A seeker can choose a category, apply filters and view matching jobs.
“When the user does X, what else must update? Immediately, after Apply, or after a refresh?”Interaction behavior and dependent UI updates.Applying a filter updates listings, categories and facet counts together.
“What do these terms mean here? Can users select multiple values? What counts as a match?”Domain rules that the prompt leaves ambiguous.Selected job types use OR; different facets combine with AND.
“What should happen with no results, invalid input or a failed action? Can users undo or retry?”Required alternate journeys and recovery behavior.An empty search retains removable active filters and offers Clear all.
“Must this work across refreshes, shared links or devices? Are updates live?”Persistence, navigation and synchronization behavior.Applied searches survive refresh and can be shared through the URL.

Write the FR: “[Actor] can [action]; the system produces [observable result], subject to [agreed business rule].” Ask about the user-visible behavior before choosing endpoints or technologies.

Non-functional requirements · what should I ask?

  • Latency: “p95 of which operation, measured from where?” Distinguish API response time from interaction-to-visible-result time.
  • Availability: “What percentage of valid requests must succeed, over what window? What is a usable degraded response?”
  • Consistency and freshness: “Must users immediately see their own writes? Can search lag? Must ordering be global or per entity?” Choose guarantees per operation.
  • Durability and recovery: “Can an acknowledged write be lost? Which failures must we survive? What RPO (acceptable data loss) and RTO (recovery time) are needed?”
  • Security and privacy: “Who may access each resource? Is there sensitive data, tenant isolation or a deletion/retention requirement?”
  • Frontend experience: “Which devices/networks? Keyboard/screen-reader requirements? What should users see while loading, offline, empty or failing?”

Scope · what should I ask?

Ask the stakeholderRecord after the answer
“Which journeys must this design cover? If we can only finish three, which matter most?”In scope: the essential behaviors to design end to end.
“Should I include [adjacent feature], or focus on [core journey]?” Example: job discovery only, or application submission too?Out of scope: named exclusions confirmed with the stakeholder, rather than silently omitted.
“Which features are useful extensions if we have time?”Stretch: optional work, separate from the baseline design.
“Are we designing the frontend, backend/API, or both? Is [external service] already provided?”System boundary: what you own, what you integrate with and the assumed dependency contracts.
“Which clients, regions and workload must we support now? Can offline mode, global deployment or personalization wait?”Limits: the operating envelope and explicit exclusions. Confirm these against the non-functional targets.

Confirm before drawing: “I’ll cover [A, B, C], assume [scale/quality targets], and leave [D, E] out. Does that match your expectations?” Scope is a boundary around the agreed requirements, not a separate type of user feature.

After clarification · agreed job-discovery requirements

  • Goal / actors: job seekers discover relevant open roles on responsive web.
  • Must-have: browse category descendants; apply facets; update categories/counts/results together; paginate and open job details; share applied searches via URL.
  • Quality / scale assumptions: search API p95 ≤300 ms, interaction-to-result p95 ≤500 ms on the target network, 99.9% monthly search availability, 5 million active jobs, about 460 peak search RPS. These are proposed targets, not facts from the prompt.
  • Consistency: all panels represent one applied query; search indexing may lag writes by up to the agreed freshness target. Revalidate current job status on the detail/application boundary.
  • In scope: discovery, taxonomy, faceting and indexing. Stretch: saved searches. Out of scope: submitting applications, employer billing, chat and personalized recommendations.
  • Clarify the ambiguity: “Do facet counts only describe current matches, or show alternatives that could broaden the search?” This changes aggregation semantics.

Common requirements pitfalls

Do not confuse requirements with solutions: “Users see new messages within the latency target” is a requirement; “use Kafka/WebSockets/Redis” is a proposed solution. “Scalable” needs a workload; “strong consistency” needs a specific operation and guarantee. Excluding application submission does not exclude authorization or safe handling of private data in the included features.

Reference: requirement categories and terminology

CategoryChat exampleQuestion to ask
FunctionalSend messages and retrieve history.Direct messages, groups, or public channels?
LatencyTarget p95 online delivery under 300 ms within the chosen region.Does this include client network time?
AvailabilityIllustrative 99.9% monthly successful durable-send availability.Which operation and measurement boundary define success?
DurabilityAcknowledged messages survive the defined failure model.One node, one zone, or an entire region?
ConsistencyCanonical order per conversation; eventual receipts/presence.What happens if ordering cannot be safely assigned?
LimitsBound group size, payload size, retention, and concurrent devices.What workload would invalidate this design?

Terminology: Availability is an observed service outcome over a window, not a synonym for replication. Latency needs a percentile and boundary. Consistency describes observable data guarantees; it is separate from durability. During a network partition, CAP concerns the tradeoff between linearizable consistency and availability in its formal sense; it does not mean every system always “chooses two of three.”

Components: choose a role before choosing a product

A component earns its place by solving a specific pressure. The same product may fill several roles; separating responsibilities on a diagram does not require deploying a microservice for each box.

ArchitectureAPI integration
RoleWhat it solvesLimit or alternative
Load balancer / reverse proxyRoutes traffic to healthy instances; can terminate TLS.Does not own conversation data or guarantee delivery.
Application serviceValidates requests, authorizes resources, applies business rules.Start as modules in one service when that is enough.
DatabaseDurable authoritative state and transactional invariants.Choose by access pattern and correctness; indexes and replicas have costs.
CacheAvoids repeated expensive reads.Define keys, TTL, invalidation, and acceptable staleness; never assume it is authoritative.
QueueDistributes work among competing consumers.Retries and redelivery require idempotent effects.
Topic / event streamLets independent consumer groups process the same event history.A Kafka partition orders its records; it does not globally order a whole topic.
Object storage + CDNStores large immutable objects and serves them near users.CDNs do not replace authorization or live message persistence.
Coordination / leaseTemporary ownership and recovery when owners fail.A lease alone does not stop stale writes; enforce fencing where needed.

Existing foundations: Reuse HTTP caching, database transactions, and leases and sweepers. The chat case demonstrates why and where to combine them.

UI solutions: start from journeys and visible states

For fullstack application design, connect architecture to a concrete user journey. Define what the user sees before, during, and after each operation—including slow, disconnected, empty, partial, unauthorized, and failed states.

ArchitectureReactAccessibility
DecisionQuestionTradeoff
Rendering and navigationWhat must appear immediately? What needs SEO, streaming, or persistent layouts?SSR can improve initial delivery but adds server/hydration complexity; client transitions need data/focus/scroll ownership.
State ownershipWhich values belong in the URL, local state, or server cache?Duplicated owners create synchronization bugs; normalized state adds indirection.
Interaction feedbackCan an action be optimistic? Can it be reversed?Fast feedback helps UX; an irreversible operation needs a truthful pending/confirmed contract.
Data volumePagination, virtualization, or both?Pagination bounds transfer; virtualization bounds DOM work and complicates scroll/accessibility.
Accessibility and devicesHow do keyboard, screen reader, mobile, and slow-network users complete the task?Avoid a mouse-only happy path or desktop-only assumptions.

Design summary: Sketch the main screen, an interaction sequence, and the state transitions. Tie each to an API and data owner. Use the chat UX state matrix, then reference rendering choices, state ownership, and accessibility verification.

Compare implementations: Use the same UI problem under different state tools and the checkout pattern comparison to explain why a chosen architecture earns its complexity.

RESTful contracts: entities, methods, errors & idempotency

RESTful resource design starts with domain entities and lifecycle operations. Resource-oriented URLs and HTTP semantics make a contract predictable; using JSON over HTTP alone does not establish all REST constraints. Choose a practical contract and be precise about its guarantees.

HTTPAPI integrationResilience
ConcernDecision to explain
ResourcesIdentify collections, resource IDs, relationships, and ownership; avoid leaking database tables as the API by default.
MethodsGET reads without intentional state changes; POST commonly creates/processes; PUT replaces a target representation; PATCH partially modifies; DELETE removes a resource association according to the contract.
OutcomesUse meaningful 2xx/4xx/5xx statuses, validation codes, pagination cursors, rate-limit guidance, and a consistent error body.
RetriesPUT/DELETE are idempotent in intended effect, though responses may differ; POST/PATCH are not inherently idempotent. Define application deduplication when needed.
ConcurrencyUse a version or ETag/If-Match where stale updates must be rejected; idempotency keys address repeated operations, not conflicting independent operations.
SecurityAuthenticate the caller and authorize each resource; validate bounds and never trust client-owned prices, identities, or roles.

Idempotency-key contract: Scope a stable key to the authenticated principal and operation, fingerprint the relevant payload, and atomically reserve/store its outcome with the business mutation. Define in-progress retries, conflicting reuse, retention, and recovery after a crash. A cached HTTP response written after the side effect leaves a dangerous failure window. For external effects, use the dependency’s idempotency contract or reconcile.

Alternatives: REST fits stable resource operations and standard HTTP infrastructure. GraphQL can suit varied client query shapes; RPC can express commands naturally. WebSocket messages still need schemas, authorization, correlation, retry, and error contracts. See HTTP semantics, GraphQL comparisons, and the chat REST surface.

Architecture: modular services, load balancing & scale

Draw logical responsibilities before deciding deployment boundaries. Start with a modular monolith when one team and one deployment can meet the needs. Choose microservices when independent scaling, ownership, isolation, or release cadence justifies distributed-system costs.

ArchitecturePerformanceResilience
ChoiceBenefitCost / caution
Modular monolithLocal calls and simpler transactions, deployment, debugging.Scaling/releasing the whole unit can couple teams and resources.
MicroservicesIndependent deployment, domain ownership, and targeted resource scaling.Network failures, API/version compatibility, observability, deployment overhead, and cross-service consistency become explicit work.
Horizontal scalingAdds instances to distribute load and survive instance failure.Shared state, hot keys, database limits, and coordination may still bottleneck.
Load balancingRoutes eligible traffic to healthy instances.Choose L4/L7 needs, health/readiness checks, timeout policy, and zone capacity; sticky sessions can cause skew.
Async workBuffers bursts and decouples slow consumers.Adds backlog latency, retries, deduplication, and eventual outcomes.

Load-balancing decisions: Round-robin is simple; least-connections can help unequal long-lived connection counts, but neither guarantees equal CPU or message fanout. Health checks should separate liveness from readiness; removing a draining instance from new traffic does not finish existing work. Autoscale on a useful saturation signal and keep failure headroom, not just average CPU.

Service boundaries: Keep one owner for an invariant where possible. If a write crosses services, define the workflow, compensation/reconciliation, and idempotency rather than assuming a distributed transaction exists. A circuit breaker isolates repeated dependency failures; it does not create a correct fallback. See application boundaries and chat deployment choices.

Consistency: specify guarantees per operation

A design should name the observable guarantee for each operation. “Strong” and “eventual” are starting labels; explain what a client may see after concurrent writes, replica lag, retries, and failover.

ConcurrencyArchitectureResilience
Guarantee / mechanismMeaningCost or limit
LinearizabilityEach operation appears atomic at a point between its call and response, respecting real-time order.Requires coordination; latency or availability may suffer during partitions.
Read-your-writesA client can observe its own acknowledged mutation.Can use writer reads or consistency tokens; does not imply global linearizability.
Eventual consistencyReplicas converge if updates stop and propagation succeeds.Stale reads/conflicts need policy; no finite staleness bound follows automatically.
Monotonic reads / cursorsA session does not move backward in the relevant observed version.Needs version-aware routing/merging; a timestamp alone may be insufficient.
Optimistic concurrency controlReject a write whose expected version is no longer current.Callers must merge or retry intentionally; it does not deduplicate repeated effects.

Distinguish: Transaction isolation describes concurrent transaction behavior; durability describes committed data survival; delivery semantics describe message handling. Neither a replica count nor an “exactly once” slogan defines all three. State the failure model, write acknowledgement rule, replication mode, and RPO/RTO.

Use selectively: A permission revocation or account balance may need authoritative checks, while typing indicators can tolerate staleness. Explain the product consequence of each relaxation. Apply this to conversation ordering and replica reads, and reuse optimistic concurrency choices.

Caching and CDNs: place, key, freshness & failure

A cache strategy specifies what is cached, where it lives, who owns the source of truth, and how stale or missing data is handled. A cache hit improves a specific path; it is not automatically a correctness guarantee.

StorageHTTPPerformance
Strategy / locationUse whenTradeoff
Browser/query cacheReuse UI data, deduplicate requests, keep interactions responsive.Clear personalized data on logout; coordinate invalidation and optimistic updates.
Cache-aside at the serviceRead-heavy data can tolerate a defined freshness policy.Misses still hit the database; invalidation/refill races can reintroduce stale data.
Read-through / write-throughA cache layer owns loading or synchronously coordinates writes.Adds layer coupling and failure handling; persistence atomicity must be specified.
Write-behindDelayed writes are acceptable under a durable buffering contract.Volatile buffering risks data loss; inappropriate for pretending unpersisted messages are accepted.
CDN/edge cacheVersioned frontend assets and approved static/media content.Cache keys, access checks, purge behavior, and origin protection matter.

Key and freshness: Include relevant tenant/user scope, resource version, locale, filters, and permission context; avoid secrets in keys/logs. Define TTL, event-driven invalidation or versioning, and whether stale-while-revalidate or stale-if-error is acceptable. A delayed refill can overwrite newer cache data; use version-aware updates where correctness requires it. Coalesce concurrent misses and jitter expiry to reduce cache stampedes.

CDN policy: Content-hashed JS/CSS can use long freshness and immutable caching, while the HTML entry point needs a compatible update/revalidation policy. Private API/message data should not enter a public shared cache. Signed media URLs need validated expiry/access at the appropriate layer and a deliberate cache key; URL signing alone does not make every shared-cache configuration safe.

Failure: Bypassing a failed cache can overload the origin—bound concurrency and shed load. Stale content may be fine for a past message display but unsafe for membership authorization. See HTTP validators/cache directives, chat cache placement, and CDN behavior.

Observe errors, monitor outcomes & define fallbacks

Monitoring checks known signals and thresholds; observability helps explain system behavior using metrics, logs, traces, and events. A dashboard is useful only if it connects to a user outcome, a diagnosis, and an action.

ResiliencePerformanceArchitecture
SignalPurposeDesign consideration
Metrics / SLIsRates, latency distributions, availability, saturation, queue age.Use bounded labels; request IDs/user IDs create high-cardinality metric problems.
Structured logsExplain a specific failure or state transition.Include safe codes, trace/correlation IDs, versions; redact credentials and sensitive bodies.
Distributed tracesFollow timing and dependencies through an operation.Propagate context across HTTP, sockets, and async jobs; choose sampling and privacy policies.
Frontend error reporting / RUMCapture render exceptions, rejected operations, failed assets, and real user latency.Use release/source-map context, deduplication, and consent/privacy rules; handled failures need explicit reports.
Synthetic checksExercise login, load history, and send through an end-to-end probe.A health endpoint cannot prove a full journey works; bound test side effects.

Alerting: Define SLOs with a denominator, eligible population, time window, and latency threshold. Alert on sustained/multi-window error-budget burn or loss of critical durability, not every individual error. Include owner, runbook, recent deploy context, and the first diagnostic queries.

Fallback contract: For each dependency, document timeout, retry budget, circuit-breaker policy if useful, degraded UI, recovery path, and what must never be claimed. Serve explicitly stale read data when permitted; disable optional presence; keep uncertain sends pending. Never fabricate success or silently weaken authorization. See chat error diagnosis and fallback decisions.

Practice with requirement changes

After the baseline chat design, change one assumption and identify what breaks before proposing another technology.

Architecture
  • 100,000-member channels: revisit fanout, hot partitions, membership reads, and retention.
  • Active users across continents: revisit home regions, write ownership, replication lag, failover, and latency.
  • End-to-end encryption: revisit key distribution, device membership, recovery, search, and moderation.
  • Images and attachments: introduce signed upload/download URLs, malware scanning, object storage, and CDN caching rules.

Self-check: Can you explain one message from send to persistence to display, then recover it after a gateway crash? If not, refine that path before expanding the architecture. Continue to the worked chat case.
