Navigation models: document loads vs. client transitions

Document navigation asks the browser to load a document. Client-side routing updates the URL and rendered route within the current document. A hybrid framework can serve the initial HTML, then perform client transitions; routing is distinct from CSR/SSR rendering choices.

BrowserArchitecture

Use: Client transitions support persistent layouts, local interaction state, and route-level loading. Document navigation is simpler for independent pages and provides native loading/history behavior. Both need valid URLs, authorization, accessible navigation, and a working direct-load path.

Contract: Preserve real anchors for destinations and buttons for actions. A router may intercept an eligible same-origin click, but must preserve modified clicks, downloads, target behavior, and external destinations. On a static SPA host, deep links need an appropriate fallback; avoid turning asset failures or real 404s into misleading HTML success responses.

State ownership: Paths identify resources; query parameters represent shareable view state. Keep one authoritative owner and validate parsed values using the existing URL-state model.

History API: push, replace & back/forward

The History API manages same-document history entries. pushState adds an entry; replaceState changes the current entry. Neither dispatches popstate immediately. Back/forward traversal between relevant history entries can dispatch popstate, which a client router uses to restore the route.

BrowserState management
function renderRoute() {
  const url = new URL(location.href);
  console.log('Render route:', url.pathname, url.searchParams.get('tab'));
}
function navigate(path, { replace = false } = {}) {
  const url = new URL(path, location.href);
  if (url.origin !== location.origin) throw new Error('Same-origin routes only');
  history[replace ? 'replaceState' : 'pushState'](null, '', url);
  renderRoute(); // pushState does not emit popstate
}
window.addEventListener('popstate', renderRoute);
// navigate('/orders?tab=open'); // Adds a history entry
// navigate('/orders?tab=all', { replace: true });

Choose: Push for a meaningful destination the user should return from. Replace for canonicalization, redirects, or intermediate edits that should not flood history. History state is structured-serializable metadata, not a durable database or a suitable place for large sensitive payloads.

Use a router: This example illustrates the primitive; it omits route matching, cancellation, focus, loaders, and blockers. Use an established router/framework for application navigation. Hash routing can work without server fallback, but has URL and fragment-navigation tradeoffs.

Nested routes: layout, data & error ownership

Nested routes express a hierarchy of URL segments and UI ownership: an orders layout can persist while its list or detail outlet changes. A layout route may group UI without adding a path segment. Nest routes when they share a lifecycle, not merely because their components are visually adjacent.

ReactArchitectureResilience

Example: /orders/:orderId owns the selected order’s loader and detail error boundary; its parent owns navigation and the list layout. A failed detail request should show a local recovery state while preserving useful navigation.

Loading: Independent parent/child requests should start in parallel when supported. Await a parent only for a real dependency such as a required identifier. Avoid fetching everything in nested mount effects, which can create waterfalls; see performance techniques.

Error boundaries: Router loader/action errors and React render errors have related but distinct interception mechanisms. React boundaries do not catch every async rejection or event-handler exception; routers can integrate loader failures into route boundaries. Place retry UI at the owner of the failed operation; see rendering failure isolation.

Security: Client route guards improve UX but cannot enforce permissions. Loaders, mutations, and APIs must validate identity and resource authorization on the server.

Navigation data: cancellation, prefetching & revalidation

A navigation has a data lifecycle: start the needed work, show useful pending UI, commit the winning result, and handle failure or cancellation. Separate the route’s current location from a pending destination so stale completions cannot replace newer navigation.

API integrationState managementPerformance

Example: The user opens order A and immediately switches to B. Pass the router-provided AbortSignal to fetch where available; ignore A’s obsolete result even if cancellation arrives too late. fetch abort does not guarantee that the server stopped processing. See AbortController.

Prefetch: Fetch route code or data on strong intent, such as focus/hover, or for likely destinations. Balance latency savings against bandwidth, authorization-sensitive cache contents, and wasted work. Avoid prefetching mutations or URLs that incorrectly cause side effects.

Cache ownership: Coordinate router loaders with an existing query cache rather than creating two independent stale copies. After a mutation, invalidate/revalidate the authoritative data according to the framework contract. Deduplicate overlapping loads and retain a policy for back/forward restoration; see server-state lifecycle.

Scroll, focus & announcements after navigation

Same-document navigation does not automatically reproduce a document load’s accessibility behavior. Define focus management, document title updates, route announcements, and scroll restoration as part of the router contract.

AccessibilityBrowser
  • New destination: after the winning route commits, update the title and usually focus a meaningful heading or main region using tabindex=-1. Avoid stealing focus for background refreshes.
  • Fragment navigation: reveal the target and account for sticky-header offsets; move focus when needed for keyboard orientation.
  • Back/forward: restore a meaningful history position rather than always scrolling to the top. Wait until content/layout can support that position.
  • Announcements: use a restrained live-region message if the transition otherwise lacks a clear announcement; avoid duplicate announcements from focus and live regions.

Implementation: Prefer your router’s restoration facilities; if using history.scrollRestoration='manual', the application owns restoration and must handle images, deferred data, and virtualized lists. Test keyboard and screen-reader journeys using focus foundations.

Unsaved changes: blockers, drafts & submission races

An unsaved-change guard protects a dirty draft during navigation. Dirty means the current draft differs from its saved baseline, not merely that the user has focused a field. Update the baseline after a confirmed save; preserve the draft on failure.

FormsResource lifecycleResilience

Use: A router blocker for internal transitions with a real risk of losing work. It should explain the loss, offer stay/discard choices, and resume exactly the blocked transition after confirmation. Do not mutate history repeatedly to trap the user.

External exits: Attach beforeunload only while genuinely dirty. Browsers control the warning text and may require prior interaction; the event is unreliable on some mobile termination paths and can affect back/forward caching in some browsers. Use draft persistence or autosave where appropriate rather than treating the prompt as a guarantee.

Submission races: A pending save is not a successful save. Define whether navigation waits, cancels local work, or lets server processing continue. Protect duplicate submissions with the server’s idempotency policy, and handle failures after the user leaves. See form submission contracts and server snapshots and drafts.
