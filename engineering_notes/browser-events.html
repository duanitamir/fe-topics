Event loop & scheduling

Execution order in the browser

  1. Run the current task’s synchronous code until it finishes. Calling an async function also runs its body synchronously up to its first await.
  2. Drain microtasks in enqueue order: Promise .then()/.catch()/.finally() callbacks, ready await continuations, and queueMicrotask(). Keep running newly queued microtasks until the queue is empty.
  3. If a rendering opportunity is due: run requestAnimationFrame() callbacks before painting the frame. Rendering is not guaranteed between every pair of tasks.
  4. Run the next eligible task (for example, a timer or user-input task), then repeat the microtask checkpoint and rendering check.

Remember: synchronous code → all queued microtasks → possible rendering → next task. A Promise callback has no special priority over queueMicrotask(); whichever is enqueued first runs first. There is no guaranteed order between a zero-delay timer and requestAnimationFrame() across all scheduling conditions.

The browser coordinates JavaScript execution, input, and rendering through the event loop. JavaScript on a given main thread runs to completion: a handler cannot be interrupted by another handler halfway through its synchronous work.

BrowserConcurrencyPerformance
  • Tasks (often called macrotasks): Include timer callbacks and event dispatch for user interactions. There are multiple task queues; do not assume one global FIFO order across all task sources.
  • Microtasks: Include Promise reactions, continuations after await, and queueMicrotask() callbacks. At a microtask checkpoint, the browser drains the queue, including newly added microtasks, before continuing. An endless chain causes microtask starvation, delaying input and rendering.
  • Rendering opportunities: The browser may update rendering between tasks when a frame is due. It does not paint after every task. requestAnimationFrame() callbacks run before the associated rendering update paints, making them suitable for visual updates; heavy callback work still delays the frame.
  • Timers are not deadlines: setTimeout(fn, 0) schedules a future task after an applicable minimum delay; current work, microtasks, and throttling can postpone it. It neither executes immediately nor guarantees a paint first.
console.log('A');
setTimeout(() => console.log('timer'), 0);
Promise.resolve().then(() => console.log('promise'));
queueMicrotask(() => console.log('microtask'));
console.log('B');

// For this standalone example:
// A → B → promise → microtask → timer

Output: A → B → promise → microtask → timer. A and B are synchronous. The Promise callback is enqueued before the explicit microtask. Both run before the timer task.

Practical diagnosis: If typing is delayed while a large filter runs, changing an event handler to async does not move the calculation off the main thread. await Promise.resolve() only yields to microtasks, not to a rendering opportunity. Split work and yield via a task boundary, such as scheduler.yield() where supported, or move suitable computation to a Web Worker. See long tasks and execution measurement.

For promise composition, rejection propagation, and bounded parallel requests, see Promises and asynchronous programming. The event loop explains scheduling; combinators define outcome policy.

For server-specific runtime resources rather than DOM scheduling, see libuv thread-pool contention and worker threads.

Event propagation, bubbling & delegation

Propagation

How the event travels through the DOM tree.

Bubbling

The phase in which an event travels upward from its target toward ancestors.

Delegation

Where we choose to handle the event: at a common ancestor rather than each child.

Event propagation

Browser

Event propagation describes the path a DOM event takes. For a typical click, it has three phases: capturing (ancestors down toward the target), target (the element where the event occurred), and bubbling (back up through ancestors). Not every event bubbles.

Event bubbling

Browser

When a user clicks a nested element, a bubbling click can be observed by listeners on its ancestors. For example, a click on a <button> can also reach its enclosing <li> and <ul>. Propagation control is separate from default-action cancellation; see Default actions & cancellation for the precise method contracts.

Event delegation

Browser

Delegation is the intentional use of propagation to centralize event handling. We attach a listener to a parent, inspect event.target, and use a selector such as closest() to identify the relevant descendant. It is especially helpful for dynamic lists and plain DOM code.

Example

<ul id="products">
  <li data-id="1"><button>Buy iPhone</button></li>
  <li data-id="2"><button>Buy MacBook</button></li>
</ul>

<script>
  const products = document.querySelector("#products");

  products.addEventListener("click", event => {
    const item = event.target.closest("li[data-id]");
    if (!item || !products.contains(item)) return;

    console.log("Clicked product:", item.dataset.id);
  });
</script>

Why closest()? The actual clicked element may be a button or a nested span. closest("li[data-id]") walks from that element toward its ancestors to find the nearest product row. event.target identifies the target visible to this listener (Shadow DOM retargeting can change it); event.currentTarget is the element whose listener is executing (here, the ul).

React connection: Hydration connects server-rendered interactive UI to client-side React logic. React already uses delegated handling internally for many events, so ordinary onClick handlers on individual React elements are fine. You still need to understand propagation, event.target vs. event.currentTarget, and stopPropagation().

Key distinction: Propagation is the browser mechanism. Bubbling is one propagation phase. Delegation is the technique built on top of it, usually using bubbling, although capture-based delegation is also possible.

Default actions & cancellation

Default actions are browser behaviors associated with events, such as following a link or submitting a form. They are distinct from listener execution and event propagation.

Browser
MethodEffectDoes not do
preventDefault()Cancels the default action if the event is cancelable and the listener is not passive.Stop propagation or other listeners.
stopPropagation()Stops further propagation along the event path.Cancel default actions or stop other listeners on the current target.
stopImmediatePropagation()Also stops remaining listeners on the current target.Cancel the default action.
form.addEventListener('submit', event => {
  event.preventDefault(); // Handle submission without native navigation.
  saveForm(new FormData(form));
});
  • Check the contract: event.cancelable tells whether cancellation is supported; event.defaultPrevented records successful cancellation. Calling preventDefault() after an await can be too late; cancel synchronously during dispatch when you need to take over the action.
  • Passive listeners: { passive: true } promises not to cancel the default action, allowing the browser to proceed without waiting for a cancellation decision on scroll-blocking events. It does not make handler work faster. A genuinely canceling listener needs passive: false; use it only when necessary.
  • Preserve native behavior: Broad propagation blocking can break ancestor controls and analytics. Intercept only the action you own; custom link handling should preserve modified clicks and opening new tabs.

Listener lifecycle & resource ownership

Register listeners when their owner becomes active and remove them when it is disposed. Listeners attached to long-lived targets such as window can retain stale closures and component data after the UI disappears.

Design patternBrowserResource lifecycle
  • capture: Selects capture-phase registration; removal must match the same capture flag.
  • once: Removes the listener after its first invocation. If the event never arrives, explicit teardown may still be required.
  • passive: Declares that the listener will not cancel the default action; choose it according to the behavior described above.
  • signal: Associates listener lifetime with an AbortSignal. Aborting its controller removes all listeners registered with that signal. See the AbortSignal cancellation contract.
function mountPanel(panel) {
  const controller = new AbortController();
  const { signal } = controller;

  panel.addEventListener('click', handlePanelClick, { signal });
  window.addEventListener('resize', updatePanelLayout, { signal });

  return () => controller.abort(); // Call when the panel is disposed.
}

Callback identity matters: removeEventListener(type, callback, capture) must receive the original function reference, event type, and matching capture flag. A fresh arrow function or a new bind() result will not remove the original listener. The options object itself need not be the same object; passive and once are not removal-matching keys.

React integration: Install native subscriptions in an effect and return cleanup; the effect dependency and timing rules explain when re-synchronization occurs. Include reactive dependencies to avoid stale closures; recreating the subscription when dependencies change is valid. Make cleanup safe for StrictMode’s development setup/cleanup replay. See AbortController lifecycle for signal reuse and cancellation limits.

Resource ownership & disposal as a general pattern

Design patternResource lifecycle

Purpose: Pair acquisition with release at the same ownership boundary. Subscriptions, observers, timers, workers, and connections should not outlive the feature that owns them. This is explicit resource management; it resembles RAII’s ownership discipline, but JavaScript garbage collection does not provide deterministic cleanup of external resources.

Example: A chart component creates a ResizeObserver, subscribes to store updates, and starts a refresh timer in its effect. Cleanup disconnects the observer, unsubscribes, and clears the timer; a shared application connection instead belongs to a longer-lived service, not each chart.

Use when: Setup registers future work or retains a resource. Return a disposer, use try/finally for bounded imperative work, or use an effect cleanup for React synchronization. If setup partially fails, release resources already acquired. Cleanup should tolerate the lifecycle’s repeated setup/teardown.

Benefits and tradeoffs: Prevents leaks, duplicate notifications, and stale writes. Cleanup alone does not undo a completed server operation; combine it with cooperative cancellation and stale-result guards.

When not to use: Pure calculations and derived values need no disposal effect. Do not add an effect just to calculate data; see derived state. A finalizer is not a reliable substitute for explicit release. Effect dependencies define resynchronization; subscription contracts define what unsubscribe must stop.

When delegation breaks inside a web component

Symptom: An ancestor listens for a click and calls event.target.closest('button'), but cannot find a button inside a custom element’s shadow tree.

Browser
  • Event retargeting: Outside the shadow boundary, event.target typically points to the custom-element host rather than its internal button. closest() does not traverse from a host into its shadow tree.
  • bubbles vs. composed: Bubbling controls upward propagation; composition controls crossing shadow boundaries. A bubbling custom event still stays inside its shadow tree unless it is composed. Native click events are normally both bubbling and composed.
  • composedPath(): Inspect the event path during dispatch when diagnosing an open shadow root. Closed-root internals are hidden from outside observers. Depending on internal button selectors creates a fragile coupling even when it works.

Prefer a public semantic event: Let the component handle its internal DOM and emit an event such as product-selected with a documented payload. Consumers depend on the component’s public behavior rather than its markup.

// Inside the component's shadow-root click handler:
button.dispatchEvent(new CustomEvent('product-selected', {
  detail: { productId },
  bubbles: true,
  composed: true
}));

// Outside: delegate on the public event, not the internal button.
productList.addEventListener('product-selected', event => {
  selectProduct(event.detail.productId);
});

Custom-event contract: CustomEvent defaults to bubbles: false, composed: false, and cancelable: false. Opt into each deliberately. If the component supports a cancelable action, set cancelable: true and check dispatchEvent()’s return value before performing that action. Only expose payload data that belongs in the public API.

Review: event delegation

Event delegation is a pattern built on top of DOM event propagation. Instead of registering event listeners on multiple child elements, we register a single listener on their common ancestor. When an event occurs on a child, it bubbles up to the ancestor, where we can identify the original target and handle the event accordingly. This reduces the need for individual listeners and also works for dynamically added children.
