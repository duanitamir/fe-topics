Foundations

Choose a pattern by the pressure it resolves

Design patterns describe recurring solutions and their tradeoffs. Architectural patterns organize larger boundaries; principles guide decisions. Use the smallest mechanism that makes ownership, behavior, and failure handling explicit. A function or module is often enough; naming a pattern does not require classes or a framework.

PressureStart withRelated alternative
Interchangeable algorithmsStrategyA direct conditional for a small fixed choice.
Mismatched external contractAdapterUse the original API directly when its coupling is acceptable.
Hard-coded dependenciesDependency injectionDirect imports for stable, pure helpers.
A complicated subsystemFacadeDirect calls when the workflow is already simple.
Business rules coupled to infrastructurePorts and adaptersModules with explicit boundaries for small applications.
Client-specific API compositionBFFA shared API or framework server route when sufficient.
Risky replacementStrangler Fig / branch by abstractionA direct replacement for small, easily verified changes.
Dependency failures spreadingCircuit breaker / bulkheadTimeouts and bounded concurrency as a baseline.
Abandoned background workLease + recovery scanManaged queue visibility timeout/redelivery, or a short transaction for database-only work.
Multi-service workflow with partial failureSagaA single database transaction when all changes share one transactional boundary.
Different models for writes and readsCQRSOne CRUD model with indexes/views when sufficient.
Database read capacity / standby failoverPrimary/replica replicationQuery/index tuning first; assess staleness and recovery requirements.

For messages and state transitions, use the existing commands, events, and actions, unidirectional data flow, and state-machine sections. This page focuses on application code and integration boundaries.

SOLID: principles for code that can change

SOLID is five design principles for reducing coupling and making changes safer. They originated in object-oriented design; their ideas also apply to functions, modules and React components. They guide decisions rather than requiring classes, microservices or a pattern for every function.

Architecture

Each principle below combines its meaning, a common use and a minimal before/after example.

Read each pair as one small refactoring, not a requirement to add abstractions everywhere.

Each pair is an independent illustration: before shows the coupling or broken contract; after shows the smallest useful change. Keep these abstractions only where they solve a real change pressure.

S · Single Responsibility Principle

A module has one cohesive responsibility—one reason to change.

Common use: A checkout form renders inputs; a payment adapter handles provider-specific integration. Changing the provider should not require rewriting field markup.

Before

function receipt(items) {
  const total = items.reduce((sum, item) => sum + item.price, 0);
  return `Total: ${total}`;
}

After

const totalPrice = items => items.reduce((sum, item) => sum + item.price, 0);
const formatReceipt = total => `Total: ${total}`;
const receipt = items => formatReceipt(totalPrice(items));

What improved: Calculation and formatting have different reasons to change. The composing function may call both; SRP does not forbid orchestration. For a tiny stable helper, the original can be sufficient.

Single responsibility is not one function per file. Several functions can serve one cohesive responsibility.

O · Open/Closed Principle

Support expected variations by extending behavior without repeatedly changing stable core logic.

Common use: A product sorter accepts a ranking function. Add a new ranking Strategy without changing the sorter.

Before

function rank(items, mode) {
  return [...items].sort(mode === 'price'
    ? (a, b) => a.price - b.price : (a, b) => b.rating - a.rating);
}

After

const rank = (items, compare) => [...items].sort(compare);
const byPrice = (a, b) => a.price - b.price;
rank(products, byPrice);

What improved: A new ranking supplies another comparator; the sorting workflow stays unchanged. products is caller-supplied data.

Open/closed does not forbid editing code. Add extension points for real variation, not speculative future possibilities.

L · Liskov Substitution Principle

A replacement implementation must honor its abstraction’s behavioral contract: do not strengthen preconditions or weaken promised outcomes.

Common use: If storage.save() promises persistence before resolving, an adapter that resolves after only buffering in memory is not a valid substitute. Matching TypeScript signatures is insufficient.

Before

// Behavioral contract: return ascending values; leave input unchanged.
// This signature alone does NOT express the non-mutation promise.
type Sorter = (items: number[]) => number[];
const sort: Sorter = items => items.sort((a, b) => a - b);

const original = [3, 1, 2];
const sorted = sort(original);
// sorted: [1, 2, 3] — correct.
// original: [1, 2, 3] — WRONG: the caller expected [3, 1, 2].

After

// Same behavioral contract and type; safe for the same caller.
type Sorter = (items: number[]) => number[];
const sort: Sorter = items => [...items].sort((a, b) => a - b);

const original = [3, 1, 2];
const sorted = sort(original);
// sorted: [1, 2, 3]; original: [3, 1, 2] — both promises honored.

What improved: a caller may need both the original order and a sorted view. The first implementation breaks that caller’s assumption; the second can replace any sorter promising to preserve the input. That substitutability is the Liskov connection. Mutation alone is not a violation: without the non-mutation promise, the first implementation could be valid. Copying also costs an extra array allocation.

Liskov is about behavior, not just types. Errors, accepted inputs and side effects must preserve the documented contract.

Make the contract more explicit: accept readonly number[] instead of number[]. TypeScript then rejects calling the mutating items.sort() through that parameter. Sorting a copy still works; modern JavaScript also offers items.toSorted(). Readonly is a compile-time restriction, not a runtime freeze.

I · Interface Segregation Principle

Consumers should not depend on capabilities they do not need.

Common use: A search feature depends on a SearchClient contract, rather than a large platform-service interface including billing and administration.

Before

type PlatformApi = {
  search(q: string): Promise<string[]>;
  deleteUser(id: string): Promise<void>;
};
const find = (api: PlatformApi, q: string) => api.search(q);

After

type SearchApi = { search(q: string): Promise<string[]> };
const find = (api: SearchApi, q: string) => api.search(q);

What improved: The search consumer and its test doubles no longer need an unrelated administration capability. A larger platform client can still satisfy the smaller contract.

Interface segregation is not splitting every method into its own interface. Group capabilities around consumer needs.

D · Dependency Inversion Principle

High-level policy and low-level details depend on abstractions; infrastructure implements contracts shaped by the business needs.

Common use: PlaceOrder depends on a PaymentGateway port. A Stripe adapter implements it; order logic does not import the Stripe SDK. See ports and adapters.

Before

// Illustrative vendor SDK, configured elsewhere.
import { provider } from './vendor-sdk';
const pay = (amountMinor: number) =>
  provider.charges.create({ amount_cents: amountMinor });

After

type PaymentGateway = { charge(amountMinor: number): Promise<void> };
const pay = (gateway: PaymentGateway, amount: number) => gateway.charge(amount);
// Infrastructure adapter translates the vendor API into the app-owned port.
const gateway: PaymentGateway = {
  charge: async amount => { await provider.charges.create({ amount_cents: amount }); },
};
await pay(gateway, 1000);

What improved: The application owns PaymentGateway; infrastructure implements it. Supplying gateway is dependency injection. The SDK API is illustrative, and the after snippet assumes the adapter module imports the configured provider.

Dependency inversion differs from dependency injection. Inversion defines the dependency direction; injection supplies the implementation. Injecting a concrete vendor client alone does not establish a business-owned abstraction.

Applying SOLID in practice

Frontend connection: a headless hook can separate interaction behavior from presentation (S); a render strategy can support extension (O). A component replacement must preserve its accessibility and callback contract (L). Use composition and headless APIs where that flexibility is useful, rather than forcing class inheritance.

Explanation: “I apply SOLID to concrete change pressures: separate responsibilities that change independently, provide extension points where variation exists, preserve behavioral contracts, keep consumer interfaces focused and protect business policy from infrastructure details.”

When not to add abstractions: stable pure helpers and small local workflows often need only direct functions. Strategy supports O, focused ports support I and ports/adapters supports D, but using those patterns does not automatically satisfy all five principles.

DRY: one authoritative definition per rule

DRY (Don’t Repeat Yourself) means avoiding multiple independent definitions of the same knowledge or business rule. The goal is that a policy change has one authoritative place to update—not that every similar line of code must become a shared helper.

Architecture

Common use: one shipping policy, two screens

The cart and checkout display the same delivery fee. If each owns a copy of the rule, changing the free-shipping threshold can make them disagree. This simplified example assumes one currency, region and delivery method; amounts are in minor units.

Before

const cartShipping = subtotal => subtotal >= 5000 ? 0 : 499;
const checkoutShipping = subtotal => subtotal >= 5000 ? 0 : 499;
// A policy change must be repeated in both places.

After

const shippingFee = subtotal => subtotal >= 5000 ? 0 : 499;
const cartShipping = shippingFee(cartSubtotal);
const checkoutShipping = shippingFee(checkoutSubtotal);

What improved: both screens use the same policy function. A threshold change has one definition to update. The two subtotal values come from their respective screens.

When should I extract shared code?

Extract when the copies express the same rule and should change together. Common candidates include pricing rules, canonical validation schemas and generated API contracts. In React, a custom hook can share repeated behavior and cleanup; each call still has its own state. See custom hook contracts.

When similar code should stay separate

An account display name and a delivery instruction may both start with “non-empty text” validation, but they represent different rules and may evolve independently. Sharing a validator only because the code currently looks alike creates accidental coupling. A shared helper that accumulates flags for every caller is a signal to reconsider the abstraction.

Frontend/server distinction: checking a field in the browser and validating it again on the server is necessary enforcement at two trust boundaries. Share an appropriate schema where useful, but never remove server validation to avoid duplication. Likewise, shared frontend shipping calculations are previews; the server must determine the authoritative charge.

Relationship to SOLID: DRY centralizes one rule; Single Responsibility separates rules that change for different reasons. Extracting every similar block into one generic module can work against that separation.

Rule of thumb: “Would these copies need to change together for the same business reason? If yes, consider one shared definition. If not, similar code may be safer than the wrong abstraction.”

Code-level patterns

Strategy: make a behavior interchangeable

Purpose: Encapsulate alternative algorithms behind one contract. The caller chooses a strategy without knowing its implementation. In JavaScript, an injected function is often simpler than a class hierarchy.

Design patternArchitecture

Use when: A product list supports several ranking policies, or an export feature supports different formatters. Each policy varies independently of the calling workflow.

type Product = { price: number; rating: number };
type Ranking = (a: Product, b: Product) => number;
const byPrice: Ranking = (a, b) => a.price - b.price;
const byRating: Ranking = (a, b) => b.rating - a.rating;
function rank(products: Product[], strategy: Ranking) {
  return [...products].sort(strategy); // Preserve caller-owned data.
}
const ranked = rank([{ price: 20, rating: 4 }, { price: 10, rating: 3 }], byPrice);

Benefits and tradeoffs: Policies are independently testable and replaceable, but extra indirection makes a tiny workflow harder to follow. Strategies must honor the same semantics, including mutation, errors, and ordering guarantees.

When not to use: For one stable algorithm or two trivial local branches, use a function or conditional. A data lookup table suits constants; Strategy suits executable behavior.

Compare: Strategy selects how to perform work; the State pattern changes behavior according to lifecycle state. An Adapter translates an incompatible contract rather than selecting an algorithm. A React render prop may inject a rendering strategy; see composition patterns.

Dependency injection: supply dependencies explicitly

Purpose: Let an application function receive its collaborators instead of locating or constructing them internally. This separates policy from dependency creation and enables deterministic testing.

Design patternArchitecture

Is a hook dependency injection? Only when it receives a collaborator, for example useSearch(query, searchClient). A hook that directly imports a fixed client is not DI merely because it is a hook. A provider can also supply the dependency; preserve stable identity and appropriate request/session scope.

Use when: Time, network clients, storage, or feature policies need to vary by environment or test. Construct them at a composition root—the application’s setup boundary—and inject through parameters, constructors, or a scoped provider.

type Clock = () => number;
type Session = { expiresAt: number };
function isExpired(session: Session, now: Clock): boolean {
  return now() >= session.expiresAt;
}
isExpired({ expiresAt: 2000 }, () => 1000); // Deterministic: false.
isExpired({ expiresAt: 2000 }, Date.now);   // Production clock.

Benefits and tradeoffs: Dependencies become visible and replaceable. Too many parameters can reveal an oversized responsibility; a DI container can hide the dependency graph and introduce lifetime mistakes.

When not to use: Stable pure helpers usually work as direct imports. Prefer explicit parameters before introducing a container. A service locator asks a registry for dependencies inside business code; it hides requirements that injection makes explicit.

Compare: React Context can distribute an injected service, but Context is a delivery mechanism, not dependency injection itself. Keep service identity stable when appropriate and scope personalized services per request/session; a global singleton can leak SSR user data. Ports define contracts; injection supplies implementations.

Adapter: translate an external contract

Purpose: Convert an existing interface or data model into the one your application expects. Keep vendor naming, serialization, and error formats at the boundary instead of spreading them through components.

Design patternArchitectureAPI integration

Example: A provider returns { payment_id, amount_cents, currency_code }; a payment adapter maps it into your Payment model. Do not silently guess currency precision: money units are part of the contract.

Use when: Integrating a vendor, migrating APIs, or connecting a form library to an input contract. Validate untrusted JSON at runtime before adapting it; TypeScript annotations do not validate a network response.

type ProviderPayment = { payment_id: string; amount_cents: number; currency_code: 'USD' };
type Payment = { id: string; amountMinor: number; currency: 'USD' };
function adaptPayment(raw: ProviderPayment): Payment {
  return { id: raw.payment_id, amountMinor: raw.amount_cents, currency: raw.currency_code };
}

Benefits and tradeoffs: Isolates external changes and makes application models consistent. Mapping code and error translation need maintenance; a lowest-common-denominator interface can hide essential provider capabilities.

When not to use: Do not wrap every utility in a pass-through adapter. Use a stable API directly if there is no meaningful mismatch or boundary to protect.

Compare: Adapter translates a contract; Facade simplifies a subsystem; Strategy swaps behavior. An anti-corruption layer is a broader domain boundary that prevents another system’s concepts from distorting your model, often using adapters. See component and form adapters.

Facade: expose a cohesive workflow

Purpose: Give callers a small interface over a complex subsystem. A facade hides coordination details while exposing outcomes the caller needs.

Design patternArchitectureAPI integration

Is a BFF a Facade? Often, yes: it hides backend-service coordination behind a frontend-friendly API. Facade describes simplification; BFF describes a backend tailored to a client experience. A facade may also be a local module, so the terms are not interchangeable.

Example: checkout.submit(draft) coordinates validation, an order API, and confirmation mapping. The React form knows about pending, success, and actionable failure rather than every SDK involved.

Use when: Several callers repeat the same sequence or must obey the same integration rules. Return explicit domain outcomes and preserve enough error information for recovery.

Minimal example · one call hides several steps:

async function loadDashboard(userId) {
  const [profile, orders] = await Promise.all([
    users.get(userId), ordersApi.list(userId),
  ]);
  return { profile, orders };
}

The caller uses one dashboard operation instead of coordinating the two services. Error policy remains part of the facade contract.

Benefits and tradeoffs: Reduces coupling and centralizes orchestration. An expanding facade can become a god object; keep it scoped to a cohesive capability. Calling several APIs through one method does not make the workflow atomic—handle partial failure explicitly.

When not to use: One clear operation rarely needs another wrapper. If the concern is only translating one provider’s contract, use an Adapter. If business orchestration is substantial, use an application service with injected collaborators.

Compare: A facade can be a local module. A BFF is a server boundary and may expose facade-like endpoints. A proxy preserves an interface while controlling access or remote invocation; a facade intentionally simplifies the interface.

Architecture and evolution

Ports and adapters: protect business rules

Purpose: In hexagonal architecture, the application core defines the capabilities it needs through ports. Infrastructure implements those ports through adapters. Source-code dependencies point toward the core’s contracts; the core does not import React, a database driver, or a payment SDK.

Design patternArchitectureAPI integration

Example: A place-order use case accepts a PaymentGateway port and an OrderRepository port. An HTTP handler is a driving adapter that invokes the use case; a payment SDK adapter is a driven adapter used by it. A composition root wires them together through dependency injection.

Use when: Business rules are meaningful, several entry points share them, or infrastructure changes independently. In a frontend, keep pricing rules or workflow decisions in framework-independent modules, while hooks adapt those rules to React lifecycles.

// Core contract: owned by the application, not a vendor SDK.
interface OrderRepository {
  findById(id: string): Promise<{ id: string; totalMinor: number } | null>;
}
function makeLoadOrder(orders: OrderRepository) {
  return (id: string) => orders.findById(id);
}
// An HTTP or database adapter implements the port; the use case stays unchanged.

Benefits and tradeoffs: Supports focused tests and replaceable infrastructure. Interfaces and mappings add indirection; a port for every CRUD getter can merely duplicate a library API.

When not to use: A small UI with minimal business logic may need only feature modules and a clear API client. Extract boundaries when a real dependency or policy needs isolation.

Compare: A layered architecture can also enforce inward dependencies; folder names alone do not guarantee this. An Adapter is one building block, while hexagonal architecture governs relationships across the application. Keep authoritative rules on the server even if shared client logic improves UX; see server authorization.

Relationship to SOLID: this architecture applies Dependency Inversion. Microservices define deployment/service boundaries; ports and adapters organize dependencies inside a monolith, service or frontend.

Backend for Frontend: shape a server boundary for a client

Purpose: A BFF provides APIs tailored to one frontend experience. It can aggregate upstream responses, adapt payloads, and keep upstream credentials on the server.

Design patternArchitectureAPI integration

Example: A product page calls GET /web/product-page/42; its BFF fetches product and availability data, authorizes the user, and returns a view-oriented response. Reviews may remain independently loaded so a slow optional dependency does not block the page.

Use when: Web and mobile have materially different data needs, browser-to-service orchestration is complex, or a server-managed session fits the credential threat model. Framework route handlers can implement this boundary without a separate service.

Minimal example · one frontend-specific response:

// Inside an authenticated dashboard HTTP handler:
const [user, orders] = await Promise.all([
  users.get(currentUser.id), ordersApi.list(currentUser.id),
]);
return { greeting: user.name, recentOrders: orders.slice(0, 3) };

The BFF returns the screen’s data shape; the browser makes one request instead of two. These service clients are illustrative.

Benefits and tradeoffs: Reduces client coupling and can reduce request waterfalls, but adds server operations, latency, cache policies, and another failure boundary. Enforce resource authorization; avoid an unbounded pass-through proxy or aggregation endpoint.

When not to use: If a shared API already fits, use it directly. Use an API gateway for shared routing, authentication infrastructure, or quotas; use a BFF for client-specific composition. GraphQL offers a query contract and execution model and can be used within a BFF—it is not automatically an alternative deployment boundary.

Compare: Server Components govern component execution and can call server-side services; a BFF governs the browser-facing API/session boundary. A single framework application can contain both. Protect upstream work with timeouts and failure containment.

CQRS: separate write decisions from read models

CQRS (Command Query Responsibility Segregation) means designing changing data and reading data as separate responsibilities, with models suited to each. A command asks the system to make a change; a query asks for information without changing business state. A “model” here means the data shape and rules used for that responsibility—not necessarily a separate database.

Design patternArchitecture

Start with the problem: an employer edits a job; thousands of job seekers search it. Editing needs ownership checks and valid changes. Searching needs fast filters, counts and display-ready results. Making both use the same general-purpose job model can become awkward as these needs diverge.

Before / ordinary CRUD: one Job model supports editing and searching. This is often sufficient. After / CQRS: the write side owns business changes; the read side exposes a purpose-built search model. You separate the responsibilities because they need different behavior—not simply because one endpoint is POST and another is GET.

Concrete split · the same job, two purposes:

// Write-side command: change authoritative data; enforce business rules.
async function changeJobTitle(user, jobId, title) {
  await permissions.requireJobEditor(user, jobId);
  await jobs.updateTitle(jobId, title);
}

// Read-side query: return display-ready search results.
async function searchJobs(filters) {
  return jobSearchView.find(filters); // Includes company name and facet counts.
}

These are illustrative configured adapters, not built-in APIs. The write model might store a job with a company ID and enforce who can edit it. The read model can combine job title, company name and filterable fields so search does not repeatedly assemble them. Reading still enforces visibility permissions; separating reads never bypasses authorization.

When it earns its cost: complicated write rules and demanding reads need different models or independent scaling. When not to use it: a small CRUD app can keep one model with good queries/indexes. CQRS adds extra models to maintain; a separate asynchronous read store also adds lag, synchronization, retries and rebuild work. You can start with separate command/query logic in one application and one database—CQRS does not require microservices, a queue or eventual consistency.

Compare: primary/replica replication copies database data for availability/read capacity; CQRS changes the read/write models. Event sourcing stores events as the authoritative history; CQRS does not require it. Saga coordinates multi-step business changes; it can coexist with CQRS. See the concrete job-search read model.

Remember: “Use one model to decide and apply valid changes, and another to answer the reads efficiently.” A separate search index is one concrete implementation; the essential idea is the separation of read and write responsibilities/models.

Incremental replacement: Strangler Fig & branch by abstraction

Purpose: Replace a legacy implementation in controlled steps while keeping the product usable. These approaches reduce the amount of behavior changed at once.

Design patternArchitectureResilience

Use when: A design-system, framework, API, or persistence migration is too broad for a safe direct replacement. Define the seam, behavior contracts, verification metrics, rollout cohorts, and rollback path before moving traffic.

Minimal example · Strangler Fig vs branch by abstraction:

// Strangler Fig: migrate one external capability/route.
const app = path.startsWith('/products') ? newApp : legacyApp;
app.handle(request);

// Branch by abstraction: switch behind the same internal API.
const storage = useNewStorage ? indexedDbAdapter : legacyAdapter;
storage.save(draft);

Routing and adapters are illustrative. Each switch chooses one implementation, rather than silently dual-writing both.

ApproachMechanismExample
Strangler FigRoute selected capabilities to the new implementation while the legacy implementation serves the rest.Move product routes to a new frontend, then checkout, then remove the old frontend.
Branch by abstractionIntroduce a stable interface, implement old and new variants behind it, and migrate callers before removing the old variant.A storage port switches from localStorage to IndexedDB without rewriting each feature simultaneously.

Example plan: Adapt the legacy implementation behind the interface; add the new implementation; switch a small cohort with a feature flag; compare errors and user outcomes; expand; remove the flag and old code. For data/schema changes, use backward-compatible expand-and-contract steps. Rolling code back may not undo already-written data.

Benefits and tradeoffs: Smaller releases and explicit rollback come with temporary duplication and compatibility work. Assign an owner and removal criteria so the transition does not become permanent.

When not to use: Prefer a direct replacement for a small, well-tested change. A feature flag is a routing tool, not a migration architecture. Avoid casually dual-writing both systems: divergent writes need an explicit consistency and recovery policy.

Compare: Strangler Fig moves capability boundaries; branch by abstraction moves implementations behind a contract. Adapters translate old/new interfaces; production performance measurements help verify a migration’s actual outcome.

Distributed workflows and recovery

Saga: coordinate a workflow across services

A Saga splits a multi-service business operation into local transactions. Each committed step has a planned compensating action when the workflow cannot complete. It addresses distributed workflow consistency; it is not one database transaction.

Design patternArchitectureResilience

Example: checkout reserves stock, authorizes payment and confirms an order. If confirmation permanently fails, release the stock reservation and void the payment authorization. If payment was already captured, compensation may be a refund rather than an undo.

Use when: independent services own their databases and a business operation spans them. Expose pending, completed and compensating states in the UI; a successful first step is not final success.

Minimal example · forward steps and compensations:

// Illustrative durable workflow-engine API, not built-in JavaScript.
await saga.run([
  { execute: reserveStock, compensate: releaseStock },
  { execute: authorizePayment, compensate: voidAuthorization },
  { execute: confirmOrder },
]);

On permanent failure, the engine compensates completed steps in reverse order. It must persist progress and recover/retry; a plain try/catch is not a durable Saga.

Two coordination styles: Orchestration uses a durable coordinator to issue commands and track progress—clear for complex workflows, but adds a central workflow component. Choreography lets services react to events—fewer central dependencies, but harder to trace and avoid cycles as the workflow grows. Both need idempotent handlers and durable state/message delivery.

Limits / alternative: Saga does not provide automatic rollback or isolation; users may observe intermediate state, and compensation can fail. Use reservations, version checks and reconciliation where needed. Prefer a single ACID transaction when all changes fit one database. Two-phase commit offers distributed atomic commitment where supported, with coordination/availability costs; Saga trades that atomicity for recoverable business steps.

Connect: commands and events express the work and results; a state machine models progress; transactional outbox connects local commits to message publication. A Circuit Breaker protects individual dependency calls; it does not compensate a workflow.

Failure containment: circuit breakers & bulkheads

Purpose: Protect application capacity when dependencies slow down or fail. These patterns are most relevant in your backend/BFF; a browser can degrade its UI but cannot enforce service-wide protection.

Circuit breaker: stop repeatedly calling a failing dependency

Design patternResilienceAPI integration

Minimal example · fail fast while open:

// Illustrative resilience-library API.
const breaker = makeBreaker(recommendations.fetch);
const items = await breaker.call(userId);

The library tracks failures: closed allows calls, open rejects quickly, half-open permits probes. Configure thresholds and handle rejection with a defined fallback.

A breaker monitors configured failure/timeout rates. In closed state it allows calls; in open state it rejects quickly for a cooldown; in half-open state it permits limited probes to decide whether to recover. Scope breakers to the dependency/operation that fails rather than disabling unrelated work.

Example: After repeated recommendation-service timeouts, return a clearly degraded product page without recommendations. A breaker needs minimum sample sizes, suitable thresholds, bounded probes, and observability. It does not repair the dependency.

Bulkhead: isolate capacity so failures cannot consume everything

Design patternResilienceAPI integration

Minimal example · isolate concurrency capacity:

// Illustrative library API: separate bounded pools.
const imagePool = makePool({ concurrency: 2, maxQueued: 10 });
const checkoutPool = makePool({ concurrency: 20, maxQueued: 40 });
await checkoutPool.run(() => placeOrder(order));

Image work must use imagePool; checkout uses checkoutPool. Saturating one pool does not consume the other’s slots. Separate pools still share process CPU and memory.

A bulkhead gives operations separate bounded resources, such as concurrency limits, connection pools, or queues. If image processing saturates its allocation, checkout still has capacity. Bound waiting queues and reject or degrade when capacity is exhausted.

Use when: A shared process calls unreliable services or handles workloads with different criticality. Breakers reduce futile work; bulkheads limit how far resource exhaustion spreads. They complement each other.

Benefits and tradeoffs: Better failure isolation costs configuration and capacity planning. Isolated pools can leave capacity unused; a breaker can block a recovering dependency if poorly tuned. Per-instance breakers do not automatically coordinate across a fleet.

When not to use: Start with request deadlines, bounded concurrency, cancellation where supported, and actionable errors. Add breakers where repeated failures are a demonstrated risk; avoid placing every browser fetch behind a homegrown global breaker.

MechanismPrimary question
Timeout/deadlineHow long may this operation occupy resources?
Retry with exponential backoff and jitterIs a bounded additional attempt likely to succeed safely?
Circuit breakerShould we attempt this dependency now?
BulkheadHow much isolated capacity may this workload consume?
Rate limitingHow frequently may requests enter?
React error boundaryWhich UI subtree should show a fallback after a rendering failure?

Retry safely: Retry only suitable transient failures within an overall deadline and attempt budget. Use backoff/jitter to avoid synchronized retry storms; respect server guidance. Mutations need idempotency semantics, and aborting a browser fetch does not guarantee upstream work stopped. Rate limiting protects admission; error boundaries isolate UI failures rather than dependency capacity.

Leases: temporary ownership of background work

A lease grants ownership until an expiry time. The owner must renew it to keep working; expiration lets another owner recover work after a crash. A lease bounds how long others wait for an unresponsive owner. It does not stop an expired owner’s code from continuing.

Design patternConcurrencyResource lifecycle

Example: A worker claims a purchase-processing job for 30 seconds and renews every 10 seconds while healthy. If it crashes, its lease expires and the job becomes recoverable. These intervals are illustrative: choose them from operation latency, pause time, renewal load, and acceptable recovery delay.

Atomic claiming: one authoritative ownership transition

Store a durable job record with status, owner_id, lease_until, a monotonically increasing generation, attempts, and run_after. Claim it with an atomic conditional update or a short transaction; a separate SELECT followed by an unchecked UPDATE lets two workers both believe they own it.

-- PostgreSQL. $1 is this worker's ID. Initialize attempts/generation to 0.
-- run_after is the earliest eligible retry time; status starts as 'pending'.
WITH candidate AS (
  SELECT id FROM jobs
  WHERE status = 'pending'
    AND run_after <= statement_timestamp() AND attempts < 5
  ORDER BY run_after, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET status = 'running', owner_id = $1,
    lease_until = statement_timestamp() + interval '30 seconds',
    generation = j.generation + 1, attempts = j.attempts + 1
FROM candidate AS c
WHERE j.id = c.id
RETURNING j.id, j.generation, j.lease_until;

How it works: The row lock protects selection and update in one statement. SKIP LOCKED lets other claimers choose different jobs; it is useful for queue-like access, not a general consistent-read strategy. No returned row means no eligible job was claimed. Commit promptly and perform the long-running work outside the transaction; do not hold a database lock while calling a purchase provider.

Renewal & completion: verify the current generation

-- $1: job ID; $2: worker ID; $3: generation returned by the claim.
UPDATE jobs
SET lease_until = statement_timestamp() + interval '30 seconds'
WHERE id = $1 AND owner_id = $2 AND generation = $3
  AND status = 'running' AND lease_until > statement_timestamp()
RETURNING lease_until;

-- Record success only if this claim is still valid.
UPDATE jobs
SET status = 'completed', owner_id = NULL, lease_until = NULL
WHERE id = $1 AND owner_id = $2 AND generation = $3
  AND status = 'running' AND lease_until > statement_timestamp()
RETURNING id;

Failure contract: Zero updated rows means ownership was lost. A renewal timeout is also uncertain: stop initiating new side effects until ownership is confirmed, and cancel ongoing work when possible. Do not resurrect an expired lease with an unconditional extension. Avoid overlapping renewal calls; a heartbeat is evidence of liveness, while a successful conditional renewal extends ownership.

Time & tradeoffs: Use a documented authoritative time source, such as the same database clock for claim, renewal, and expiry checks; independently skewed worker clocks are unsafe. Wall-clock jumps and store failover remain concerns. Short leases recover faster but increase false expiry and renewal traffic; long leases tolerate pauses but delay recovery. Use a durable coordinator with defined consistency guarantees.

Compare: A transaction lock protects a short database critical section; a lease supports ownership across longer work without holding that transaction open. A TTL only expires data unless an ownership protocol gives it lease semantics. Local mutexes do not coordinate separate processes. See transactions and conditional updates.

Sweepers: find expired work & recover it safely

A sweeper is a periodic background scan that detects abandoned or overdue records and applies a recovery policy. It may requeue expired jobs, release expired reservations, or clean up temporary resources. A lease defines when ownership ends; the sweeper decides what happens afterward. They are complementary mechanisms, not a mandatory pair.

Design patternResilience
-- PostgreSQL: recover at most 100 expired claims per batch.
WITH expired AS (
  SELECT id FROM jobs
  WHERE status = 'running' AND lease_until <= statement_timestamp()
  ORDER BY lease_until, id
  FOR UPDATE SKIP LOCKED
  LIMIT 100
)
UPDATE jobs AS j
SET status = CASE WHEN j.attempts < 5 THEN 'pending' ELSE 'failed' END,
    owner_id = NULL, lease_until = NULL,
    run_after = statement_timestamp() + interval '5 seconds'
FROM expired AS e
WHERE j.id = e.id AND j.status = 'running'
  AND j.lease_until <= statement_timestamp()
RETURNING j.id, j.status;

Concurrency: The short row-locking transaction coordinates renewal and sweeping; expiry predicates are rechecked during recovery. Concurrent sweepers skip locked rows rather than process one record together. Already recovered/completed records no longer match, making repeated scans safe at the state-transition level. Keep generation monotonic across retries; never reset it when requeuing.

Bounded operation: Index the scan path, for example a PostgreSQL partial index on (lease_until, id) WHERE status = 'running'. Process small batches and commit between them. The example uses a fixed retry delay for clarity; production retries usually need capped exponential backoff with jitter, an attempt limit, and a terminal-failure/manual-review policy.

Recovery latency: Expect roughly the remaining lease duration plus scan interval and scheduling/queue delay. A sweeper is periodic recovery, not an exact timer. Monitor oldest expired lease age, sweep duration, retry rate, renewal failures, and terminal failures.

When not to build one: A managed job queue’s visibility timeout and redelivery may already provide this mechanism. Directly reclaiming expired rows can eliminate a separate sweeper for a simple queue; opportunistic cleanup can suit low-volume temporary data. Database TTL deletion is useful for disposal, but usually does not implement business recovery or an audit trail.

Fencing & idempotency: protect against stale owners and retries

Lease expiration is not mutual exclusion at the CPU or network level. A paused worker may resume after another worker has taken ownership, and an old in-flight request may finish after expiry. Correctness must be enforced where the protected write or side effect happens.

ConcurrencyResilience

Minimal example: worker A holds generation 7; after expiry, B gets generation 8. A’s write with token 7 is rejected by the resource enforcing the current token (fencing). B retries payment with the same purchase key order-42; the provider returns the original payment outcome instead of charging twice (idempotency).

Fencing tokens: reject obsolete ownership generations

Design patternConcurrency

A fencing token is a monotonically increasing ownership number that accompanies protected operations. The resource must validate it atomically with the write. In the job record above, checking the current generation rejects A’s generation 41 after B claims 42. Checking the lease also rejects A before a new owner arrives.

For a separate resource, token ordering must match the resource’s ownership scope. Independent per-job counters cannot safely fence a resource shared by multiple jobs. A resource that only remembers the highest token seen can reject an older token after observing a newer one, but cannot detect expiry by itself. Stronger guarantees require checking current ownership/expiry through an appropriate coordination contract. Merely generating or logging a token is not fencing.

Idempotency: avoid repeating the logical business effect

API integrationResilience

Example: A calls the payment provider successfully, then crashes before marking the job completed. B retries. The job generation protects the completion record, but cannot undo A’s payment. Use a stable idempotency key for the logical purchase operation, shared across attempts, with the provider’s documented deduplication/retention contract. A new key per lease generation defeats that protection.

Combine mechanisms: Use generation/lease checks for job ownership, a unique constraint or transaction for database effects, and idempotency or reconciliation for external effects. Keep an operation result/receipt so an ambiguous timeout can be resolved. Do not claim exactly-once execution from a lease and sweeper; retries and overlapping execution remain possible. See ambiguous API outcomes and optimistic concurrency control.

MechanismWhat it solvesWhat it does not guarantee
LeaseTemporary ownership and eventual recovery after missed renewals.An expired process stops executing.
SweeperDetection and recovery of abandoned durable state.Immediate recovery or deduplicated business effects.
FencingRejection of stale ownership at an enforcing resource.Deduplication of all valid retries or arbitrary external effects.
IdempotencyRepeated logical operations do not repeat their effect within the defined contract.Exclusive execution or recovery of stuck work.

When to use: Durable background jobs, temporary reservations, and workflows that outlive an HTTP request. For short database-only changes, prefer transactions and constraints; for local work, use a local concurrency primitive; for queue workloads, evaluate existing queue guarantees first.

Shutdown connection: Stop claiming jobs, keep renewing while draining work you still own, then finish or release conditionally. Never release ownership while the old worker can still perform unprotected writes. Crashes bypass graceful cleanup, so expiry and recovery remain necessary; see Node.js graceful shutdown.

Design checks: Pause a worker beyond expiry, race renewal with sweeping, lose a renewal response, run two sweepers, and crash after the external effect but before completion. State precisely which operation is atomic, where fencing is enforced, and how a retry finds an existing result.

Review: explain the seam and the cost

Start with a concrete pressure: changing policy, an external contract, hidden dependencies, repeated orchestration, migration risk, or failure propagation. Identify who owns the contract, show the smallest implementation, and describe how it fails and is tested. Explain the simpler alternative and why the current complexity earns its cost.

Practice: Design a replaceable payment client (Adapter + injection), keep checkout rules independent (ports), hide coordination behind a focused facade, and explain why that does not make payment and order persistence atomic. For frontend state, connect these decisions to command handlers and pure reducers.
