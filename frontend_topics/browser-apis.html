Browser APIs: Observation, Workers & Storage

Choose APIs for cancellation, observation, background computation, persistence, and cross-tab coordination. Define the lifecycle, failure behavior, and data owner before using each mechanism.

Use browser-managed observation for visibility and size changes, and cooperative cancellation for obsolete asynchronous work. These APIs avoid repeated polling and make resource cleanup explicit.

AbortController & AbortSignal: cancel obsolete work

AbortController owns the cancellation action: call abort(). Its AbortSignal communicates cancellation to supporting operations through the signal option, the aborted flag, and an abort event. This is cooperative cancellation, not a way to forcibly stop arbitrary JavaScript or any Promise.

BrowserConcurrencyResource lifecycle

Use it for: Aborting an obsolete search, canceling a fetch when a React component unmounts, or removing event listeners registered with a signal. It complements debouncing and request deduplication; those reduce different kinds of work.

// Inside a Client Component:
useEffect(() => {
  const controller = new AbortController();
  const { signal } = controller;

  async function load() {
    try {
      const response = await fetch(
        '/api/search?q=' + encodeURIComponent(query),
        { signal }
      );
      if (!response.ok) throw new Error('HTTP ' + response.status);
      const results = await response.json();
      // Guard the state update if cancellation occurred meanwhile.
      if (!signal.aborted) setResults(results);
    } catch (error) {
      if (!signal.aborted) setError(error);
    }
  }

  load();
  return () => controller.abort(); // Query changes or unmount.
}, [query]);
  • One-shot lifecycle: An aborted signal stays aborted. Create a new controller for a new operation; a shared signal intentionally cancels all operations listening to it.
  • Error handling: Default abort() cancellation causes fetch to reject with an AbortError. Custom abort reasons and timeout signals can produce other reasons, so do not assume every cancellation has that name.
  • Timeouts & composition: Where supported, AbortSignal.timeout(ms) provides a timeout signal and AbortSignal.any([...]) combines signals, aborting when the first input aborts. Distinguish user cancellation from timeouts when presenting errors.
  • Correctness boundary: Aborting a request does not guarantee server-side processing stops or undo a completed mutation. Prevent obsolete results from committing to state as well; use a request identity when multiple operations can overlap beyond one effect lifecycle. The state-machine example shows a request-ID transition guard.

To package these lifecycles as reusable behavior, follow the custom hook contracts; choose effect timing using effects and synchronization.

Intersection Observer: observe visibility boundaries

Intersection Observer asynchronously reports when an element’s intersection with a viewport or scroll container crosses configured thresholds. It replaces many scroll handlers that repeatedly measure element geometry.

BrowserPerformanceResource lifecycle
  • root: The viewport by default (null), or an ancestor scroll container.
  • rootMargin: Expands or shrinks the observation boundary. A positive bottom margin can trigger prefetching before an element enters the viewport.
  • threshold: Intersection-ratio boundaries between 0 and 1. A threshold of 0.5 reports crossings around 50% intersection; it does not promise continuous position updates.

Use it for: Infinite-scroll sentinels, prefetching upcoming content, or starting work when a section approaches the viewport. For ordinary offscreen images, prefer native loading="lazy" when it meets your needs.

// Prefetch a section shortly before it enters the viewport.
const observer = new IntersectionObserver(entries => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    observer.unobserve(entry.target); // One-time trigger.
    prefetchSection(entry.target.dataset.section);
  }
}, { root: null, rootMargin: '0px 0px 300px 0px', threshold: 0 });

observer.observe(section);
// On teardown: observer.disconnect();

Important limits: Geometric intersection does not prove the user actually saw an element; overlays or a background tab can affect visibility. Impression tracking may also need page-visibility checks and a minimum exposure duration. For infinite scrolling, guard against concurrent loads and stop observing when no more data remains.

Resize Observer: observe element dimensions

Resize Observer reports changes to an element’s observed box size, even when the browser window stays the same size. For example, opening a sidebar can resize a chart without firing a window.resize event.

BrowserPerformanceResource lifecycle

Use it for: Resizing charts or canvases, measuring variable-height virtualized rows, or informing JavaScript widgets of container-size changes. For purely visual responsive styles, prefer CSS container queries when possible.

// A chart needs an explicit width when its container changes size.
const observer = new ResizeObserver(entries => {
  for (const entry of entries) {
    chart.resize({ width: entry.contentRect.width });
  }
});

observer.observe(chartContainer); // Content box by default.
// On teardown: observer.disconnect();
  • Box model: Choose content-box, border-box, or device-pixel-content-box as appropriate. contentRect reports content-box dimensions; the size properties provide the corresponding box measurements.
  • Resize feedback loops: Changing the observed element’s size inside the callback can trigger more resize notifications. Avoid circular dependencies; compare expected dimensions before writing. Scheduling writes with requestAnimationFrame() can defer them, but does not fix a logically endless resize loop.
  • Scope: This API observes size, not position or viewport intersection. Keep callback work small; expensive callbacks still consume rendering time. See layout thrashing for the cost of interleaving geometry reads and DOM writes.

Web Workers: move computation off the main thread

A dedicated Web Worker runs JavaScript in a separate execution context and thread, keeping CPU-heavy parsing, indexing, or transformations from blocking input. It cannot access the DOM. Ordinary async functions and React transitions do not move calculations to another thread.

BrowserConcurrencyPerformance
// main.js — initialize once per owner, not on every render.
const worker = new Worker(new URL('./sum-worker.js', import.meta.url), {
  type: 'module'
});
let latestId = 0;
worker.onmessage = ({ data }) => {
  if (data.id === latestId) console.log('Current sum:', data.sum);
};
function calculate(values) {
  worker.postMessage({ id: ++latestId, values });
}
// On teardown: worker.terminate();

// sum-worker.js — a separate file.
self.onmessage = ({ data: { id, values } }) => {
  const sum = values.reduce((total, value) => total + value, 0);
  self.postMessage({ id, sum });
};
  • Communication: postMessage normally uses structured cloning. Transfer large ArrayBuffer values through a transfer list to avoid copying; the sender’s buffer becomes detached. Functions and DOM nodes cannot be cloned.
  • Ownership: Track request IDs, handle error/messageerror, and terminate when the owner is disposed. A cancel message cannot interrupt a worker’s long synchronous function; chunk work so it can process messages, or terminate the worker when losing all its tasks is acceptable.
  • Tradeoff: Startup, serialization, and communication add overhead. Use a worker for substantial independent CPU work, not small calculations or ordinary network fetching. Measure the main-thread bottleneck first.
  • Different workers: A Service Worker is an event-driven network/offline intermediary with a browser-managed lifetime; it is not a permanently running computation worker.

Browser storage: choose by data and lifetime

StorageSuitable useMechanism and tradeoffs
localStorageSmall preferences such as a theme.Synchronous string key/value API, generally scoped by origin. JSON serialization is manual. Blocking operations make it unsuitable for large datasets. JavaScript can read it.
sessionStorageTemporary tab-specific drafts.Synchronous, scoped by origin and top-level browsing context; survives reloads but is not a shared cross-tab store.
IndexedDBStructured offline data, larger datasets, blobs.Asynchronous transactional object stores with indexes. Handle schema upgrades and blocked upgrades from other open tabs; a wrapper can simplify its event-based API.
CookiesSmall server-facing values, especially session identifiers.Attached automatically to matching HTTP requests, adding request overhead. Server-set HttpOnly cookies are inaccessible to JavaScript. Scope, expiration, Secure, and SameSite affect security.

Decision: Keep temporary state in memory, shareable navigation in the URL, small preferences in localStorage, and substantial offline records in IndexedDB. Storage persists a snapshot; it does not make that snapshot authoritative or current. For credentials, follow the token storage threat model.

Storage quotas, eviction & recovery

BrowserStorageResilience

Quota and eviction policies vary by browser, storage type, device, and browsing mode. Origin storage is often best-effort; users or the browser can remove it. Do not promise a universal capacity or treat local persistence as a backup.

  • Estimate: await navigator.storage.estimate() returns approximate usage/quota for managed origin storage. It is not a guarantee that the next write succeeds and does not replace each API’s limits.
  • Persist deliberately: navigator.storage.persist() requests protection against automatic storage-pressure eviction; check its boolean result. It does not stop users clearing data.
  • Handle failures: Catch QuotaExceededError, transaction aborts, blocked access, and malformed stored JSON. Evict expendable cached data, bound cache size, and provide an in-memory fallback. Keep irreplaceable drafts recoverable or synchronize them to a server.
  • SSR boundary: Browser storage is unavailable during server rendering. Read it in an appropriate client lifecycle and avoid hydration mismatches from different initial values.

Cross-tab synchronization: notifications are not transactions

Use BroadcastChannel for messages between eligible same-origin contexts in the same storage partition, or the storage event for localStorage changes. A localStorage change notifies other eligible documents, not the document performing the write. Neither mechanism supplies durable event history.

BrowserConcurrencyStorage
const channel = new BroadcastChannel('app-session');
channel.onmessage = ({ data }) => {
  if (data?.type === 'session-changed') {
    // Application-owned: recheck session, then refresh/clear identity-scoped data.
    revalidateSession();
  }
};
// Publish a notification, never a credential.
channel.postMessage({ type: 'session-changed' });
// On teardown: channel.close();

Practical contracts: Update the sending tab locally, validate message shape, and re-read authoritative state after a notification. Recheck on focus/resume because a closed or suspended tab can miss messages. For atomic shared data updates use IndexedDB transactions; read-modify-write through localStorage or BroadcastChannel is not atomic. Version records and define conflict behavior. Cross-tab logout improves UX, while server invalidation supplies the security boundary.

Choosing the right API

  • “Is this section approaching the viewport?” Use Intersection Observer.
  • “Did this chart’s container change size?” Use Resize Observer.
  • “Is this request still relevant?” Use AbortController with a supporting operation and guard stale updates.

For CPU work, choose a Web Worker; for persistence, choose by data size and lifetime; for multi-tab coordination, use notifications with explicit recovery.

Resource lifecycle: Use unobserve(element) to stop observing one target, or disconnect() for all targets. In React, set up observers in an effect and disconnect them in its cleanup; create controllers within each effect execution so cleanup and StrictMode replay remain safe.
