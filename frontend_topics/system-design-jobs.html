Step 1 · Clarify the discovery contract

Design a job discovery page where category navigation, eligible filters, dynamic counts and job results are projections of the same applied search query. The difficult part is defining what each count means and keeping every panel synchronized.

Architecture

Functional requirements

  • Browse a hierarchical category taxonomy; selecting a category shows its matching immediate children, breadcrumb ancestors and descendant jobs.
  • Apply experience, salary, skills and job-type filters. Update categories, facet options, counts and listings together.
  • Remove individual filters, clear all, change sort and paginate. Preserve searches in shareable URLs and browser Back/Forward.
  • Open a job detail page; support loading, empty, error and retry states.

Non-functional requirements

  • Illustrative targets to validate: search API p95 ≤300 ms at agreed load; interactive update p95 ≤500 ms on the target network; 99.9% monthly search availability.
  • Keyboard and screen-reader access; responsive layout; deterministic query semantics; no stale-response overwrite.
  • Search freshness target: 99% of accepted job changes indexed within 30 seconds. Closed jobs must be revalidated on the detail/application boundary.

In scope

Discovery, taxonomy navigation, faceting, public job detail, ingestion into a search read model and operational recovery.

Out of scope

Application submission, employer billing, recommendations/personalization, CV storage and chat. Employer writes are an indexing input, not a fully designed recruiting workflow.

Clarify before drawing: single or multiple categories? OR or AND for skills? Include descendants? Count jobs or vacancies? Hide zero-count options? Currency and salary-period conversion? This design assumes one category subtree, OR within categorical facets, AND across facets, and one count per unique visible job.

Define facet eligibility and count semantics before implementation

Conjunctive filtering: results match the text query, visibility scope, selected category subtree and every active facet. Within one multi-select facet, selected values are OR-ed. A skills “must have all” mode would require explicit AND semantics and different aggregation logic.

API integrationArchitecture

There are two valid count contracts. Do not silently mix them:

ContractCount for option v in facet FBehavior / cost
Strict / conjunctiveApply all current constraints, including F, then count jobs also having v.Only options in the current result set remain eligible; meets a literal narrowing-only interpretation, but alternatives can disappear.
Disjunctive / self-excludingApply every constraint except F, then count jobs having v.Lets users choose alternatives or broaden an OR selection. Requires per-facet aggregation scopes. The displayed count is not the predicted total after adding v.

Chosen baseline: disjunctive faceting for useful multi-select discovery; explicitly confirm this product decision. “Eligible” means nonzero under that facet’s self-excluding scope. If the stakeholder requires strict narrowing, use the first contract; the architecture stays the same. Return countMode in the response.

Worked example: A = Engineering / Remote / React / Full-time; B = Engineering / Remote / React / Contract; C = Engineering / Onsite / React / Full-time. With Engineering + Remote + Full-time, results contain A. Strict job-type counts: Full-time 1, Contract 0. Self-excluding job-type counts: Full-time 1, Contract 1. Selecting both returns A and B. Counts overlap for multi-valued facets, so adding counts does not produce a distinct-job total.

Category counts: exclude the current category constraint but retain query, visibility and every active facet; bucket by ancestor category IDs. Show matching immediate children of the selected node plus breadcrumb navigation. Parent counts deduplicate jobs, so sibling totals can exceed a parent when jobs have multiple classifications.

Never strand the user: retain selected zero-count options with a removable chip, and retain selected categories/ancestors even if empty. Hide or disable unselected zero-count options according to the agreed contract. An empty result must still allow recovery.

Estimate load and choose the simplest search engine that fits

Assume 5 million active jobs, 200,000 daily searchers and 20 committed searches each: 4 million searches/day ≈46 average RPS; a 10× peak is approximately 460 RPS. Draft keystrokes are excluded: count actual requests after debouncing. A 2 KB search document gives roughly 10 GB raw data before inverted indexes, replicas and operational headroom.

One request performs hits plus several aggregations: API RPS is not shard work. Benchmark realistic facet cardinality, skew, OR selections and cold caches; measure query fanout and memory before selecting shard counts.

UI sketch · categories, filters and results

Use nested lists with links/disclosures for category navigation unless a full ARIA tree interaction is required. Use labeled checkboxes, fieldsets and legends for facets; salary gets labeled number inputs as an alternative to a slider. Keep focus on the activated control; politely announce the final result count and use aria-busy during updates. Do not announce every intermediate keystroke.

Keep the previous complete snapshot visible with an “Updating results” state. On failure, identify that the visible snapshot belongs to the previous applied query; offer retry or undo. Never present old counts as though they match new selections.

Frontend sketch · URL ownership and one search snapshot

URL state: text, category ID, stable facet IDs, salary range, sort and cursor. Server state: jobs, counts, eligible options and category labels. Local state: drawer visibility, expanded navigation and uncommitted input/range drafts. Do not copy the server snapshot into independent component reducers.

ReactState management

A query-cache library handles keyed remote snapshots, deduplication and cancellation. A local reducer can coordinate draft/apply/reset transitions. Redux is optional for broader client workflows; Context distributes stable dependencies; neither computes authoritative facet counts. Reuse the state-tool comparison.

Normalize selected values (sorted, deduplicated IDs), omit defaults and validate URL parameters. Changing query/filter/category/sort resets the cursor in one transition. Debounce text input; apply checkbox changes immediately on desktop, batch drawer changes on mobile. Back/Forward restores URL state. See routing and navigation.

Step 2 · High-level architecture and indexing

Start with a modular application and independently scalable search cluster; microservices are not a prerequisite. Serve static assets through a CDN. The search API authenticates where needed, validates filters, adds visibility constraints, checks a bounded cache and submits the search plan.

ArchitectureStorage

Index documents contain job ID, title/description search fields, employer summary, stable skill IDs, job type, experience, location/remote policy, salary metadata, category IDs plus ancestor IDs, visibility, status and version. Use keyword fields/doc values for exact filters and aggregations; analyzed text for relevance. A taxonomy registry defines facet IDs, labels, types and category applicability; observed matching values determine eligibility.

Write the job and outbox record in one SQL transaction. Indexers process at least once, apply monotonically versioned upserts/deletion tombstones and retry with backoff/dead-letter handling. Prevent an old update from resurrecting a closed job. Taxonomy moves require ancestor-path reindexing; build a versioned replacement index, verify it, then switch an alias. See durable outbox publication.

API contract · one query, one coordinated response

Use GET /api/job-search for bounded public search parameters; repeated query parameters encode multi-select values. Use GET /api/job-categories/{id} for taxonomy metadata and GET /api/jobs/{id} for authoritative detail. Long complex searches can use a documented read-only POST search endpoint with explicit cache identity. GET search needs no idempotency key.

Return normalized applied constraints/warnings when they differ from the request. Bound page size, selected values, query length and facet buckets. Reject invalid ranges, unknown filters and tampered cursors with structured 400 errors; 429 includes Retry-After; 503 indicates temporary unavailability. Do not silently drop a salary or permission filter.

Bind the opaque cursor to normalized query, sort, visibility scope and expiry. Sort by relevance/date plus a unique ID tiebreaker. Offset pagination is simpler for shallow browsing; search_after plus a point-in-time (PIT) reader avoids duplicate/missing hits during deeper navigation at the cost of retained search resources. On expired PIT, ask the client to restart. Detail pages recheck current visibility/status.

Step 3 · Query planning, taxonomy and salary semantics

For result hits, apply the full predicate. For each self-excluding facet F, aggregate with that facet’s selection removed while retaining all other constraints and authorization. For categories, aggregate ancestor IDs without the category selection, then project the selected node’s immediate children. A single search request can express filtered aggregations over the same reader context; separate requests may observe different refresh states.

ArchitecturePerformance

In Elasticsearch-style execution, a post_filter changes hits after aggregations; it does not automatically implement all self-excluding facets. Build explicit per-facet filter scopes. Put mandatory visibility/security constraints outside any user-filter exclusion so no aggregation can reveal hidden jobs.

For a salary interval, decide whether a job must overlap or be contained. Baseline: interval overlap, so job.max ≥ requested.min and job.min ≤ requested.max. Unknown salary is excluded only when an explicit salary filter is active; expose an optional “include undisclosed” policy. Store amount, currency, period and normalized annual amounts using a documented exchange-rate date. Do not compare raw hourly and annual salaries or different currencies.

Global facet counts must come from the index, never the current page of 20 jobs. Distributed top-terms aggregations may omit rare values or have count error. For bounded enums use explicit filter buckets/exhaustive terms; for high-cardinality skills use searchable facet values and an explicit truncation/accuracy contract. Exact distinct counts for multiply classified jobs may require more expensive aggregation; do not relabel approximate cardinality as exact.

A selected category can make a previously selected facet inapplicable. Prefer retaining it visibly and explaining zero results; if the agreed product policy clears incompatible values, return the normalized query and surface what changed. Avoid hidden filter removal.

Interaction sequence · atomic panels and stale-response safety

Use AbortController to stop obsolete requests and a monotonically increasing generation/query-key check before committing. Cancellation alone is insufficient: the response may already have completed. A cache may retain A under A’s key, but must not display it as B. Commit the complete response, not three separately arriving panel updates. Reuse the autocomplete race-handling mechanism.

SSR the initial query for discoverability and fast first content, hydrate with the same normalized key, then use client navigation. Never assume React transitions debounce network calls or eliminate races. Preserve structural layout, avoid list-wide skeleton flicker, and defer costly rendering only after measuring.

Scale, consistency, caching and failure recovery

Consistency: all panels describe one search response/read context, not a globally serializable database snapshot. Search is eventually consistent with authoritative writes. Detail/application validation prevents relying on a stale open-job status; expose an unavailable detail state when a listing has closed.

Observe: p50/p95/p99 end-to-end query latency, aggregation vs hit time, error/timeout rate, aborted/obsolete responses, cache hit ratio, shard saturation, queue age, index lag, zero-result rate and filter abandonment. Correlate traces by request ID across API and search; log a query fingerprint, not raw sensitive search text. Track field interaction-to-paint and long tasks in the browser.

Security: validate allowed fields/operators; never pass arbitrary search DSL from the browser. Enforce object-level visibility on search, facets and detail endpoints. Rate-limit expensive queries, cap pagination/PIT lifetime, escape job text and sanitize permitted rich HTML. See security foundations.

Step 4 · Verify the invariants and defend the tradeoffs

Correctness tests: run a tiny catalog through every facet scope and compare hits/counts to a simple reference evaluator. Include OR selections, overlapping skills, multiple category paths, selected zero-count options, salary boundaries/unknowns, visibility restrictions and taxonomy moves. Assert no unauthorized job contributes to any bucket.

Interaction tests: late response A after B, canceled request still completing, Back/Forward, mobile draft cancel/apply, cursor reset, empty-state recovery, expired PIT, keyboard/focus and live announcements. Test ingestion duplicates, out-of-order close/update events and rebuild alias switches. Load-test realistic facets and cold caches against latency targets.

Design wrap-up: “The URL owns the applied query. One search operation returns coherent hits, facets and category counts. We explicitly choose self-excluding counts to allow alternatives. SQL owns job records; a versioned index enables discovery with bounded freshness. We control expensive aggregations, protect visibility in every scope and recover without misrepresenting stale results.”

Defend these choices: strict versus disjunctive facets; immediate versus Apply-button interaction; SQL versus search index; exact counts versus bounded/approximate counts; offset versus cursor/PIT; fresh availability versus cached resilience. Change the requirements first, then explain which choice changes. Return to the design framework.
