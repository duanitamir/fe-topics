What GraphQL solves—and what it does not

GraphQL is a query language and execution model for a typed API. Clients select fields from a server-defined schema; the server validates and executes the selection and returns a correspondingly shaped result. It is not a database, ORM, transport protocol, or replacement for authorization.

GraphQLAPI integrationArchitecture

Problem: Different screens need different combinations of related data. Fixed endpoint representations may over-fetch unused fields or require several client requests. GraphQL exposes a composable schema so a client can request a tailored view of those relationships.

Example: A product page requests product name plus seller name, while checkout requests price and availability. The schema can serve both without a new endpoint per view. One operation can still trigger many backend calls; a small response is not proof of a cheap query.

Use: Multiple clients with evolving, relationship-rich views and teams able to own schema governance and execution cost. For a few stable resource operations, REST is often simpler. A BFF can aggregate data using REST or GraphQL; these are separate choices.

Schema, types & operation documents

The schema defines available fields and types. An operation document selects fields, passes arguments, and names the requested work. Variables provide typed values separately from the document; fragments reuse field selections; aliases rename result keys or request a field with different arguments.

GraphQLAPI integration
type Query {
  product(id: ID!): Product
}
type Product {
  id: ID!
  name: String!
  priceMinor: Int!
  seller: Seller!
}
type Seller {
  id: ID!
  name: String!
}
query ProductCard($id: ID!) {
  product(id: $id) {
    id
    name
    seller { id name }
  }
}

The successful response follows the selected shape; unselected priceMinor is absent:

{
  "data": {
    "product": {
      "id": "42",
      "name": "Engineering Handbook",
      "seller": { "id": "7", "name": "Bookshop" }
    }
  }
}

How to read it: ID is an opaque identifier scalar, not necessarily a number. The exclamation mark is a non-null contract. The product lookup itself is nullable (for example, no visible match), while a present product must supply name and seller under this schema. Variables might be { "id": "42" }; do not concatenate untrusted strings into query source.

Other components: Scalars represent leaf values; enums constrain named choices; input objects describe structured arguments; interfaces/unions model polymorphic outputs. Directives such as skip/include conditionally select fields. Custom scalars need documented serialization and validation; a Date scalar is not built in. GraphQL Int is a signed 32-bit integer; choose a documented scalar/representation when money or IDs exceed that range.

Pagination: A connection-style field may expose edges/node/cursor and pageInfo/hasNextPage/endCursor. This is a common schema convention, not a GraphQL requirement. Bound first/last and follow the underlying pagination contract.

How a GraphQL request executes

A GraphQL server parses an operation document, validates it against the schema, coerces variables, and executes the selected fields. An operation name selects which operation to run if the document contains several. The schema limits what can be requested; resolvers supply the actual values.

GraphQLAPI integrationHTTP

Transport: GraphQL is commonly served over HTTP, often at one endpoint. POST can carry document, variables, and operation name; some servers support GET for queries. Mutation operations must not execute through GET. Subscriptions require a supported transport/protocol, such as a chosen WebSocket protocol or SSE integration.

Tradeoff: A shared endpoint simplifies schema entry but changes logging, caching, and rate-limit granularity. Record operation names/hashes, duration, errors, and backend calls; avoid logging sensitive variables indiscriminately.

Resolvers, context & N+1 prevention

A resolver supplies a field’s value. Common server libraries call resolvers with parent/source, arguments, request context, and execution info. Default field resolution often reads an object property; explicit resolvers connect fields to services and relationships.

GraphQLPerformanceSecurity
// Common resolver-map convention; wire through your server framework.
// context.services enforces access; sellerById is scoped to this request.
const resolvers = {
  Query: {
    product: (_parent, { id }, context) =>
      context.services.products.findVisibleById(id, context.user)
  },
  Product: {
    seller: (product, _args, context) =>
      context.loaders.sellerById.load(product.sellerId)
  }
};

Context: Supply validated identity, application services, request IDs, and request-scoped loaders. Do not trust a userId variable to establish identity. Enforce authorization consistently in application/data access, including nested fields.

Batching: A DataLoader-style utility batches loads within its scheduling window and caches them within its configured scope. Its batch function must return results aligned to input keys, including missing values/errors. Scope it per request and authorization boundary; a process-global personalized loader can leak data.

Use: Relationship fields with repeated entity lookups. Prefer a join/eager load or purpose-built query when it is simpler and cheaper. A loader cannot rescue an arbitrarily expensive query or guarantee one database round trip for the whole operation. See N+1 tradeoffs.

Queries, mutations & subscriptions

Queries read data. Mutations request changes. Subscriptions establish an event source that produces execution results over time. These are schema operation categories; they do not automatically define persistence or delivery guarantees.

GraphQLState managementConcurrency
input RenameProductInput {
  id: ID!
  name: String!
}
type RenameProductPayload {
  product: Product
}
type Mutation {
  renameProduct(input: RenameProductInput!): RenameProductPayload!
}

Mutation behavior: Top-level fields in one mutation operation execute serially. This does not make nested resolution serial, create a database transaction, roll back earlier successful fields, or serialize all clients’ writes. Invoke an application service with explicit validation, transaction, and concurrency-control rules.

Example: RenameProduct checks access and a permitted name, updates the record, and returns the confirmed product. Return enough identity/version data for the client cache to reconcile. Choose an explicit typed payload for expected business outcomes rather than exposing database exception strings.

Subscription limits: Reconnection does not inherently replay missed events or guarantee exactly-once delivery. Authorize subscriptions, bound resource usage, and define resume/refetch behavior. Ordinary polling may be sufficient for infrequent updates; compare WebSocket, SSE, and polling.

Nullability, partial data & errors

A GraphQL execution response can contain both data and errors. A field-level error can leave other fields usable. Non-null propagation moves a null-producing failure to the nearest nullable ancestor; the schema’s nullability determines the blast radius.

GraphQLResilience

Example: In the product schema, seller is non-null. If seller resolution fails, product can become null even when its name resolved successfully, because product is the nullable ancestor. If every ancestor were non-null, the error could null the operation’s data.

List notation: [Product] allows a null list and null items; [Product!] allows a null list but not null items; [Product!]! allows neither. Use non-null for guarantees the server can maintain, not as a blanket preference.

Client policy: Deliberately choose whether partial results render, show a warning, or fail the task. Error paths identify affected fields; expose safe application codes in extensions where the contract specifies them. Transport failure, parse/validation failure, field execution errors, and expected domain rejection need distinct handling.

HTTP: Do not assume HTTP 200 means full application success or that every GraphQL failure must return 200. Status behavior depends on failure phase and the server’s HTTP/media-type contract. Inspect the GraphQL result and the client library’s error policy. See UI failure isolation.

Client caching, identity & mutation reconciliation

A normalized GraphQL cache stores identifiable entities separately and connects query results through references. Clients such as Apollo or Relay can merge representations when configured identity and field policies agree. A plain fetch call has no automatic normalized cache.

GraphQLState managementPerformance

Example: Two operations fetch Product 42 with different fields. A cache using type plus ID can retain one entity, allowing a confirmed mutation response to update its known fields. Lists, membership, ordering, pagination, deleted entities, and argument-specific fields still require explicit policies.

Use: Reused entities across relationship-rich screens. Supply stable IDs, sensible pagination/merge rules, and identity/tenant isolation. For a small operation surface, an ordinary query cache plus explicit updates may be simpler than normalization.

Server/HTTP caching: POST-based arbitrary operations do not map as naturally to ordinary shared HTTP caching as resource GETs. Persisted queries and suitable GET query support can enable stable request identities, but server/CDN policies must include variables, authorization scope, and relevant headers. Persisted operations are not automatically authorized or cacheable.

Comparison: Request-local loader caching avoids repeated backend reads within an operation; normalized client caching coordinates entity views; HTTP caching reuses responses. Follow the same server-state lifecycle and cache boundaries.

Schema evolution, generated types & query safety

A typed schema enables documentation, validation, operation-aware code generation, and change detection. Generate types from the actual selected operation when possible; a schema’s Product type is not the same as the ProductCard query’s selected result.

GraphQLSecurityTooling

Evolution: Add fields, deprecate old ones, measure usage, and migrate clients before removal. Adding required arguments/input fields breaks callers; nullability and enum changes can break generated assumptions too. A schema registry or CI compatibility check helps, but client rollout behavior still matters.

Cost controls: Bound pagination, operation size, aliases/batching, depth, and estimated cost as appropriate. A shallow query can still be expensive, so combine static policies with timeouts, concurrency limits, and backend measurements. Rate-limit by meaningful work/identity rather than only “one HTTP request.”

Security: Validate scalar/business values and enforce object/field permissions. Disabling introspection is not authorization. Trusted persisted-operation allowlists can reduce exposed query shapes, but authorization and variable validation remain necessary. Avoid leaking internal stack traces and private fields through errors or shared caches.

Tradeoff: Schema governance and tooling pay off for substantial multi-client APIs but can be overhead for small services. Generated TypeScript still does not establish runtime truth; see static versus runtime validation.

GraphQL vs. REST: choose by the client and operating cost

REST organizes interactions around resources and representations using HTTP semantics; many practical “REST APIs” use a pragmatic resource-oriented style. GraphQL offers a typed field-selection/execution contract. Neither guarantees good domain design, low latency, security, or maintainability.

ConcernGraphQLResource-oriented HTTP API
Variable screen dataClient selects related fields through a schema.Use resource representations, sparse fields, includes, or a BFF as needed.
Backend workResolvers need batching, authorization, and cost controls.Handlers need efficient queries, authorization, and bounded work too.

Choose GraphQL: Several clients need changing combinations of related entities, shared schema ownership is realistic, and the organization can operate query-level authorization/cost/caching policies.

Choose REST: Resource operations are stable, HTTP caching is valuable, clients are simple, or the team wants a smaller operational surface. Avoid adding GraphQL just to remove one inconvenient endpoint; an aggregate endpoint or BFF may solve it.

Other alternatives: RPC suits explicit commands/workflows and can have generated contracts; gRPC uses Protobuf and requires deliberate browser integration. SSE/WebSockets address ongoing delivery, not resource modeling. A system can combine REST downloads/uploads, GraphQL reads, and event subscriptions without forcing one style everywhere.

Explanation: Start with client data shapes and ownership, measure waterfalls and backend work, then choose the contract and operating model. One endpoint or fewer response fields is not a sufficient performance argument.
