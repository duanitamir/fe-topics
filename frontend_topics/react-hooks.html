React Hooks

Begin with render snapshots and state. Build up to refs, effects, shared subscriptions, responsive updates, and reusable hooks; use the hook index for direct lookup.

Choose hooks by the responsibility they manage: state, synchronization, identity, scheduling, or integration. Hooks compose behavior; they do not replace clear state ownership or make expensive work disappear.

Version scope: React 19-era applications, including useEffectEvent in React 19.2+. useFormStatus comes from react-dom; the other React APIs below come from react. Check your installed React version and framework support before adopting newer APIs. Most stateful and effectful hooks belong in Client Components; use has distinct rules and can also be used in Server Components. See component execution boundaries.

Study format: Each hook follows the same seven-part structure: purpose, when to use, example, when not to use and alternatives, benefits and tradeoffs, pitfalls and guarantees, and related concepts. Examples are independent; React hooks are imported from react unless a different import is shown. Application helpers and component fragments are identified explicitly.

Rules, render snapshots & dependencies

  • Rules of Hooks: Call hooks at the top level of a function component or custom hook, before conditional returns. Do not call them in loops, event handlers, or ordinary utility functions. React relies on consistent hook call order. The use API is an explicit exception discussed below.
  • Render snapshots: Each render sees its own props and state. Callbacks close over that snapshot. A stale closure occurs when later work uses an outdated captured value; a dependency omission is a common cause.
  • Purity: Rendering calculates UI. Do not mutate external data, start subscriptions, or send requests as a render side effect. React may retry or discard render work; reducers, initializers, and memo calculations must also be pure.
  • Dependency arrays: Include every reactive value read by an effect or memoized callback/calculation. Dependencies are compared using Object.is. Fix the code’s ownership or synchronization model rather than disabling exhaustive-deps to force a preferred schedule.
  • Hook identity & state lifetime: State belongs to a component’s position and identity in the tree. Changing its key can reset state; defining component types inside another component can cause unintended remounts. A hook call does not create globally shared state.

Connect this model to render, reconciliation, and commit, and to referential stability when designing dependencies.

For the language mechanism behind captured values and object identity, see lexical closures and reference equality and structural sharing.

State & transitions

useState

ReactState management

Purpose: Stores a local state value and queues renders when it changes. Each render sees a snapshot; a setter does not mutate the value in the running handler.

When to use: An independent value such as an expanded panel, input query, or selected tab.

Example

function Counter() {
  const [count, setCount] = useState(0);
  function addTwo() {
    setCount(previous => previous + 1);
    setCount(previous => previous + 1);
  }
  return <button onClick={addTwo}>{count}</button>;
}

Functional updaters run against queued state, so the two updates add 2 even when React batches them.

When not to use & alternatives: Do not store values that can be derived from props/state during render. Use useRef for mutable values that should not render, or useReducer for related transitions.

Benefits & tradeoffs

  • Benefits: Small API, local ownership, and automatic batching reduce coordination work.
  • Tradeoffs: Many interdependent setters can obscure invariants; lifting state too far broadens render work.

Pitfalls & guarantees: Use immutable updates and pure updaters. The setter identity is stable; Object.is-equal values can skip updates. useState(() => createInitialDraft()) lazily initializes; pass a function wrapper when storing a function. React may invoke initializers/updaters twice in development. Batching is not one guaranteed render for an entire async workflow.

Related concepts: State ownership · Render snapshots · Hook index

useReducer

ReactState management

Purpose: Applies a pure (state, action) => nextState function to queued actions. It makes related transitions explicit.

When to use: A workflow with several events and invariants, such as draft editing, retries, or selection management.

Example

function counterReducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'reset': return { count: 0 };
    default: throw new Error('Unknown action: ' + action.type);
  }
}

function Counter() {
  const [state, dispatch] = useReducer(counterReducer, { count: 0 });
  return (
    <button onClick={() => dispatch({ type: 'increment' })}>
      {state.count}
    </button>
  );
}

Events describe intent; the reducer centralizes the permitted state change. Shared-provider wiring stays in the existing Context topic.

When not to use & alternatives: For one simple value, prefer useState. For hierarchical or parallel workflows, consider a dedicated state-machine library rather than an expanding switch statement.

Benefits & tradeoffs

  • Benefits: Centralized transitions are independently testable and easier to audit.
  • Tradeoffs: Adds action types and indirection; it does not automatically optimize rendering or share state.

Pitfalls & guarantees: Dispatch has stable identity. Keep reducers immutable and side-effect free; fetch in a handler/effect and dispatch completion events. useReducer(reducer, initialArg, init) supports lazy initialization. A reducer is not automatically an FSM; model states and guards explicitly.

Related concepts: Context + reducer · Finite state machines · Hook index

Refs & imperative integration

useRef

ReactResource lifecycle

Purpose: Keeps a stable object with a mutable current property; mutation does not request a render.

When to use: DOM access, timer IDs, or an imperative resource that is not the screen’s source of truth.

Example

function SearchField() {
  const inputRef = useRef(null);
  return (
    <>
      <input ref={inputRef} aria-label="Search" />
      <button onClick={() => inputRef.current?.focus()}>Focus search</button>
    </>
  );
}

React assigns the DOM node during commit. The click handler uses it without putting the node in state.

When not to use & alternatives: Use state for values that must update UI. Do not use refs to conceal missing effect dependencies; useEffectEvent may fit genuinely non-reactive effect logic.

Benefits & tradeoffs

  • Benefits: Provides stable mutable storage and direct integration with DOM APIs.
  • Tradeoffs: Changes are invisible to rendering and can become hidden state if overused.

Pitfalls & guarantees: Do not generally read/write refs during render except predictable initialization patterns. DOM refs can be null before attachment and after removal. StrictMode may create/discard a ref object in development while checking purity; only the committed instance matters.

Related concepts: Reactive state · Restricted imperative APIs · Hook index

useImperativeHandle

ReactResource lifecycle

Purpose: Customizes the handle exposed through a ref instead of exposing the component’s complete internal DOM.

When to use: A parent needs a small imperative capability such as focus, selection, or scroll-to-item.

Example

// React 19: function components receive ref as a prop.
function SearchInput({ ref }) {
  const inputRef = useRef(null);
  useImperativeHandle(ref, () => ({
    focus() { inputRef.current?.focus(); }
  }), []);
  return <input ref={inputRef} aria-label="Search" />;
}

The parent receives a focus method, not arbitrary access to the internal input API.

When not to use & alternatives: Prefer declarative props for open state, selection, or other persistent UI state. Expose a raw DOM ref only if that is the intended public contract.

Benefits & tradeoffs

  • Benefits: Encapsulates implementation details while supporting necessary imperative integration.
  • Tradeoffs: Introduces parent/child timing coupling and a public API that must remain compatible.

Pitfalls & guarantees: Include reactive values captured by the handle in dependencies. With no dependency array, a new handle is created each render. React 18 and earlier generally need forwardRef; React 19 supports ref as a prop. Handle access must tolerate unmounted children.

Related concepts: Component customization contracts · DOM refs · Hook index

Effects & synchronization

useEffect

ReactResource lifecycle

Purpose: Synchronizes committed UI with an external system through setup and cleanup.

When to use: Subscriptions, timers, observers, connections, and third-party widgets whose lifetime follows component inputs.

Example

function WindowTitle({ title }) {
  useEffect(() => {
    const previousTitle = document.title;
    document.title = title;
    return () => { document.title = previousTitle; };
  }, [title]);
  return null;
}

This single-owner example updates an external browser resource after commit and restores it when synchronization ends.

When not to use & alternatives: Calculate derived data during render; handle an explicit user action in its handler. Use useLayoutEffect only when pre-paint measurement is required. Prefer a framework/query cache over hand-written effects for complex server-state fetching.

Benefits & tradeoffs

  • Benefits: Explicit setup/cleanup coordinates resource lifetime with changing inputs.
  • Tradeoffs: Adds lifecycle and race-condition complexity; fetching this way can create waterfalls and misses SSR data delivery.

Pitfalls & guarantees: No array: runs after each commit. []: no reactive dependencies. [a, b]: cleanup then setup when dependencies change; cleanup also runs on unmount. StrictMode checks setup → cleanup → setup in development. Effects never run on the server, and are not guaranteed to run after paint. Do not make the callback async; return cleanup, not a Promise. Include reactive dependencies and guard obsolete async results.

Related concepts: Listener lifecycle · Async cleanup and cancellation · Non-reactive effect logic · Hook index

useLayoutEffect

ReactResource lifecycle

Purpose: Runs after DOM commit and before the browser repaints, allowing measurement and a synchronous visual correction.

When to use: A tooltip or overlay must measure its rendered box before its final position is painted.

Example

function MeasuredLabel({ text }) {
  const ref = useRef(null);
  const [width, setWidth] = useState(0);
  useLayoutEffect(() => {
    setWidth(ref.current.getBoundingClientRect().width);
  }, [text]);
  return <span ref={ref} data-measured-width={width}>{text}</span>;
}

The geometry read happens after the DOM exists. This illustrates initial/text-driven measurement, not tracking every font or container-size change.

When not to use & alternatives: Use CSS for layout when possible, useEffect for non-visual synchronization, or Resize Observer for ongoing size changes.

Benefits & tradeoffs

  • Benefits: Prevents a visible intermediate position when measurement determines placement.
  • Tradeoffs: Blocks paint; synchronous updates add work to the frame’s critical path.

Pitfalls & guarantees: It does not run during SSR, which has no browser layout. Keep server output stable and choose an appropriate client boundary. Dependency and cleanup rules still apply. Avoid alternating geometry reads and writes, which can force repeated layout.

Related concepts: Layout thrashing · Resize Observer · Hydration · Hook index

useEffectEvent

ReactResource lifecycle

Purpose: Defines non-reactive effect-triggered logic that reads the latest committed props/state without making those values synchronization dependencies. Requires React 19.2+.

When to use: A connection depends on roomId, while its notification should use the current theme without reconnecting.

Example

function ConnectionNotice({ roomId, theme }) {
  const onConnected = useEffectEvent(() => notify('Connected', theme));
  useEffect(() => {
    const connection = createConnection(roomId); // Application API.
    connection.on('connected', () => onConnected());
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);
  return null;
}

roomId remains reactive. The effect-triggered notification sees the latest theme without replacing the connection.

When not to use & alternatives: Do not use it to hide dependencies that should re-synchronize an effect. Use ordinary handlers for UI events, useCallback for a memoized callback prop, or complete effect dependencies for reactive logic.

Benefits & tradeoffs

  • Benefits: Separates resource lifetime from incidental reads without manual ref synchronization.
  • Tradeoffs: Has deliberately narrow calling rules and needs compatible React/lint tooling.

Pitfalls & guarantees: Call Effect Events only from effects or their effect-triggered logic in the same component/hook. Do not call them during render or from UI handlers, pass them to children, or add them to dependency arrays. They are not a general-purpose stable callback.

Related concepts: Effect dependencies · Official reference · Hook index

useInsertionEffect

ReactResource lifecycle

Purpose: Provides a specialized phase for CSS-in-JS libraries to insert styles before layout effects run.

When to use: You maintain a runtime styling library whose dynamic rules must exist before consumers measure layout.

Example

// Library-internal illustration, not a recommended application pattern.
function useRuntimeRule(rule) {
  useInsertionEffect(() => {
    const style = document.createElement('style');
    style.textContent = rule;
    document.head.append(style);
    return () => style.remove();
  }, [rule]);
}

The example shows ordering and cleanup. A production library also needs deduplication, SSR extraction, and CSP-compatible style insertion.

When not to use & alternatives: Use static CSS, CSS Modules, or your styling library’s supported API in application code. Use layout effects for measurement, not insertion effects.

Benefits & tradeoffs

  • Benefits: Makes styles available before layout-effect readers need them.
  • Tradeoffs: Advanced integration surface; runtime style insertion adds complexity and browser style work.

Pitfalls & guarantees: Do not update state or rely on refs being attached. DOM mutation ordering is not an application measurement contract. It does not run on the server; server styles need a separate strategy. Never interpolate untrusted CSS without an appropriate security model.

Related concepts: Style calculation and rendering · Pre-paint measurement · Hook index

Memoization & identity

useMemo

ReactPerformance

Purpose: Caches the result of a pure calculation while dependencies remain equal by Object.is.

When to use: Profiling identifies an expensive repeated calculation, or a stable object enables another measured optimization.

Example

// Fragment inside a component; filterProducts is a pure helper.
const visibleProducts = useMemo(
  () => filterProducts(products, query),
  [products, query]
);

It reuses results only when both dependency references/values remain unchanged; the initial calculation still runs.

When not to use & alternatives: Use a plain calculation when cheap. Use state/ref for semantic persistence or resource ownership; a cache must not be required for correctness.

Benefits & tradeoffs

  • Benefits: Can avoid repeated CPU work and stabilize derived object identity.
  • Tradeoffs: Retains values and compares dependencies; unstable inputs or cheap calculations can erase the benefit.

Pitfalls & guarantees: React may discard the cache; StrictMode may call the calculation twice in development. Keep calculations pure and dependencies complete. React Compiler can reduce manual memoization when enabled, but does not fix bad ownership or impure code.

Related concepts: Memoization tradeoffs · Profiling · Provider identity · Hook index

useCallback

ReactPerformance

Purpose: Caches a function identity while dependencies remain equal; it does not cache results or make the function’s body faster.

When to use: A memoized child benefits from a stable callback prop, or a subscription API’s contract needs a stable function.

Example

// Fragment inside a component; api is a stable imported application API.
const handleSave = useCallback(
  draft => api.save(projectId, draft),
  [projectId]
);
return <MemoizedEditor onSave={handleSave} />;

The editor can reuse the callback until projectId changes. Child memoization only helps if its other props also permit skipping work.

When not to use & alternatives: Use a normal function when identity does not matter. Put an effect-only helper inside the effect rather than adding an unnecessary callback layer.

Benefits & tradeoffs

  • Benefits: Can preserve memoized-child bailouts and make identity contracts explicit.
  • Tradeoffs: Dependency maintenance and cache overhead add complexity without guaranteed savings.

Pitfalls & guarantees: Omitting captured values causes stale closures. Creating the function expression still happens; React chooses whether to return the cached one. Its cache is an optimization, not a permanent identity guarantee. Compiler-enabled code may need less manual memoization.

Related concepts: Result vs. function caching · Callback identity for listener removal · Hook index

Context & external stores

useContext

ReactState management

Purpose: Reads and subscribes to the nearest matching provider’s value. The context distributes data; it does not own state transitions.

When to use: A subtree shares a theme, dependency, session display value, or domain state without prop drilling through unrelated layers.

Example

const ThemeContext = createContext('light');

function ThemedButton() {
  const theme = useContext(ThemeContext);
  return <button className={'button-' + theme}>Save</button>;
}
// An ancestor may override the default with a ThemeContext provider.

The fallback applies only when there is no provider; a provider value of undefined does not restore the fallback.

When not to use & alternatives: Use props for explicit, shallow dependencies; use composition to avoid needless plumbing. For fine-grained frequent subscriptions, consider context selectors or an external store.

Benefits & tradeoffs

  • Benefits: Simple scoped dependency distribution, with different values in different subtrees.
  • Tradeoffs: Changing the provider value updates all consumers of that context, potentially broadening render work.

Pitfalls & guarantees: React compares provider values using Object.is. React.memo does not block a consumed context update; returning one field from a custom hook is not a selector subscription. Split domains/actions deliberately; read the existing architecture rather than rebuilding it here.

Related concepts: Provider implementation · Selectors · Propagation and stability · Hook index

useSyncExternalStore

ReactState managementConcurrency

Purpose: Subscribes to a store outside React while coordinating snapshots with concurrent rendering to avoid inconsistent reads (tearing).

When to use: An external state library or browser source of truth changes independently of React.

Example

// Module-scope functions keep the subscription identity stable.
function subscribeOnline(onChange) {
  window.addEventListener('online', onChange);
  window.addEventListener('offline', onChange);
  return () => {
    window.removeEventListener('online', onChange);
    window.removeEventListener('offline', onChange);
  };
}
const getSnapshot = () => navigator.onLine;
const getServerSnapshot = () => true; // Shared initial SSR/client assumption.

function OnlineStatus() {
  const online = useSyncExternalStore(
    subscribeOnline, getSnapshot, getServerSnapshot
  );
  return <p>{online ? 'Browser reports online' : 'Offline'}</p>;
}

The Boolean snapshot is stable when unchanged. The same server snapshot is used for SSR and initial hydration, then the browser snapshot is read. navigator.onLine does not prove the backend is reachable.

When not to use & alternatives: Use React state/reducers for React-owned data. A hand-written effect subscription may suffice for an independent side effect, but does not replace this API’s store-consistency contract.

Benefits & tradeoffs

  • Benefits: Provides concurrency-safe subscription semantics and an explicit hydration snapshot.
  • Tradeoffs: Requires careful store design, immutable/cached snapshots, and an SSR policy.

Pitfalls & guarantees: subscribe must return unsubscribe. getSnapshot must be Object.is-equal when data has not changed; returning a fresh object each call can loop. Prefer stable subscription functions. SSR consumers need a matching getServerSnapshot or a deliberate client-only strategy. Updates to external mutable stores cannot be made non-blocking merely by wrapping a mutation in startTransition.

Related concepts: Subscription cleanup · Hydration · External store selection · Hook index

Responsive interactions

useTransition

ReactConcurrencyPerformance

Purpose: Returns pending state and startTransition, which marks non-urgent state updates for interruptible background rendering.

When to use: You own the setter for costly tab content or a result view, while input feedback must remain urgent.

Example

// Fragment inside a tab component; tabs is the available tab list.
const [tab, setTab] = useState('overview');
const [isPending, startTransition] = useTransition();
return (
  <>
    {tabs.map(next => (
      <button key={next} onClick={() => {
        startTransition(() => setTab(next));
      }}>{next}</button>
    ))}
    <div aria-busy={isPending}><TabContent tab={tab} /></div>
  </>
);

Urgent interactions can interrupt transition rendering; isPending lets the UI communicate outstanding work.

When not to use & alternatives: Do not transition a controlled text input’s own value update. Use useDeferredValue when you receive a changing value rather than controlling its setter. Use task splitting/workers for long synchronous CPU work.

Benefits & tradeoffs

  • Benefits: Prioritizes interaction feedback and can preserve already-visible content during suspension.
  • Tradeoffs: Background rendering may restart, doing additional work; the pending state needs deliberate UX.

Pitfalls & guarantees: The callback begins immediately; it is not a timer or worker. React 19 supports async Actions, but updates after await currently need another startTransition to be transition updates. General async transitions do not guarantee request completion order; guard stale responses or use an action API with suitable queue semantics.

Related concepts: Deferring received values · Scheduling · Queued Actions · Hook index

useDeferredValue

ReactConcurrencyPerformance

Purpose: Lets part of the UI render with an older value while React prepares the updated value in the background.

When to use: A fast input feeds an expensive result subtree and you want that subtree to catch up without blocking typing.

Example

function Search() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  return (
    <>
      <input aria-label="Search" value={query}
        onChange={event => setQuery(event.target.value)} />
      <div style={{ opacity: query !== deferredQuery ? 0.6 : 1 }}>
        <SlowResults query={deferredQuery} />
      </div>
    </>
  );
} // SlowResults must be memoized or compiler-optimized appropriately.

The input updates immediately. Isolating the costly subtree lets the unchanged deferred value skip its urgent render.

When not to use & alternatives: Use debouncing to reduce request frequency; useTransition when you control the update. A cheap subtree does not need deferred rendering.

Benefits & tradeoffs

  • Benefits: Adaptive scheduling without choosing a fixed debounce delay; can keep stale results visible while loading.
  • Tradeoffs: Users temporarily see stale data, and background renders may restart.

Pitfalls & guarantees: It does not prevent a network request per keystroke or offload CPU work. Pass a stable value; a newly created object can cause unnecessary background renders. React 19 supports an optional initialValue for the initial client render; SSR ignores that argument during initial hydration.

Related concepts: Debouncing · Transitions · Suspense · Hook index

Actions, forms & async resources

useActionState

ReactForms

Purpose: Tracks an Action’s returned state and pending status, with queued dispatches through the same hook. Returns state, dispatchAction, and isPending.

When to use: A form submission returns validation errors or a result needed by the UI.

Example

async function saveProfile(previousState, formData) {
  // Application API: returns { error: string | null }.
  return profileApi.save({ name: formData.get('name') });
}

function ProfileForm() {
  const [state, formAction, isPending] = useActionState(
    saveProfile, { error: null }
  );
  return (
    <form action={formAction} aria-busy={isPending}>
      <label>Name <input name="name" required /></label>
      <button disabled={isPending}>Save</button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}

The form establishes the Action context. The action receives previousState before its form payload and returns the next UI state.

When not to use & alternatives: For trivial synchronous state use useState. For server-state caching, invalidation, and retries, or complex form validation, use an appropriate query/form abstraction rather than expecting this hook to supply those features.

Benefits & tradeoffs

  • Benefits: Combines action results, queueing, and pending state without manual coordination.
  • Tradeoffs: Adds an Action-specific signature and semantics; queueing can delay later submissions.

Pitfalls & guarantees: Manual dispatch needs an appropriate Action/transition context. Represent expected validation failures in state; thrown failures need error handling, such as an Error Boundary. A React Action is not automatically a Server Function. The optional permalink argument supports specific progressive-enhancement flows with Server Functions; framework support and matching action identity matter.

Related concepts: Form-scoped pending UI · Server authorization · CSRF protections · Hook index

useFormStatus

ReactForms

Purpose: Reads the nearest parent form’s submission status and submitted data from a descendant. Import it from react-dom.

When to use: A reusable submit button or status indicator should work without passing pending state through every layer.

Example

import { useFormStatus } from 'react-dom';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>;
}
// Render <SubmitButton /> inside ProfileForm's <form> above,
// replacing its ordinary submit button.

The descendant subscribes to the containing form; it does not need to know which action implementation is used.

When not to use & alternatives: Use useActionState’s isPending when the form-owning component needs that action’s status, or explicit props for a non-form async button.

Benefits & tradeoffs

  • Benefits: Encapsulates form-aware presentation and removes pending-state prop drilling.
  • Tradeoffs: Couples the consumer to a parent form; placement determines which submission it observes.

Pitfalls & guarantees: It cannot read a form merely returned by the same component, or an unrelated/sibling form. Besides pending, it exposes data, method, and action for the relevant submission. Do not assume it observes arbitrary fetches outside the form’s action lifecycle.

Related concepts: Complete form example · Containment and composition · Hook index

useOptimistic

ReactConcurrencyState management

Purpose: Layers temporary speculative state over authoritative base state while an Action is pending.

When to use: A comment, reaction, or toggle should feel immediate before a server confirms the change.

Example

// Fragment inside a component. saveLikes is an application API.
const [likes, setLikes] = useState(initialLikes);
const [optimisticLikes, addOptimisticLike] = useOptimistic(
  likes, (current, amount) => current + amount
);
const [isPending, startTransition] = useTransition();

function like() {
  startTransition(async () => {
    addOptimisticLike(1);
    try {
      const confirmedLikes = await saveLikes();
      startTransition(() => setLikes(confirmedLikes));
    } catch (error) {
      reportError(error); // Application-level failure feedback.
    }
  });
}
return <button disabled={isPending} onClick={like}>{optimisticLikes}</button>;

The speculative increment is visible immediately. Success updates the base value; failure leaves the base unchanged once the Action finishes.

When not to use & alternatives: Use a pending indicator when failure is common or the operation is irreversible/high impact. A query library’s optimistic mutation support may better coordinate an existing server-state cache; see mutation reconciliation.

Benefits & tradeoffs

  • Benefits: Reduces perceived latency and centralizes reconciliation over a base value.
  • Tradeoffs: Requires a credible rollback/failure experience and careful ordering when mutations overlap.

Pitfalls & guarantees: Dispatch optimistic updates in an Action/transition; keep updateFn pure. Commit confirmed data to base state, handle server-generated IDs, and avoid duplicates. Optimistic state is temporary, not durable. This example disables overlapping clicks; multi-request workflows need an explicit ordering policy.

Related concepts: Action lifetime · Transition guards · Hook index

use

ReactRendering

Purpose: Reads a supported Promise or context during rendering. Pending Promises suspend; rejected Promises reach an Error Boundary.

When to use: A Suspense-compatible framework/cache supplies a stable Promise, or conditional context reading fits the component.

Example

function ProductDetails({ productPromise }) {
  const product = use(productPromise);
  return <h2>{product.name}</h2>;
}
// Parent: <Suspense fallback={<p>Loading…</p>}>
//           <ProductDetails productPromise={stablePromise} />
//         </Suspense>
// Provide an Error Boundary for rejected resources.

The Promise is supplied rather than recreated during every client render. Suspense owns the pending UI.

When not to use & alternatives: Prefer await inside async Server Components when it fits. Use a query library/framework for resource ownership; use does not supply caching, invalidation, cancellation, or a fetch trigger by itself.

Benefits & tradeoffs

  • Benefits: Integrates async reads with Suspense and can read context conditionally.
  • Tradeoffs: Requires a resource-lifetime strategy plus loading/error boundaries.

Pitfalls & guarantees: Unlike ordinary hooks, use can appear in loops and conditions, but still only inside components/hooks. Do not wrap Promise reads in try/catch. Fresh uncached client-render Promises are unsupported; obtain stable resources from an appropriate cache/framework. Do not confuse use with useEffect: a resource read is not a render side effect.

Related concepts: Suspense and streaming · Server vs. Client Components · Caching · Hook index

Accessibility & diagnostics

useId

ReactAccessibility

Purpose: Generates an ID suitable for relationships between elements, including consistent SSR/hydration identities.

When to use: Reusable fields need unique label/input or description/input associations across multiple instances.

Example

function EmailField() {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>Email</label>
      <input id={id} type="email" aria-describedby={id + '-help'} />
      <p id={id + '-help'}>Use your work email.</p>
    </>
  );
}

One generated ID can derive related IDs without hard-coded collisions between field instances.

When not to use & alternatives: Use data-derived stable keys for lists, database identifiers for records, and domain keys for caches. A fixed ID only fits a guaranteed singleton.

Benefits & tradeoffs

  • Benefits: Supports reusable accessible markup and coordinated server/client rendering.
  • Tradeoffs: IDs depend on React’s tree coordination and are not portable business identifiers.

Pitfalls & guarantees: Do not call it inside a list loop; extract a field component per instance. Multiple independent roots may need coordinated identifierPrefix values. Server and client trees must match; useId does not fix arbitrary hydration mismatches. It is not currently supported in async Server Components.

Related concepts: Accessibility contracts · Hydration · Hook index

useDebugValue

React

Purpose: Adds a diagnostic label for a custom hook in React DevTools without changing its rendered UI.

When to use: A reusable library/domain hook exposes a useful internal state such as connection status or cache freshness.

Example

function useDebuggedOnlineStatus() {
  const online = useOnlineStatus(); // Shared domain hook, implemented elsewhere.
  useDebugValue(online, value => value ? 'Online' : 'Offline');
  return online;
}

The formatter produces an inspection label; this snippet illustrates diagnostics, not a second subscription implementation.

When not to use & alternatives: Use application logging/telemetry for production diagnostics and the Profiler for timing. Simple local hooks may not need custom labels.

Benefits & tradeoffs

  • Benefits: Makes reusable abstractions easier to inspect; an optional formatter defers label-formatting work until inspection.
  • Tradeoffs: Only benefits inspection and can clutter DevTools if used indiscriminately.

Pitfalls & guarantees: Keep formatting pure. Do not perform expensive work before passing the value if it can live in the formatter. Labels do not measure performance and should not be relied on for application behavior.

Custom hooks

Custom hooks

Design patternReact

Purpose: Functions named use… compose hooks into a coherent reusable capability. Each call has independent state unless it explicitly consumes Context or an external store.

When to use: Several components share a behavior with a meaningful lifecycle and API, such as a debounced value, browser subscription, or domain operation.

Example

function useDebouncedValue(value, delayMs) {
  const [debouncedValue, setDebouncedValue] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(value), delayMs);
    return () => clearTimeout(timer);
  }, [value, delayMs]);
  return debouncedValue;
}

The initial value is immediate; subsequent changes use trailing-edge debouncing. Value/delay changes restart the timer, and cleanup prevents an obsolete timer from committing.

When not to use & alternatives: Use an ordinary utility function for pure non-hook logic. Do not extract merely to hide lines or create useMount wrappers that conceal dependencies. Use Context/store ownership when callers actually need shared state.

Benefits & tradeoffs

  • Benefits: Reuses lifecycle logic, hides implementation details, and exposes a testable domain contract.
  • Tradeoffs: An overly generic API hides dependencies, introduces naming/return-shape commitments, and can obscure state ownership.

Pitfalls & guarantees: Document callback stability, return values, errors, cancellation, and controlled/uncontrolled behavior. Debouncing does not cancel an already-started request. Test observable behavior under changed inputs, cleanup, unmount, failures, and obsolete completions; do not assert incidental render counts.

Related concepts: Debouncing · Cancellation · Domain consumers · Headless APIs · Hook index

Custom hook API variations

Design patternReact

Choosing an owner: Custom hooks reuse logic; they do not automatically share state across callers. Compare hooks, Context, reducers, and stores, then choose Redux Toolkit or XState only when their model solves a concrete sharing or lifecycle problem.

  • Value hooks: Return a focused value or tuple; define initial and subsequent behavior.
  • Subscription hooks: Own setup/teardown; use useSyncExternalStore when an external source of truth needs consistent snapshots.
  • Domain hooks: Expose meaningful state/actions with provider checks and narrow subscriptions; see Context consumer hooks.
  • Headless hooks: Return actions, refs, or prop getters while the caller owns markup. Document accessibility, adapters, and event-handler composition.

Decision process

  1. Who owns the state? Distinguish client ownership from a remote source of truth, then choose local state, Context, a query cache, or another store.
  2. Is this derived data, an event, or synchronization? Calculate during render, act in a handler, or synchronize with an effect accordingly.
  3. Does it need to block paint or be urgent? Reserve layout effects for pre-paint work; transitions for non-urgent UI.
  4. What is the lifecycle contract? Specify dependencies, cleanup, cancellation, snapshots, and race handling.
  5. What evidence justifies optimization? Use profiling before relying on memoization, and keep correctness independent of caches.
