Clarify the product: what are we building?

Prompt: Design a web chat app with direct messages and groups of up to 100 members. Users can send text, load history, see new messages live, and recover after disconnecting. We will support multiple devices per user.

ArchitectureSecurity

Functional requirements describe behavior; non-functional requirements describe quality and constraints. Scope defines which parts of the product and infrastructure this design will cover. The targets below are illustrative assumptions to validate with the stakeholder.

Functional requirements: what users can do

Architecture
  • Create direct conversations and groups of up to 100 members; list the conversations the user belongs to.
  • Add or remove members through authorized operations; enforce current membership for sending, history access, and live subscriptions.
  • Send plain-text messages with a 4 KB text limit and retrieve paginated message history.
  • Receive new messages in near real time while connected, and catch up on missed messages after reconnecting.
  • Show pending, accepted, delivered, read, and failed/uncertain states with defined meanings; allow safe retries without creating a new logical message.
  • Support multiple authenticated devices per user and synchronize their accepted messages and relevant receipt state.
  • Preserve an unsent draft during supported in-app navigation and recoverable connection failures; show clear loading, empty, error, and reconnect states.

Non-functional requirements: quality targets & constraints

ArchitectureResilience
  • Latency: Target p95 online message delivery under 300 ms within the chosen region under normal load; define eligibility and measure failed/timed-out deliveries too. This is not a guarantee for disconnected recipients.
  • Availability: Target 99.9% monthly durable-send success for eligible requests, using the denominator defined in the monitoring contract.
  • Durability: Once accepted, a message survives the defined single database-node/availability-zone failure model; acceptance waits for the configured durable replication acknowledgement.
  • Consistency: Preserve canonical order within each conversation and read-your-writes for acknowledged sends. Receipt/presence state may be eventually consistent. Avoid a second visible message on a retry within the deduplication contract.
  • Capacity: Plan against the illustrative 1 million daily active users, 50 million sent messages/day, and 100,000 concurrent device connections from the workload estimates, with peak and failure headroom.
  • Retention: Retain message history for one year under the case’s policy; account for indexes, replicas, backups, and archival/deletion procedures.
  • Security & privacy: Encrypt transport, authenticate sessions, authorize resources, bound inputs, protect private cached data, and avoid sensitive content in telemetry.
  • Usability & accessibility: Support responsive mobile/desktop layouts, keyboard and screen-reader interaction, draft preservation, truthful pending/error feedback, and deliberate scroll/focus behavior.
  • Operability & resilience: Bound queues/buffers/retries, recover missed events, instrument end-to-end outcomes, and define alerts, graceful shutdown, and degraded behavior.

In scope: what this design covers

Architecture
  • Product: Private one-to-one chat and small groups, plain text, history, membership, receipt cursors, and multiple devices.
  • Frontend: Conversation list, history view, composer, optimistic/pending items, retries, pagination/virtualization, accessibility, and reconnect UX.
  • Application boundary: REST resources and WebSocket events using shared authorization, validation, idempotency, and error semantics.
  • Architecture: Gateway/load balancing, message service, authoritative database, outbox, delivery workers/broker, and transient connection routing.
  • Operations: Single-region multi-zone deployment, capacity estimates, cache/CDN placement, monitoring, failure recovery, and fallback decisions.
  • Dependencies: Integrate an existing identity/session mechanism. Discuss optional approximate presence and offline notifications where they illustrate delivery tradeoffs; a complete notification platform is not required.

Out of scope: boundaries and extensions

Architecture
  • Large public channels, global ordering across conversations, and active-active cross-region writes.
  • Images/files, voice/video calls, full-text search, message editing/deletion, reactions, and threads.
  • End-to-end encryption, device-key recovery, and a complete moderation/anti-abuse platform; basic security, authorization, and rate limiting remain required.
  • Building identity-provider internals, a general push-notification service, or a complete disaster-recovery implementation. State regional-loss limitations and recovery objectives rather than silently promising them.
  • Exactly-once execution or unconditional instant delivery during partitions, overload, or client disconnection. These are excluded guarantees, not hidden features.

Clarifying questions: Can a newly added member read earlier history? We assume yes for this case, subject to current membership. What counts as read: opening the conversation, or actually revealing a message? We use an explicit client report after the conversation is visible and the relevant messages are rendered. Presence is approximate and may lag.

Product choice: If the conversation write authority is unavailable, leave the message pending or fail clearly; do not acknowledge an uncommitted local-only message as durable. Existing object-level authorization applies to history, sends, receipts, and subscriptions.

Define APIs and the meaning of an acknowledgement

Use HTTPS for history, membership, and session operations; use WSS for bidirectional message/receipt events. This is one reasonable transport split. HTTP POST for sends plus SSE for downstream updates is a simpler alternative when that traffic pattern fits; compare WebSockets and SSE.

States: Pending is client-owned intent. Accepted means durable server storage, not that a recipient received it. Delivered means a recipient device explicitly acknowledged receipt under our chosen policy; a socket write is insufficient. Read is an explicit user/device signal, not proof that a human understood the text. Define whether “delivered to a user” means any device or every device; this case uses any authorized device.

Errors: Return correlated codes such as NOT_MEMBER, PAYLOAD_TOO_LARGE, or RATE_LIMITED. A timeout after send is ambiguous: retry with the same clientMessageId or query its outcome. See error and retry contracts.

REST endpoints and idempotency keys

The HTTPS surface models conversations, memberships, messages, and receipt state as resources. WebSocket commands share the same application-service invariants; two transports must not implement different permission or deduplication rules.

Key handling: Scope the send key to authenticated sender + operation; store the conversation, canonical payload fingerprint, state, and result. A unique constraint and the message transaction resolve concurrent retries. Same key/different payload returns a documented conflict (for example 409), while an in-progress retry follows an explicit wait/lookup policy. Keep keys across offline retries; communicate any retention expiry.

Errors: Distinguish unauthenticated (401), forbidden or deliberately hidden resources (403/404 policy), invalid content (documented 400/422), oversized payload (413), throttling (429 with retry guidance), and transient unavailability (503). GET history can be conditionally revalidated with a resource-specific validator; personalized content needs private caching rules. See the reusable REST checklist.

Model authoritative data and access patterns

Start with a relational message store because transactions can atomically enforce membership, allocate a conversation sequence, deduplicate sends, and record an outbox event. This is a starting choice, not a claim that one database fits every chat workload.

Indexes: Order message history by (conversationId, sequence), and index membership lookup and pending outbox scanning. Use keyset/cursor pagination, not offset over a long active conversation. Store history ascending internally; reverse a backward page for display where useful. See pagination.

Transaction: Enforce authorization against a membership version/lock that coordinates with membership changes, serialize sequence allocation on the conversation, insert the message and outbox event, then commit. Handle a deduplication conflict by rolling back and returning the original stored outcome. A UUID identifies a message but does not define its order.

Growth: One year of retained messages requires a real partitioning, archival, backup, and restore plan. Partition/shard by conversation ownership to keep a conversation’s ordered writes together; a large partition key or hot group can still bottleneck. A wide-column store becomes an alternative when access patterns and measured scale justify more application-managed coordination.

Draw the baseline: persistence plus live delivery

Start with stateless HTTP application instances, a gateway tier for long-lived sockets, and a durable database. An outbox relay plus broker decouples persistence from live fanout as operational needs justify it. These are logical roles: the first version can deploy application logic and gateways together.

ArchitectureResilienceAPI integration

Why an outbox? “Commit to DB, then publish” can lose the event if the process crashes between those operations. Publishing first can expose a message that later rolls back. A transactional outbox records the publication intent with the message; the relay retries independently. It gives durable intent with at-least-once publication, not exactly-once effects.

Durability configuration: For this baseline, configure the database so acceptance waits for durable local WAL and a synchronously persisted copy in another availability zone, under the chosen database’s documented commit/failover guarantees. This targets survival of one database-node/zone failure, not loss of the entire region. If the required replica acknowledgement is unavailable, do not acknowledge the write. Backups provide recovery for corruption or operator error; replication alone is not a backup.

Simpler version: At small scale, one service can persist and attempt live delivery with reconnect-based reconciliation; this trades prompt offline notifications and delivery recovery latency for fewer components. Add the broker/outbox when durable asynchronous fanout and independent consumers are requirements.

Connection epochs: A reconnect can replace an old device connection. Register a fresh epoch and delete directory entries conditionally so an old disconnect handler cannot remove the new connection. Where ownership expires, reuse lease/generation principles. Presence is derived and approximate.

Deployment choices: modular first, microservices when justified

Deploying a gateway, message handler, and fanout module separately is a choice, not a prerequisite for the diagram. For an initial product, one modular application plus a durable store and background relay can be easier to operate.

ArchitecturePerformanceResilience

Split when evidence supports it: Gateways have socket/memory-heavy lifecycles; message writes need transactional correctness; fanout/notifications absorb bursts. Extracting these boundaries can allow independent scaling and deployment. Keep message + deduplication + outbox in one transaction owner rather than creating a network call per table.

Cost: Every split adds versioned contracts, network timeouts, tracing, authentication, rollout coordination, and on-call ownership. Start by isolating modules and measuring resource saturation. A “microservice per entity” decomposition would make the send transaction harder without necessarily improving throughput.

Load balancing: Use an HTTP/WebSocket-capable L7 balancer if handshake routing and TLS termination require it. Distribute new connections using measured capacity, readiness and zone health; existing sockets remain pinned to their gateway. Least-connections is a useful heuristic, but hot group traffic can make equal socket counts unequal workloads. Drain before shutdown and provision capacity to survive a zone loss.

Blueprint validation: Before this deep dive, confirm that the stakeholder accepts durable ordered history, small-group fanout, one region, and eventual receipt/presence state. If the intended product is massive public channels, revisit the high-level design first. See architecture tradeoffs.

Directory structure: feature modules and service boundaries

This illustrative monorepo starts with feature boundaries and separates deployment units only when justified. It is a design sketch, not additional application code implemented by this documentation project.

ArchitectureTooling

Ownership rules: UI components do not call the database; transport adapters do not independently reimplement membership rules; workers do not bypass authorization/fencing contracts. Keep the message + deduplication + outbox invariant inside one transaction-owning module. Avoid a giant shared package containing business state or a global database singleton exposed to all layers.

Deployment tradeoff: A monorepo shares versioned source/contract checks, not automatically a shared release lifecycle. Separately deployed consumers still need compatible schemas and rollout plans. See the modular versus microservice decision.

Subtle point: The same clientMessageId must not silently accept different text or a different conversation. Store enough request identity to reject conflicting reuse. Ordering and consistency: define the visible guarantees

Guarantee a canonical order within one conversation, not a global order across the app. Concurrent sends from different users receive server-assigned sequences; there is no unique “real-world first” when their operations overlap.

ConcurrencyArchitectureResilience

Implementation: A transactional conversation row counter or a single write owner serializes accepted writes. The database’s ownership/failover mechanism must prevent two unfenced owners from assigning conflicting sequences. This introduces contention in a hot conversation; shard different conversations independently before redesigning ordering for exceptionally large channels.

Live transport: A WebSocket preserves order on its own connection, but retries, separate gateways, broker consumers, and reconnect can reorder application events. Store events by canonical sequence, deduplicate, and recover detected gaps. Broker partition ordering only covers its own append order; ensure per-conversation relay ordering if relying on it, or reconcile against database sequences.

Read consistency: An accepted send can be absent from a lagging replica. For read-your-writes, serve the authoritative writer or use a supported minimum-position/consistency-token policy. Do not hide stale-replica gaps as permanent message loss. History is durable; presence and receipts can be eventually consistent.

Availability tradeoff: During loss of safe write ownership, reject or hold sends as pending rather than pretending they are durably ordered. Acknowledged writes survive only the stated replication failure model: async cross-region copies can still lose recent data in regional disaster recovery. State RPO/RTO explicitly before promising zero loss.

Reconnect and offline catch-up: live events are an optimization

Clients need a reconciliation protocol, not just an automatic socket reconnect. Treat authoritative history as the recovery source and live events as a low-latency delivery path.

ResilienceBrowserState management

Why subscribe first? Fetching history and only then subscribing can miss a message committed in between. A framework-specific replay token or durable per-user sync stream is another valid design, but must define the same boundary. Never assume socket replay exists without a server protocol.

Multi-conversation recovery: At small scale, sync each known conversation from its cursor and refresh the conversation list to discover new membership. At larger scale, introduce a per-user change feed with retention and resume tokens. If tokens expire, fall back to a bounded full refresh. A sequence cursor is not authorization.

Browser limits: Keep offline cursors/drafts in appropriate storage, account for quota/eviction, and avoid treating local persistence as a durable server acknowledgement. Coordinate duplicate tabs if needed using cross-tab synchronization.

Queue vs. topic: fanout and offline notifications

Fanout converts one message into recipient/device deliveries. For groups capped at 100, looking up members and routing to their online devices is a reasonable starting point. Avoid writing a full message copy per recipient unless read patterns justify the storage amplification.

ArchitectureConcurrencyResilience

Queue versus topic: A queue normally distributes each work item to one competing consumer. An event topic/stream lets independent subscriptions or consumer groups each process the same message event. Within one Kafka consumer group, partitions are assigned among consumers; every consumer does not automatically receive every event.

Kafka option: Key by conversationId to keep one conversation on a partition, then use independent consumer groups for delivery and notifications. Kafka retains a replayable log and supports partition ordering; it adds operational cost and finite retention. A simpler managed queue or outbox poller may be enough. Kafka transactions do not make database writes and arbitrary push-provider calls one exactly-once transaction.

Routing: A fanout worker consults the connection directory and sends to the owning gateways through internal routing/pub-sub. A live ephemeral pub/sub system can lose events; durable history and catch-up repair missed delivery. Broker backlog must not turn into unbounded memory in gateways.

Offline notification: After a short policy-defined delay, check receipts/preferences and send a bounded push notification. Presence alone is too stale to prove that the user received the message. Deduplicate notification jobs; lease/sweeper recovery can help if the queue does not already provide redelivery. See recovery mechanisms.

Large-channel extension: Huge groups create O(member/device count) fanout and hot conversations. Consider fanout-on-read, selective subscription, batching, separate channel infrastructure, and explicit product latency tradeoffs. Do not apply the small-group design unchanged.

Caching strategies: Cache-aside reads the database on a miss and fills the cache; invalidation and races remain your responsibility. Write-through coordinates writes via a cache layer but adds failure coupling. Write-behind buffers durable writes and risks loss unless backed by a durable contract; it is unsuitable for acknowledging messages based only on volatile memory. Use TTL as a staleness bound, not proof of current permission.

Load balancing: Existing sockets are not redistributed when adding gateways; new connections may balance better while older instances remain busy. Use connection draining and jittered reconnects during deploys. Apply graceful shutdown and avoid reconnecting all clients at once.

CDN: deliver the app shell, isolate private data

Use a CDN to serve content-hashed JavaScript/CSS and approved public static assets near users. It reduces origin load and startup latency; it does not replace WebSocket gateways, private message storage, or authorization.

HTTPPerformanceSecurity

Deployment: Publish versioned assets before serving HTML that references them, retain prior assets for an appropriate transition window, and use an HTML freshness/revalidation policy compatible with deployment and rollback. Long-lived immutable caching fits hashed assets; avoid assigning that same policy indiscriminately to the HTML entry point.

Private media extension: Upload/download through scoped signed URLs or an authenticated media edge flow, with bounded expiry, object permissions, scanning, and a deliberate cache-key policy. Ensure a cached object is not served to an unauthorized caller merely because an earlier authorized request warmed it.

Failure: Observe asset load failures and CDN/origin errors separately from API failures. Retry boundedly, detect a stale HTML/missing-chunk mismatch, and offer a controlled refresh while preserving drafts where safe. A fallback origin must retain the same security and capacity protections. Offline caching via a service worker is an additional design with versioning/revocation costs, not a free guarantee.

Fallbacks: preserve truth and recover deliberately

A fallback strategy defines a degraded but honest service behavior, with a trigger and a recovery path. It is not “retry forever” or return a successful-looking response from incomplete data.

Transport caution: HTTP+polling fallback must be designed and capacity-tested, not improvised during an outage. SSE is useful if available but may share proxy/network failure causes with WebSockets. Switching protocols changes load, ordering, and retry paths; use one canonical persistence/deduplication contract.

Wrap-up decision: State which feature degrades, which invariant remains, how long recovery may take, and what the user can safely do. See circuit breakers and bulkheads and observability and fallback principles.

Frontend design: reliable UX over an unreliable connection

Model a chat UI as server-owned history plus client-owned interaction state. A socket event is an update source, not a replacement for an authoritative cache and reconciliation rules.

ReactState managementAccessibility
  • Ownership: The URL owns selected conversation; component state owns draft and focus; a server-state cache owns normalized messages and receipts.
  • Optimistic send: Key pending items by clientMessageId, merge accepted events with canonical IDs, and expose retry/error states. Avoid duplicate display if acceptance arrives before the send callback.
  • Ordering: Render canonical sequence, retain pending items with an explicit temporary policy, and recover gaps. Do not sort exclusively by device timestamps.
  • History: Paginate and virtualize long lists; preserve scroll position when prepending older messages. Auto-scroll only when the user is near the bottom or has explicitly requested it.
  • Lifecycle: Cancel obsolete history fetches and unsubscribe from old conversations. Clean up sockets/listeners and manage reconnect state. Background tabs and offline transitions can pause timers.
  • Accessibility: Label the composer, support keyboard actions, and announce new messages without repeatedly reading the full history or moving focus.

Existing material: Use server versus client state, optimistic conflict handling, focus and scroll behavior, and virtualization and loading techniques.

Security and privacy boundaries

Authenticate the connection and authorize each resource operation. A valid session does not authorize every conversation, and a gateway subscription made earlier does not grant permanent access.

SecurityAPI integration

WebSocket specifics: Use WSS, validate the handshake Origin against an allowlist when browser cookies authenticate it, and protect against cross-site WebSocket hijacking. CORS is not a substitute for WebSocket Origin validation or server authorization. Avoid long-lived bearer tokens in URLs because URLs can leak into logs; use an appropriate cookie/session or short-lived connection-ticket flow.

Session changes: Define token/session expiry and revocation on long-lived connections. On logout, close relevant sessions, revoke access, and clear personalized cached content. Recheck or invalidate permissions when membership changes, including before fanout; define whether revocation can race an already authorized delivery.

Content: Render plain text using safe text rendering. If rich content is added, use a narrowly defined format and the existing XSS defenses, including sanitization where HTML is allowed. Apply abuse controls, payload limits, retention, and restricted operational access.

Encryption scope: TLS protects transit; encryption at rest protects stored data under a key-access model. Neither is end-to-end encryption. E2EE changes device keys, group membership, recovery, search, moderation, and server visibility and needs its own design. See session lifecycle.

Review: defend the design, then change a constraint

One-minute explanation: Keep durable ordered history in the message store. Acknowledge only after commit, with a stable client operation ID for retries. Publish committed changes through an outbox, fan out to currently authorized devices, and treat reconnect history synchronization as the recovery path. Scale gateways separately from conversation write ownership; keep presence and receipts eventually consistent where the product permits it.

ArchitectureResilience

Challenge yourself: What if the database commits but the socket closes? What if an outbox event is published twice? What if a replica is behind? What if the broker is unavailable for an hour? What if a user is removed while an event is queued? For each answer, identify the authoritative record and the precise recovery path.

Next design iteration: Choose one extension—large channels, regional disaster recovery, attachments, or E2EE. Change the assumptions and estimates first, then explain which component contracts must change. Do not append every possible component to the baseline.
